# V1.2 学习笔记

## 一、我们到底做了什么（用最白的话讲）

我们给 STM32 定了一套"说话规矩"。树莓派是老板，MCU 是下属。老板可以问各种问题（读寄存器），也可以下命令（写寄存器）。下属必须听懂每一句话，做出正确反应，遇到不合理的要求要拒绝并汇报"你刚才说的不对"。

具体做了四件事：
1. **定了消息格式**：每次通信固定 5 个字节，谁说什么、怎么说、什么顺序，全部规定死
2. **定了能聊的话题**：设备 ID、固件版本、状态、控制、采样率——一共 5 个"话题"（寄存器）
3. **定了出错怎么办**：问了不存在的话题、给了不合理的数字、试图改只读信息——每种错都有明确处理
4. **跑了一万次验证**：证明这套规矩在高强度下不会乱

## 二、核心知识点

### 知识点 1：SPI 的本质——同时交换

SPI 不是"你说完我再说"，是双方同时交换数据。想象两个人各拿一叠卡片，每次时钟响一下，双方同时递出一张。所以当树莓派发命令过去的时候，MCU 也必须同时发点什么回来——问题是这时候 MCU 还不知道树莓派问了什么，因为命令还没传完。

**关键理解**：SPI slave 的发送内容必须在事务开始之前就装好，不能"边收边决定回什么"。这是硬件层面的限制，不是软件写得不好。

### 知识点 2：流水线协议——为什么要两帧才能读一次

因为知识点 1 的限制，我们选了流水线方案：

- **第 N 帧**：树莓派发读命令，MCU 同时发出的是"上一帧准备好的东西"（第一次就是空的）
- **第 N+1 帧**：树莓派发 NOP（无操作），MCU 发回第 N 帧命令对应的数据

代价：每次读要两个事务。
好处：MCU 有整个帧间隔的时间去准备数据（毫秒级），而不是必须在一个字节传输时间内完成（微秒级）。以后换中断模式、换 DMA，协议层完全不用动。

**面试怎么讲**："我选流水线是因为它把协议正确性和 CPU 响应速度解耦了。slave 不需要在 8 微秒内算出返回值，只需要在两帧之间准备好就行。"

### 知识点 3：ECHO 字节——流水线的保险丝

MCU 返回的第一个字节是上一帧收到的 CMD 原样回传。这不是客气，是防错。

想象流水线错位了——比如某一帧因为干扰没传成功，Pi 以为自己在读 SAMPLE_RATE，实际上拿到的是 STATUS 的值。如果没有 ECHO，Pi 会把 STATUS 的值当成采样率用，而且根本不知道错了。有了 ECHO，Pi 立刻能发现"我问的是 0x04，你回的 echo 是 0x02，对不上"，马上报错。

**一句话**：ECHO 让错误变成"可检测的"，而不是"悄悄错了"。

### 知识点 4：定长帧——为什么不做变长

SPI slave 是硬件移位寄存器。时钟每跳一次，它机械地推出一个 bit，根本没有机会停下来说"等等，让我看看这帧多长"。如果帧长不固定，slave 不知道什么时候一帧结束、下一帧开始，解析就会出问题。

5 字节定长 = 1 字节命令 + 4 字节数据。简单、对齐、不需要帧头帧尾、不需要转义字符。

### 知识点 5：寄存器——嵌入式设备的"API"

寄存器就是设备暴露给外界的一组"接口"。每个寄存器有一个地址、一个功能、一个读写权限。你可以把它类比成一个结构体的字段——地址 0x00 是设备名，0x04 是采样率，等等。

跟软件 API 的区别：寄存器是硬件层面的约定，通常只有几个到几十个，每一个都有精确定义的行为、位宽、复位值。没有"调用失败抛异常"这回事，只有"写了之后状态位变了"。

**面试关键句**："我的设备暴露了一组寄存器，master 通过读写这些寄存器来配置和控制设备。这和真实芯片的寄存器接口工作方式是一样的。"

### 知识点 6：错误处理的设计哲学

三条原则：
1. **不崩**：不管收到什么垃圾命令，设备永远不会挂掉或停止响应
2. **不执行**：非法操作被拒绝，设备状态不变（比如超范围的采样率不会被写进去）
3. **可观测**：每种错误在 STATUS 寄存器里有对应的标志位，master 随时能查到出了什么问题

为什么用"锁存 + 手动清除"而不是"读时自动清除"：如果读 STATUS 就自动清除错误位，那你没办法在不破坏状态的前提下观察状态——调试的时候读一次就没了，下次再读就看不到了。锁存意味着错误一直保留到你显式地说"我知道了，清掉"。

### 知识点 7：OVR 和 resync——阻塞模式的天然缺陷

阻塞模式下 MCU 调用 `HAL_SPI_TransmitReceive` 然后等着。如果 Pi 在 MCU 还没准备好的时候就发了数据，硬件移位寄存器收到了数据但没人取，新数据又来了把旧数据覆盖了——这就是 OVR（overrun）。

`spi_resync()` 做的事：把 SPI 关掉、清空残留数据、清错误标志、重新打开。然后在 STATUS 里标一个 `SPI_RESYNC`，告诉 Pi "我刚才出了一次事故，已经恢复了"。

**为什么 SPI_RESYNC 位很重要**：它让你能量化阻塞模式有多不可靠。跑一万帧，记录 resync 了几次。V1.3 换中断模式后这个数字应该归零——这就是改进的量化证据，而不是凭感觉说"好像稳了"。

### 知识点 8：NOP 命令的角色

NOP（地址 0x7F）什么都不做。它存在的唯一目的就是给流水线提供一个"占位帧"——当你只想取回上一帧的结果、不想发新命令时，就发 NOP。

但其实你也可以不发 NOP，而是在取回数据的同时塞一条新命令进去。这样流水线就满载了，效率翻倍。测试脚本里用 NOP 纯粹是为了代码清晰。

## 三、面试怎么讲 V1.2

**如果被问"你的协议怎么设计的"**：

> 我定了一个 5 字节定长帧格式，通过流水线方式通信。定长是因为 SPI slave 是移位寄存器，没法在传输过程中解析帧长。流水线是因为 slave 必须在事务开始前装好发送数据，不能收到命令后再临时决定回什么。每帧第一个字节是命令，后四个字节是数据。返回帧的第一个字节是 echo，用来校验流水线有没有错位。

**如果被问"怎么验证的"**：

> 先做了 7 项功能测试覆盖正常读写和各种错误情况，然后跑了 10000 帧随机读写混合的压力测试，零 echo 失配。

**如果被问"阻塞模式有什么问题"**：

> 阻塞模式下 MCU 等在 HAL 调用里，如果 master 发得太快，slave 来不及准备就会 overrun。我加了 resync 恢复机制和状态位来量化这个问题的发生频率。V1.3 切到中断模式后，slave 随时在监听，这个问题就消除了。
