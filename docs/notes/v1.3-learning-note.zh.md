# V1.3 学习笔记

## 一、整体在做什么

用一句话讲：MCU 假装自己是一个采集仪器，按设定的频率不停地"测量"数据（其实是编造的），存在内部缓冲区里，等 Pi 来取。

MCU 上同时发生两件事，靠两个中断驱动：

```
┌─────────────────────────┐    ┌─────────────────────────┐
│    定时器中断 (TIM2)     │    │     SPI 中断 (SPI2)     │
│                         │    │                         │
│  谁触发：MCU 内部时钟    │    │  谁触发：Pi 发 SPI 数据  │
│  多久一次：由采样率决定   │    │  多久一次：Pi 想读就读   │
│  做什么：产一个 sample   │    │  做什么：解析命令、回数据  │
│         塞进 FIFO       │    │         从 FIFO 取数据   │
│                         │    │                         │
│  只动 fifo_head（写指针）│    │  只动 fifo_tail（读指针） │
└─────────────────────────┘    └─────────────────────────┘
```

主循环是空的。CPU 平时闲着，哪个中断来了就跑哪个。

## 二、每个函数做什么

### fifo_push() — 往缓冲区里塞一个数据

**谁调用它**：定时器中断回调，每次定时器到期时。
**做什么**：把一个新的 sample（带序列号）放到 FIFO 的 head 位置，然后 head 往前移一格。如果 FIFO 满了（head 的下一格就是 tail），就丢弃这个 sample，overflow 计数器加一。

```
FIFO（环形数组，想象成一个圆圈）：

    head                    tail
     ↓                       ↓
  [  ][新数据][数据][数据][旧数据][  ][  ]
         ↑                    ↑
      写在这里              从这里读走

head 只往前走，不管 tail 在哪。
满了就丢弃，不等、不阻塞。
```

### fifo_peek() — 看一眼最老的数据，但不拿走

**谁调用它**：SPI 中断回调（通过 reg_read → DATA_SEQ）。
**做什么**：看 tail 位置的数据，把序列号和值复制出来，但 tail 指针不动。相当于"预览"。
**为什么需要它**：Pi 读数据分两步——先读序列号（DATA_SEQ），再读值（DATA_VAL）。读序列号时不能弹出数据，否则读值时就没了。

### fifo_pop() — 把最老的数据弹出来

**谁调用它**：SPI 中断回调（通过 reg_read → DATA_VAL）。
**做什么**：tail 指针往前移一格。数据本身不需要清除，下次被覆盖就行。
**什么时候调**：Pi 读 DATA_VAL 时。读完值之后才弹出，保证序列号和值是配对的。

### fifo_level() — 看缓冲区里有多少个数据

**谁调用它**：SPI 中断回调（通过 reg_read → FIFO_LEVEL）。
**做什么**：用 head 和 tail 的位置差算出当前有几项。不修改任何变量，纯计算。
**关键细节**：这是一个函数，不是变量。之前有一个 `fifo_count` 变量被两个中断同时修改导致数据竞争，改成函数后就没有共享变量了。

### update_data_ready_gpio() — 告诉外面"我有数据"

**谁调用它**：读走数据后（DATA_VAL 的 reg_read 里）。
**做什么**：FIFO 非空就把 PA8 拉高（3.3V），空了就拉低（0V）。
**现在有什么用**：V1.3 里 Pi 还不用这根线（纯轮询），逻辑分析仪上能看到它。V3 写 kernel driver 时这根线会变成 GPIO 中断源——Pi 不再需要反复问"有数据吗"，MCU 会主动通知。

### update_timer_rate() — 设定产数据的频率

**谁调用它**：写 SAMPLE_RATE 寄存器时、START 采集时。
**做什么**：改 TIM2 的自动重装载值，控制定时器多久触发一次。

```
芯片时钟 72 MHz
  ÷ Prescaler 7200 = 10000 Hz 基频
  ÷ Period          = 最终频率

例：SAMPLE_RATE = 100 Hz → Period = 10000/100 = 100 → 每 100 个 tick 触发一次
例：SAMPLE_RATE = 1000 Hz → Period = 10000/1000 = 10 → 每 10 个 tick 触发一次
```

### HAL_TIM_PeriodElapsedCallback() — 定时器中断回调

**谁调用它**：HAL 库，当 TIM2 的计数器溢出归零时自动调用。
**做什么**：检查采集是否在运行（CONTROL.START），如果是，生成一个 sample 塞进 FIFO。
**频率**：由 SAMPLE_RATE 决定。100 Hz 就是每秒调用 100 次，1000 Hz 就是每秒 1000 次。

### HAL_SPI_TxRxCpltCallback() — SPI 帧完成回调

**谁调用它**：HAL 库，当一帧 5 字节收发完成时自动调用。
**做什么**：两件事——调用 handle_frame() 处理刚收到的命令并准备好回复，然后调用 HAL_SPI_TransmitReceive_IT() 挂上下一帧的接收。
**跟 V1.2 的区别**：V1.2 是主循环里阻塞等待（HAL_SPI_TransmitReceive），CPU 卡在那里什么都干不了。现在是中断模式，CPU 平时可以做别的事（或者闲着），SPI 数据来了才被叫醒。

### HAL_SPI_ErrorCallback() — SPI 出错回调

**谁调用它**：HAL 库，当 SPI 传输出错时（比如 overrun）。
**做什么**：调用 spi_resync() 清理硬件状态，重新挂上接收。标记 STATUS.SPI_RESYNC 让 Pi 知道出过事。

### handle_frame() — 解析命令、准备回复

**跟 V1.2 完全一样**，只是 reg_read 里多了四个 case（FIFO_LEVEL、DATA_SEQ、DATA_VAL、OVERFLOW_COUNT）。

### reg_read() / reg_write() — 寄存器读写

**跟 V1.2 的逻辑一样**，reg_write 里 CONTROL 分支加了启停定时器的操作（HAL_TIM_Base_Start_IT / Stop_IT），START 时清空 FIFO 和序列号。

## 三、Pi 端读一个 sample 的完整流程

```
Pi                              MCU
│                                │
│  帧1: 发 [0x05][0][0][0][0]   │  ← 读 FIFO_LEVEL
│  ────────────────────────────> │
│  帧2: 发 [NOP][0][0][0][0]    │  ← 取回 level 值
│  <──────────────────────────── │  收到 level = 3（有 3 项）
│                                │
│  帧3: 发 [0x06][0][0][0][0]   │  ← 读 DATA_SEQ（peek，不弹出）
│  ────────────────────────────> │
│  帧4: 发 [NOP][0][0][0][0]    │  ← 取回序列号
│  <──────────────────────────── │  收到 seq = 42
│                                │
│  帧5: 发 [0x07][0][0][0][0]   │  ← 读 DATA_VAL（弹出！tail 前进）
│  ────────────────────────────> │
│  帧6: 发 [NOP][0][0][0][0]    │  ← 取回数据值
│  <──────────────────────────── │  收到 val = 12345
│                                │
│  现在 Pi 有了: seq=42, val=12345
│  FIFO 里还剩 2 项
```

6 帧 SPI 才能读走 1 个 sample。每帧约 0.5ms + 传输时间 ≈ 总共约 5ms/sample。
所以 Pi 轮询模式的上限大约是 200 samples/sec。

## 四、出过的三个问题和怎么解决的

### 问题 1：定时器一启动 SPI 就全乱了（echo 全变 0x00）

**现象**：回归测试通过，采集一启动 SPI 通信就死了。
**原因**：SPI2 和 TIM2 的中断优先级都是默认的 0（相同）。定时器回调执行时间较长，SPI 帧处理被延迟，HAL 状态机错乱。
**解决**：CubeMX → NVIC → Priority Group 改成 4 bits → SPI2 优先级 1（高），TIM2 优先级 3（低）。SPI 可以打断定时器，定时器不能打断 SPI。

**知识点**：中断优先级。数字越小越高。高优先级中断可以"抢占"低优先级中断。

### 问题 2：加了 fifo_push 之后 MCU 崩溃（HardFault）

**现象**：定时器回调里什么都不做时 SPI 正常。加了 fifo_push 就崩——echo 全变 0x7F 或 0x00。

**出问题的代码**：

```c
static void fifo_push(uint32_t value) {
    __disable_irq();          // ← 关掉所有中断

    // ... 操作 fifo_count ...
    fifo_count++;

    __enable_irq();           // ← 重新打开中断
}
```

**为什么要加锁**：`fifo_count` 这个变量被两个中断同时修改——定时器里 `fifo_count++`，SPI 里 `fifo_count--`。`fifo_count++` 在 CPU 层面其实是三步：读出旧值 → 加一 → 写回。如果两个中断同时做这三步，最终结果会是错的。所以用 `__disable_irq()` 关中断，让这三步不被打断。

**为什么关中断会搞崩 SPI**：HAL 的 `HAL_SPI_TransmitReceive_IT` 收 5 个字节不是一次性完成的，是**每个字节触发一次中断**：

```
字节1 到达 → SPI中断 → HAL 取出放到 rx_buf[0]
字节2 到达 → SPI中断 → HAL 取出放到 rx_buf[1]
字节3 到达 → SPI中断 → HAL 取出放到 rx_buf[2]
字节4 到达 → SPI中断 → HAL 取出放到 rx_buf[3]
字节5 到达 → SPI中断 → HAL 取出放到 rx_buf[4] → 调用 TxRxCpltCallback
```

SPI 的 DR 寄存器只能存一个字节。如果一个字节到了没人取，下一个字节就会覆盖它。

**崩溃的完整时间线**：

```
t=0µs    Pi 发字节1 → SPI中断 → HAL 取走 ✅
t=8µs    Pi 发字节2 → SPI中断 → HAL 取走 ✅
t=16µs   Pi 发字节3 → 硬件收到，放进 DR 寄存器
         但就在这时定时器中断触发了！
         → 进入 fifo_push()
         → __disable_irq()  ← 所有中断被关！
         → 执行 fifo_count++
         → 这段时间 Pi 继续发字节4
         → 字节4 到达，SPI 硬件把它放进 DR
         → 字节3 被覆盖了！OVR（overrun）！
         → __enable_irq()   ← 中断恢复
         → SPI 中断触发，HAL 从 DR 取出一个字节
         → 它以为这是字节3，实际上是字节4
         → rx_buf[2] = 字节4 的值（错的）
         → 然后等字节4，但字节4 已经被当成字节3 了
         → 帧边界永久错位
         → 之后所有帧都是错的
```

注意：HAL 并不知道自己取错了。它不能分辨"这是第 3 字节还是第 4 字节"，DR 里面就是一个 8 位的值，先到的被后到的覆盖了，HAL 取到什么就当什么。它只是从这一刻起，每一帧都错位了。

**本质上是优先级问题**：`__disable_irq()` 等于说"我现在是最高优先级"。但 SPI 硬件不会等你——Pi 的时钟在跑，字节在一个接一个地到达，DR 只能存一个。你关中断 10 微秒，这段时间如果来了两个字节，第一个就永远丢了。

**解决方案——无锁 FIFO**：

```c
static void fifo_push(uint32_t value) {
    uint16_t next = (fifo_head + 1) % FIFO_DEPTH;
    if (next == fifo_tail) {
        fifo_overflow++;
        return;
    }
    fifo_buf[fifo_head].sequence = seq_counter++;
    fifo_buf[fifo_head].value    = value;
    fifo_head = next;
    // 从头到尾没有关中断
    // SPI 中断随时可以打断这个函数（SPI 优先级更高）
    // 打断了也没事，因为 SPI 只改 fifo_tail，这里只改 fifo_head
}
```

去掉了 `fifo_count`，定时器只改 `fifo_head`，SPI 只改 `fifo_tail`，没有任何变量被两边同时修改。要算有多少项就用 `head - tail`，只读不写。在 Cortex-M3 上，对齐的 16 位读写是一条指令（原子操作），不可能读到"改了一半"的值。

**知识点**：
- **数据竞争**：两个中断同时改同一个变量，结果不可预测
- **临界区（关中断）**：能保护共享数据，但会屏蔽所有中断，在"SPI 每字节都需要中断"的场景下不能用
- **无锁设计**：通过消除共享变量来消除竞争，比加锁更根本
- **OVR（overrun）**：SPI 硬件收到新字节但旧字节还没被取走，新的覆盖旧的，数据永久丢失
- **原子操作**：Cortex-M3 上对齐的 16/32 位读写是单条指令完成的，不会被中断打断到"一半"的状态

### 问题 3：1000 Hz 下 SPI 通信崩溃

**现象**：1000 Hz 采集时 Pi 疯狂读 FIFO，echo 开始出错。
**原因**：不是代码 bug。Pi 每 5ms 读一个 sample，1000 Hz 每 1ms 产一个，FIFO 永远不空，Pi 陷入不间断的 SPI 循环。密集的 SPI 中断 + 定时器中断交替触发，最终 HAL 状态机被打乱。
**解决**：不在 V1 里解决。这是 spidev 轮询方案的天花板（约 200–300 Hz）。V3 的 kernel driver 用 GPIO IRQ + 内核 SPI 驱动会突破这个限制。

**知识点**：知道系统的上限在哪，比无限优化更重要。记录下来作为下一版的改进动机。

## 五、面试怎么讲 V1.3

**如果被问"你的设备怎么采集数据的"**：

> 我用一个硬件定时器按设定的频率产生数据，每次定时器到期触发中断，在回调里把数据塞进一个 32 项的环形缓冲区。主机通过 SPI 读寄存器来取数据——先读序列号确认是哪个 sample，再读数据值并弹出。序列号是递增的，主机可以通过检查连续性来检测是否丢数据。

**如果被问"你遇到过什么并发问题"**：

> 定时器和 SPI 两个中断同时操作 FIFO，最初我用一个共享的 count 变量，加了关中断保护。但 HAL 的 SPI 中断模式是逐字节中断的，关中断会导致 SPI 传输中途丢中断，硬件溢出。最后我改成了无锁设计，生产者只写 head，消费者只写 tail，在 Cortex-M3 上对齐的 16 位读写是原子的，不需要任何保护。

**如果被问"轮询模式的上限是多少"**：

> 大约 200 到 300 Hz。读一个 sample 需要 6 帧 SPI 通信，每帧加上帧间隔大约 1ms，总共 5–6ms。超过这个频率主机就追不上了。这就是我后来写 kernel driver 用 GPIO 中断驱动读取的原因。
