## 文件描述符（file descriptor）

Linux 里，一旦你打开了任何"文件"——不管是磁盘上的普通文件、一个网络
连接（socket）、还是一个设备文件（比如 `/dev/acq0`）——内核会返回给
你一个小整数，这个整数就是接下来所有操作（读、写、关闭）用来指代
"这个已经打开的东西"的凭证。可以理解成"内核发给你的一张号码牌"：你
后续说"我要读 3 号"、"我要关 3 号"，内核就知道你说的是哪个打开的东
西。

`0`、`1`、`2` 这三个号码在几乎所有程序里都被提前占用了，分别是标准
输入（stdin）、标准输出（stdout）、标准错误（stderr）——这是 Unix
沿用了几十年的约定，不是巧合。

例子：`Device::fd_`（`userspace/device-service/include/device.hpp`）。

## RAII（资源获取即初始化）

C++ 管理"资源"（文件、内存、锁、网络连接……）最基础也最重要的一个惯
用法，全称 Resource Acquisition Is Initialization。核心思想：**把资
源的生命周期绑定到一个对象的生命周期上**——对象一创建（构造函数），
资源就准备好；对象一销毁（析构函数），资源就自动被释放。

关键好处：调用者永远不需要手写"记得最后要释放"这种代码，也不会因为
中途抛出一个异常导致某个资源忘了释放——只要对象离开作用域（正常执行
完，或者异常导致栈展开），析构函数保证会被调用。这是 C++ 里"确定性
资源管理"的根基，`std::unique_ptr`（管理内存）、`std::lock_guard`
（管理锁）、`std::ifstream`（管理文件）全都是这个模式的具体应用。

例子：`Device` 的析构函数在 `fd_ >= 0` 时调用 `::close(fd_)`
（`userspace/device-service/src/device.cpp`）——调用者永远不用自己
记得关设备。

## 错误处理：错误码 vs 异常

C 语言的传统做法是"错误码"：函数失败时返回一个特殊值（比如 `-1`），
把具体错误信息放进全局变量 `errno` 里，调用者必须**每次都记得手动检
查**返回值，一旦漏检查，错误就会被悄悄吞掉、程序继续拿着无效数据往
下跑。

C++ 的异常（`throw`/`try`/`catch`）是另一种模式：出错时直接"抛"一个
对象出去，正常的执行流程被打断，一路往外跳，直到遇到某个 `catch` 块
接住它为止——**没人接住的话，程序会终止**，不会出现"错误被悄悄忽
略"的情况。代价是：异常路径的控制流不像顺序代码那么直观，得靠"哪里
`try` 了、哪里 `catch` 了"来推理。

这个项目里的做法：包一层——原始系统调用（`::open`/`::read`）还是走
错误码，但包装函数（`Device::open()`/`read_sample()`）检查完错误码
后立刻转换成异常抛出去，后面所有业务代码就只管拿 C++ 异常处理，不用
反复手写"if 返回值 < 0"这种检查。

## 线程生命周期的标准骨架

任何"起一个后台工作线程，需要能被外部安全叫停"的场景，都是这四步：

1. **声明**：一个 `std::thread` 成员 + 一个 `std::atomic<bool>
   stop_requested_` 标志（用 `atomic` 是因为这个标志会被两个线程同
   时读写，普通 `bool` 在多线程下读写没有"看到最新值"的保证）。
2. **启动**：把标志设成 `false`，然后把某个成员函数整个"丢给"一个新
   线程去跑（`thread_ = std::thread(&Class::run, this)`）——这一行
   执行完，新线程已经在后台跑起来了，调用者立刻往下走，不等它。
3. **线程体**：一个 `while (!stop_requested_) { ... }` 循环，不停检
   查这个标志。
4. **停止**：把标志设成 `true`，然后调用 `thread_.join()`——"阻塞等
   待这个线程真正跑完退出"。

**这四步里真正的设计难点在第 4 步**：如果线程正卡在循环体里的某个
"阻塞调用"上（比如正在等一条还没到的数据），光把标志改成 `true` 没
用——那个线程根本没在检查这个标志，它在睡觉，等的是别的东西。
`join()` 会一直卡住。解法见下一节"等待方式"。

例子：`AcquisitionWorker`（`userspace/device-service/include/
acquisition_worker.hpp` + `.cpp`）。

## 等待方式的三种类型

程序"等一个还没发生的事情"，大致三种做法：

- **忙等（busy loop）**：不停地问"好了没？好了没？好了没？"——最简
  单但极其浪费 CPU，基本没人这么写。
- **纯阻塞等待**：调用一个函数（阻塞式 `read()`、条件变量的
  `wait()`），操作系统直接把这个线程"挂起"、完全不占 CPU，直到条件
  真正满足才唤醒它。省 CPU，但外部没有安全的办法主动打断它——这正是
  上一节"第 4 步"卡住的原因。
- **带超时的等待**：还是阻塞，但告诉它"最多等 N 毫秒"，时间到了不管
  条件满不满足都自动醒过来。醒来后可以做点别的事——比如检查一下"要
  不要停止"——不满足就再等一轮。

`poll()`（以及它的加强版 `epoll`）是 Linux 提供的"同时监视一个或多
个文件描述符，谁先准备好就告诉你"的机制，属于"带超时的等待"这一类。
`poll` 每次调用都要把关心的所有 fd 重新告诉内核一遍；`epoll` 让内核
记住一份"关心列表"，同时监视大量 fd 时效率高得多——这部分细节留给以
后专门学 muduo/epoll 的项目，这里只用了 `poll` 监视单个 fd 的最简单
形态。

例子：`Device::wait_readable()` 用 `poll(fd, 200ms)`，让
`AcquisitionWorker` 的停止请求最多等一个超时周期就能生效
（`userspace/device-service/src/device.cpp`）。

## 信号（signal）机制

**信号本质**：操作系统内核发给一个进程的"异步中断通知"——"异步"指这
个通知可能在程序执行到任何一行代码时突然发生，程序自己没法预判"什么
时候会收到"。每种信号有一个整数编号和约定俗成的含义，大致分三类：

**第一类：来自终端/用户操作**
- `SIGINT`（2）：按 `Ctrl+C`，终端发给前台进程，含义"用户想让你停下"。
- `SIGTSTP`（20）：按 `Ctrl+Z`，含义"暂停"（不是终止，可以用 `fg`
  恢复）。

**第二类：内核检测到程序自己出错**
- `SIGSEGV`（11）：访问了不该访问的内存地址（比如解引用空指针）——
  C/C++ 崩溃十有八九是这个。
- `SIGFPE`（8）：算术错误，最常见是除以 0。
- `SIGILL`（4）：CPU 执行了非法指令（通常是代码/栈已经损坏）。
- `SIGABRT`（6）：程序自己调用了 `abort()`（`assert()` 失败时标准库
  内部就是这么触发的）。

**第三类：其他进程/系统发来的请求**
- `SIGTERM`（15）：礼貌请求"请自己收拾好再退出"——`kill` 不带参数、
  `systemctl stop`、Docker 停容器默认发这个。
- `SIGHUP`（1）：字面"挂断"（以前指终端断开），很多长驻服务把它挪用
  成"收到就重新读配置文件"——信号编号是固定的，但具体行为完全由程序
  自己决定。
- `SIGUSR1`/`SIGUSR2`：内核完全不规定这两个信号该干什么，特意留给程
  序自己定义用途。
- `SIGKILL`（9）、`SIGSTOP`（19）：**特殊到没法被程序拦截/屏蔽/自定
  义处理**——内核收到直接强制执行"杀死"或"冻结"，不给进程任何反应机
  会。`kill -9` 能保证杀死任何进程正是因为发的是这个；处理不了，也
  就没有程序会尝试去"处理"它。

**处理信号的两种方式**：
- **经典方式**：注册一个"信号处理函数"，信号一来操作系统立刻打断正
  在跑的代码，强行跳去执行这个函数。但这个执行环境极度受限——不能加
  锁、不能等线程、不能碰文件。**这里"注册"用的接口
  （`signal()`/`sigaction()`）本身也是系统/库提供的，不是我们写
  的**——我们自己写的只是传给它的那个处理函数体；今天的讨论是"选系
  统提供的哪种接口"，不是"要不要自己实现"。
- **`sigwait` 方式（这份代码用的）**：反过来操作。先用
  `pthread_sigmask` 把关心的信号在**所有线程里都屏蔽掉**（告诉操作
  系统"先别用经典方式打断我"），然后专门起一个线程调用
  `sigwait()`——这个调用让线程乖乖睡着，直到目标信号真的发生才醒过
  来。**`sigwait()` 一醒过来，后面的代码就是在普通线程环境里跑
  的**，不是那个受限的信号处理环境，想加锁、想 `join()` 别的线程都
  可以放心做。

**为什么这次选 `sigwait` 而不是 `sigaction`**：经典方式的"打断"是不
可预测的——信号可能在任何一行代码执行到一半时发生，如果被打断的代码
当时正持有一把锁（比如 `RingBuffer::push()` 内部），信号处理函数又
想拿同一把锁，会直接自锁死；`join()` 线程、写文件也有类似的潜在冲
突（内部可能间接用到锁/内存分配，这些在信号处理环境里都不安全）。
`sigwait` 把"等待信号"和"打断正在执行的代码"彻底分开，被唤醒的线程
不是在打断谁，就是个状态完整的普通线程，所以没有这些冲突风险。

**信号相关接口家族**（都是系统/库提供的，是"选哪个"的设计决定，不是
自己实现）：
- `signal()` / `sigaction()`——注册经典信号处理函数，`sigaction` 更
  现代完整。
- `sigprocmask()` / `pthread_sigmask()`——查询/修改"当前（进程/某个
  线程）屏蔽了哪些信号"。
- `sigwait()` / `sigtimedwait()`——阻塞等待一个被屏蔽的信号真正发
  生，后者多一个超时参数。
- `kill()` / `raise()` / `pthread_kill()`——发送信号那一侧的接口。
- **`signalfd()`**（Linux 特有，值得单独记一下）：把信号包装成一个
  可以拿去 `poll`/`epoll` 的文件描述符——"这个信号发生了"变成"这个
  fd 变得可读了"，能直接塞进一个基于 `epoll` 的事件循环里，跟其他
  socket/文件事件用同一套逻辑处理，不需要像这里一样单独起一个
  `sigwait` 线程。像 muduo 这种基于 `epoll` 的服务器框架，处理信号大
  概率走的是这条路。这份代码没用它，是因为这个服务本身没有一个中心
  化的 `epoll` 事件循环，专门起一个线程比引入一整套事件循环架构更简
  单、更匹配这里的规模。

例子：`main.cpp` 里的 `block_shutdown_signals()` +
`signal_thread`（`userspace/device-service/src/main.cpp`）。

## CMake：用 `find_package`/`pkg_check_modules` 接入第三方库

C++ 项目要用一个别人写好的库（spdlog、nlohmann-json、GoogleTest、
libsystemd……），标准流程分两半：**先让操作系统装好这个库**（Linux
上通常是 `apt install lib某某-dev`，这个 `-dev` 包除了库文件本身，还
带一份头文件和一份"我是谁、我在哪"的元数据），**再让 CMake 找到
它**。找的方式有两种：

- **`find_package(库名 REQUIRED)`**：库自己提供了一份 CMake 专用的
  "配置文件"（通常叫 `<库名>Config.cmake`，装库的时候一起装到系统
  里），`find_package` 找到这份文件后，会自动定义好一个"目标"
  （target），比如 `spdlog::spdlog`、`nlohmann_json::nlohmann_json`、
  `GTest::gtest`——之后 `target_link_libraries(你的程序 PRIVATE
  spdlog::spdlog)` 一行就把头文件路径、库文件路径、这个库自己依赖的
  其他库全部自动配好，不用手动写任何路径。
- **`pkg_check_modules(变量名 REQUIRED 库名)`**（`find_package
  (PkgConfig REQUIRED)` 之后才能用）：给没有提供 CMake 配置文件、但
  提供了传统 `.pc`（pkg-config）文件的库用的备用方案（这次的
  `libsystemd` 就是这种情况）。找到后不会自动生成现成的 target，要
  自己把变量里存的头文件路径/库路径手动接上
  （`target_include_directories(... ${SYSTEMD_INCLUDE_DIRS})`、
  `target_link_libraries(... ${SYSTEMD_LIBRARIES})`）。

两种方式选哪个不是你能决定的，取决于这个库自己发布的时候提供了哪种
元数据——`find_package` 能找到就优先用，找不到再退回
`pkg_check_modules`。

例子：`userspace/device-service/CMakeLists.txt`（四个库，两种方式都
出现了：`nlohmann_json`/`spdlog`/`GTest` 用 `find_package`，
`libsystemd` 用 `pkg_check_modules`）。

## 第三方库的"标准接入姿势"—— 装好之后，代码这边要做的事往往就三步

不管具体是哪个库，模式都很像：**引头文件 → （可能需要）一次性初始
化 → 用它提供的接口**。三个例子对比一下：

- **spdlog（日志库）**：`#include <spdlog/spdlog.h>` → 用
  `spdlog::set_pattern()`/`spdlog::set_level()` 配置一次全局默认输
  出格式/级别 → 之后哪里都能直接调 `spdlog::info(...)`。
- **nlohmann-json（JSON 解析库）**：`#include <nlohmann/json.hpp>`
  → 不需要额外初始化 → `nlohmann::json j; f >> j;` 直接从文件流解
  析，`j.value("key", 默认值)` 取字段。
- **libsystemd 的 `sd_notify`**：`#include <systemd/sd-daemon.h>` →
  不需要初始化 → 在该汇报状态的地方调用 `sd_notify(0, "READY=1")`/
  `sd_notify(0, "WATCHDOG=1")`，没有被 systemd 启动时这个调用自动变
  成空操作（内部检测有没有 `NOTIFY_SOCKET` 环境变量），不需要自己写
  "如果不是被 systemd 启动就跳过"这种判断。

理解了"这三步"这个大模式，以后接入任何新库，第一件事就是找它的文档
里"要不要有一次性初始化"这一条，而不是每次都要重新摸索。

## Yocto/BitBake：造一个嵌入式 Linux 镜像，涉及哪些东西

这部分是 V6（Plan.md）做 Yocto 打包时聊出来的，跟"MCU 采集"这个业务
完全无关，是任何用 Yocto 造嵌入式系统的项目都要懂的地基知识。按"从
零开始造一个镜像会依次遇到什么"这个顺序讲，不逐行讲某个具体文件——
具体这个项目里每个文件怎么用这套框架，见
`docs/notes/yocto-layer-code-walkthrough.zh.md`。

### 四样东西 + 一个动作

- **BitBake**：真正干活的引擎本身（Python 写的通用调度工具）。它自
  己不懂任何 Linux/嵌入式的具体知识——不知道"怎么编内核"、不知道
  "CMake 项目怎么装"，这些全部知识都在下面的"配方"里，不在引擎本
  身。官方参考仓库 `poky` 里同时打包了 BitBake 引擎本身（`poky/
  bitbake/`）和几个基础层。
- **配方（recipe，一个 `.bb` 文件）**：一份"怎么编译安装某一个具体
  软件"的说明书——源码在哪、依赖什么、编译命令是什么、编完哪些文
  件要装进最终系统。
- **层（layer）**：存放配方的文件夹，按"谁写的、谁维护"分类——因
  为配方数量巨大，而且是完全不同的、互不隶属的人（Yocto 官方团队、
  某块具体板子的板厂、某个第三方软件库的社区、你自己）各自独立维
  护自己那部分，层就是让这几拨人可以互不干扰地各管各的，你作为整
  合的人自由选择"这次要拼哪几层"，不用 fork 别人的代码。
- **镜像配方（image recipe，也是一份特殊的 `.bb` 文件）**：内容不
  是"怎么编译"，而是一张"购物清单"——写满了最终系统里要装哪些软件
  包的名字，自己不产生任何可执行文件，只负责组装。
- **动作**：你自己决定这次要启用哪几层，把它们的路径写进
  `build/conf/bblayers.conf`（这是唯一登记"启用哪些层"的地方，一个
  编译目录只有一份）。

### 敲下 `bitbake <镜像名>` 之后，实际发生的事

1. 读 `bblayers.conf`，知道这次启用了哪几层。
2. 把这几层里**所有**配方（`recipes-*/*/*.bb`）扫一遍，建立一份
   "软件名字 → 配方文件在哪层"的索引——这一步跟具体要造哪个镜像还
   没关系，纯粹是盘点"这次手头有什么配方可用"。
3. 打开镜像配方（购物清单），读上面列的软件名字。**购物清单上只写
   名字，完全不提这个名字是哪个层提供的**——层与配方的对应关系，全
   靠第 2 步建好的索引自动查，没有任何文件需要你手写去声明这层对应
   关系。
4. 清单上每个名字，去索引里查到对应的配方，照着配方的内容真正执行：
   下载/定位源码 → 编译 → 装进一个临时的目标文件系统目录里。
5. 清单上所有软件都装完后，打包成一个可烧录的镜像文件。

### 两层"身份证"容易搞混的两个文件

- `build/conf/bblayers.conf`：**只有一份**，编译目录级别，内容是
  "启用哪几层的路径"——花名册。
- `<某层>/conf/layer.conf`：**每层各自一份**，内容是"我（这一层）
  叫什么名字、优先级多少"——层自己的身份证，只描述自己。

### 撞车了听谁的：层级别的优先级，也是"定制别人配方"的正规手段

如果两个不同层里恰好都提供了同名配方，靠**层自己在 `layer.conf`
里声明的优先级数字**（层级别的单一数字，层内所有配方共用，不是每
个软件单独定）仲裁，数字大的赢。这套机制的常见用途不只是"意外撞车
时兜底"，更常见的是**故意用它来覆盖/定制别人已经写好的配方**——想
微调一个官方层提供的软件，标准做法不是去改官方层的文件（那是别人
维护的，一更新你的改动就没了），而是在自己层里放一个同名配方（或
者更常见的用 `.bbappend` 文件，专门用来"追加/修改已有配方而不是完
全重写"），靠更高优先级让自己这份生效。

## 交叉编译（cross-compile）：为什么不能直接用普通 `gcc`

**核心问题**：编译，本质是把源码"翻译"成某一种 CPU 能直接执行的机器
指令——而不同架构的 CPU（比如这台开发机常见的 x86_64，跟树莓派 5 用
的 ARM64/aarch64）指令集完全不同，编出来的可执行文件互相不认识。普
通装在开发机上的 `gcc` 默认只会产出"开发机自己这种 CPU 能跑"的文
件，直接拿去目标设备上跑不了（"cannot execute binary file: Exec
format error" 就是这种错配的典型报错）。

**这如何区分"要不要交叉编译"**：区分点不是"C/C++ vs 脚本语言"这么
简单，而是"这一步有没有把源码转换成机器指令"：
- **C/C++（以及 Go、Rust 这类）**：必须编译，编出来的东西天生绑定了
  某一种 CPU 架构，所以给不同架构的目标机跑，就得让编译器产出那种
  架构的机器码——这一步叫"交叉编译"。
- **Python/Shell 这类脚本语言**：我们自己写的脚本文件本身从来没有被
  转换成机器码，靠目标机器上已经装好的解释器（`python3`/`bash`）临
  场读一行、翻译一行、执行一行。脚本文件本身不挑架构，可以原封不动
  地传过去直接跑——这也是早期版本能把 Python 测试脚本直接传到树莓
  派、这次 C 代码必须先转换一遍才能传过去的根本原因。（解释器本身
  当然也是编译出来的、也要匹配目标架构，但那是目标系统本身自带的，
  不用我们操心。）

**固定套路（这次调试实际用到的最小版本）**：
```bash
# 1. 找到 Yocto 已经准备好的交叉编译器——文件名前缀就是目标架构，
#    这是约定俗成的命名规则，任何交叉工具链都这么起名
#    （<架构>-<厂商>-<系统>-gcc）
CROSSGXX=.../recipe-sysroot-native/usr/bin/aarch64-poky-linux/aarch64-poky-linux-g++

# 2. --sysroot 指向目标系统的头文件/库所在目录——不指定的话，编译器
#    会去找开发机自己的系统头文件/库，那些是给 x86_64 用的，跟目标
#    系统的库版本、ABI 都对不上
$CROSSGXX --sysroot=.../recipe-sysroot -O2 -o 输出文件 源码.cpp

# 3. 编出来的文件传到目标机（这就是下面 SCP 那节要讲的），再登录目
#    标机执行
```
这套"交叉工具链前缀 + `--sysroot`"是所有交叉编译场景通用的固定模
式，不是这个项目专属；Yocto 的 `bitbake` 在幕后跑每个 recipe 的
`do_compile` 时，其实也是自动拼好这一整套参数再调用同一个编译器，
只是平时不需要自己手动拼。

例子：本次会话里为了单独验证 `struct Sample` 的实际大小、以及编译
`experiments/scheduler-baseline/cyclic.c` 给真机跑，都是绕开完整
`bitbake` 流程、直接调用这个交叉工具链做的一次性验证。

## SCP：怎么把编译好的东西送到目标机器

`scp`（Secure Copy）是"通过 SSH 加密通道在两台机器之间拷贝文件"的
标准命令，语法是 `scp 来源 目标`，两边都可以是"用户名@主机:路径"这
种远程写法：

```bash
scp -i 密钥文件 本地文件路径 root@树莓派IP:/tmp/目标文件名
```

本质上就是"先建立一条 SSH 连接，再在这条连接上传文件"，跟直接
`ssh` 登录用的是同一套认证方式（这里用的是密钥登录，不是密码）。这
次会话里，每次在开发机上交叉编译出一个新版本，都要靠这一步先搬到
真机上，再用另一条 `ssh` 命令登录进去执行/替换/重启服务——"编译"
和"部署"是两个独立的步骤，中间靠 `scp` 衔接。

## 实时调度四件套：SCHED_FIFO / CPU 亲和性 / IRQ 亲和性 / mlockall

这四个是 Linux 上"让某个任务的执行更可预测、少被别的东西打扰"最常
用的四把杠杆，V7 调度对比实验里用到的就是它们。**它们解决的是四个
不同层面的问题，不能互相替代**，这也是这次实测里"加了 A 有用、加了
B 几乎没用"的根本原因——用错了杠杆，自然看不到效果。

**SCHED_FIFO：管"轮到谁跑"（调度优先级）**
Linux 默认的调度策略是 `SCHED_OTHER`（也叫 CFS，完全公平调度器）——
所有普通进程按"公平"原则轮流分时间片跑，谁也不能长期霸占 CPU。
`SCHED_FIFO` 是一种"实时"调度策略：设置了这个策略的线程，只要它
**想**跑、且没有更高优先级的实时线程在跑，调度器就必须立刻把 CPU
给它，其他普通线程完全让路，不管等了多久。这就是为什么这次实验里
"负载 + SCHED_FIFO"能把延迟压到比完全空载还低——原本要跟四个
`yes` 进程抢时间片，现在四个 `yes` 进程在调度器眼里"不够资格"抢，
直接靠边站。

**代价，以及这个代价具体有多大，取决于核心数**：如果实时线程卡死不
让路，它会霸占**它当前所在的那一个核**，但一个线程任意时刻只能占用
一个核——如果机器有 N 个核、同时卡死的实时线程数少于 N，理论上其他
核仍然空着，能正常调度 `sshd` 这类普通服务，系统整体不会真的失联。
另外 Linux 自己也有一层安全网叫 **RT throttling**（`sched_rt_
runtime_us`）：默认规定每个核每 1 秒里至少留 5% 的时间必须让给非实
时任务，就是专门防这种"实时线程写崩了拖垮整机"的场景。所以"核心数
足够多、卡死线程数量可控"确实能显著降低"整机失联"的风险，不是危言
耸听式的"绝对不能长期用"。

真正无法单纯靠"数核心数"兜底的，是**这个线程卡死时手里正抓着的东
西**——比如线程下半部处理中断的代码默认也跑在实时优先级上（Linux
给 threaded IRQ 的默认优先级通常是 50），如果它卡死时正持有一把内
核锁（这个项目里的 `fifo_lock`/`spi_lock`），那问题就不再是"占了几
个核"，而是**任何想拿同一把锁的代码都会被一起拖住**，这类风险不会
因为核心数多就自动消失。所以能不能放心长期用 SCHED_FIFO，最终还是
要落到"能不能证明这段代码在所有情况下都会正常让路、不会卡在临界区
里"这件事上，核心数多只是"万一真出问题，波及范围更小"的缓冲垫，不
是替代这个证明的理由。

**CPU 亲和性（affinity）：管"在哪个核上跑"**
Linux 默认允许调度器把一个线程在多个 CPU 核之间自由搬动（哪个核闲
着就搬去哪个），这样吞吐总体更高，但每次"搬家"都有隐藏成本：这个
线程之前用的那个核的高速缓存（cache）里存的数据全部作废，搬到新核
上要重新从内存里加载，速度明显变慢。**设置 CPU 亲和性**就是告诉调
度器"这个线程/进程只能在我指定的这个核上跑，不许搬家"，换来的是没
有迁移开销，但代价是如果就这一个核恰好很忙（比如负载生成器也在抢
这个核），这个线程还是得乖乖排队——**它只解决"迁移抖动"，不解决
"优先级"问题**，这正是这次实测里"CPU 亲和性有帮助但不如 SCHED_FIFO
彻底"的原因。

**IRQ 亲和性：管"中断由哪个核负责响应"**
每个硬件中断（比如这个项目的 DATA_READY 中断）默认也可以由任意一
个 CPU 核去响应，"IRQ 亲和性"就是把某个中断固定到某一个核上处理
（这次是通过 `/proc/irq/<中断号>/smp_affinity_list` 设置的）。**注
意这管的是"谁去执行中断处理函数"，不是"谁去执行真正消费数据的用户
态线程"**——这两者是完全不同的代码、不同的执行时机。如果瓶颈根本
不在"中断响应得够不够快"，而在中断处理完之后、用户态线程排队等着
被调度这一段，那单独调 IRQ 亲和性自然见效有限——这正是这次实测里
IRQ 亲和性效果不如 CPU 亲和性、"IRQ 和 CPU 分开绑不同核"反而是全场
最差结果（跨核唤醒的额外开销盖过了隔离的好处）背后的道理。

**mlockall：管"内存会不会被换出/延迟分配"**
Linux 默认允许把一个进程暂时不用的内存页"换出"到磁盘（swap），或
者对刚申请但还没真正写过的内存"延迟真正分配物理页"（第一次真正写
入那一刻才触发，叫缺页中断，page fault）——这两种机制都可能在关键
时刻突然插入一次不可预测的延迟（要访问磁盘，或者要临时问操作系统
要一页真实内存）。`mlockall(MCL_CURRENT | MCL_FUTURE)` 的作用是告
诉内核"把我这个进程现在用的、以后会用的所有内存页，全部实实在在锁
在物理内存里，不许换出、不许延迟分配"，换来的是内存访问不会再有这
类不可预测的中断。**它只解决"内存访问延迟"这一类问题**——如果一个
程序压根没有频繁申请内存、也没有被换出的风险（这个项目的
`RingBuffer` 容量在启动时就一次性定死，运行中不再动态分配），
`mlockall` 就没有东西可修，这正是这次实测里它几乎不起作用的原因。
**这也是这四把杠杆里唯一一个"看数据表现就能判断该不该用"的**：先
看瓶颈是不是真的在内存分配/换页上，不是的话加了也白加。

**怎么选**：先搞清楚"延迟到底卡在哪一步"再对症下药，而不是四个全
加上去碰运气——这次实测把四个都测了一遍，正好验证了"针对性调优 >
无脑全加"这个道理：`SCHED_FIFO` 单独一项几乎解决了全部问题，因为
真正的瓶颈是"调度优先级"，其余三个只是从不同侧面缓解症状，没有真
正对上根因。

例子：`userspace/device-service/src/main.cpp` 里 `sched_setscheduler`
/`sched_setaffinity`/`mlockall` 三处调用，`/proc/irq/<n>/
smp_affinity_list` 的手动 `echo` 操作；完整实测数据见
`docs/performance.md`。

## 实时 Linux 调优：内核那一层的杠杆

上一节的四件套（`SCHED_FIFO` / CPU 亲和性 / IRQ 亲和性 / `mlockall`）全部是
**进程自己能做的事**。这一节是下面一层：**内核命令行和内核配置**。区别很实
际——四件套改一行代码重启进程就生效；这一节的东西大多要**改内核命令行并重
启**，有的甚至要**重新编译内核**。

这一节的内容是在 Pi 5 上做 `PREEMPT_RT` 对比实验时踩出来的
（`docs/devbus-experiments.md`、`docs/debugging/case-08`、`case-09`），但概念
本身跟本项目无关，任何做低延迟 Linux 的场合都一样。

### 核心思路：把一部分核"腾干净"

多核系统上降低尾延迟，最有效的一招不是让你的线程跑得更快，而是**让别的东
西别来打扰它**。一个核上可能打扰你的东西有四类，正好对应四个内核命令行参
数：

| 参数 | 赶走的是 | 不加会怎样 |
| --- | --- | --- |
| `isolcpus=2,3` | 普通调度器**不会**把其他任务派到这些核上 | 随便哪个后台进程都可能被调度过来 |
| `nohz_full=2,3` | 核上只有一个可运行任务时，**关掉周期性时钟中断** | 每秒 100/250/1000 次定时器中断，每次几微秒 |
| `rcu_nocbs=2,3` | RCU 的回调处理**挪到别的核**上做 | RCU 软中断/内核线程会周期性抢占你 |
| `irqaffinity=0,1` | 所有设备中断**只送到 0/1 核** | 网卡、磁盘、USB 的中断随时打断你 |

典型组合就是这四个一起用，且**互相补充、缺一不可**：只 `isolcpus` 不
`irqaffinity`，中断照样往隔离核上送；只 `nohz_full` 不 `isolcpus`，核上有
第二个可运行任务时 tickless 自动失效。

实测的效果量级（Pi 5，`devbus` 单向延迟，满载）：未调优最坏 **~10 ms** →
隔离 + `SCHED_FIFO` + `mlock` 之后 **~0.1 ms**，一百倍，而且**不需要换内
核**。这个数字值得记住，因为它意味着：

> **在换 PREEMPT_RT 之前，先把隔离做对。** 隔离带来的改善往往比换抢占模型
> 更大，而且代价小得多。

### 坑一：内核命令行参数是"请求"，不是"确认"

**这是最贵的一个教训**（`case-09`）。`nohz_full=2,3` 这种参数，如果内核编
译时没开对应的 `CONFIG_NO_HZ_FULL`，内核**只在开机时记一行日志，然后就把它
忽略掉**：

```
[    0.000000] Unknown kernel command line parameters "nohz_full=2,3 rcu_nocbs=2,3", will be passed to user space.
```

注意这行的位置和措辞有多容易漏掉：时间戳是 `0.000000`，在几百行启动日志的
最前面；级别是普通信息不是警告；而且它说的是"会传给用户态"，听起来像是被
妥善处理了，不像是"你要的功能没有"。启动不受影响，服务照常起来，你以为调
优生效了，实际上什么都没发生。**2026-09-20 在树莓派官方 6.18 内核上又原样
复现了一次**，连日志文字都一模一样。

所以规矩是：**永远回读，不要相信自己写进去的命令行。**

```sh
cat /sys/devices/system/cpu/isolated      # isolcpus 的实际结果
cat /sys/devices/system/cpu/nohz_full     # 不存在这个文件 = 根本没编进去
cat /proc/cmdline                         # 你请求了什么
dmesg | grep -i "unknown kernel command line"
```

`case-09` 里的症状是：`PREEMPT_RT` 上忙等线程把 `rcuc/3` 这个内核线程饿死，
造成 **130 ms** 的停顿。查到最后是 `bcm2712_defconfig` 没开
`NO_HZ_FULL`/`RCU_NOCB`，两个参数全被吞了。重新配置编译之后同一个测试：
**130 ms → 1.4 µs**。

推广一下：**凡是"配置了但没有回读确认"的地方，都要假设它没生效。** 这个模
式在这个项目里反复出现（sysfs 的换行符 bug、IRQ 亲和性、丢包率算法），做法
都一样：**找一个独立的信号交叉验证**。

### 坑二：RT throttling——`SCHED_FIFO` 不是无限制的

**默认情况下，实时任务每 1 秒最多只能占用 0.95 秒的 CPU。**

```sh
/proc/sys/kernel/sched_rt_period_us   # 1000000（1 秒）
/proc/sys/kernel/sched_rt_runtime_us  #  950000（0.95 秒）
```

这是内核的自保机制：一个 `SCHED_FIFO` 的死循环会把整个系统卡死（它优先级
比所有普通任务高，永远不让出 CPU），连 shell 都进不去。throttling 保证每秒
留 50 ms 给普通任务喘气。

代价是：一个**忙等**的实时线程会被周期性地强制停 **50 ms**。
`case-08` 里的现象就是 p99 延迟直接到 **39 ms**——不是调度抖动，是内核主动
按住的。

三种处理方式：
1. **别忙等**（用 futex 睡眠），实时线程只在有活干的时候才跑，根本到不了
   95% 的占用率。这是首选。
2. 把 `sched_rt_runtime_us` 设成 `-1` 关掉 throttling。**要非常小心**：从此
   一个死循环就能锁死机器，必须有别的手段兜底（看门狗、隔离核）。
3. 用 `SCHED_DEADLINE` 代替 `SCHED_FIFO`，显式声明"每 N 微秒我需要 M 微秒"，
   由内核做准入控制。最正规，但要求你真的知道自己的执行时间上界。

**内核 6.12 起这件事变了**：主线合并了 *deadline server for fair tasks*
——内核不再靠粗暴的 throttling 保证普通任务有 CPU，而是给 fair 调度类挂一个
deadline 服务器来保证它的带宽。效果是实时任务不再被那种每秒一次的大停顿
砍，同时普通任务仍然饿不死。所以**在老内核上观察到的 RT throttling 停顿，
在 6.12+ 上可能已经不复现了**——这是一个"结论有版本有效期"的典型例子，记
笔记时要连内核版本一起记。

### 坑三：C-state（CPU 省电休眠）

CPU 空闲时会进入越来越深的休眠状态（C1、C2、C6……），越深越省电，**唤醒也
越慢**（可能几十到几百微秒）。对吞吐无所谓，对延迟是致命的：你的数据到了，
CPU 正在深睡，第一件事是花 100 µs 醒过来。

```c
int fd = open("/dev/cpu_dma_latency", O_WRONLY);
int32_t target_us = 0;
write(fd, &target_us, sizeof(target_us));
// 关键：fd 必须一直开着。关掉的瞬间约束就失效了。
```

这是内核的 **PM QoS** 接口：写进去的数字是"我能容忍的最大唤醒延迟（微
秒）"，写 0 就是"完全不许深睡"。**最反直觉的一点是它靠 fd 的生命周期生
效**——进程退出、fd 关闭，约束自动撤销。这个设计其实很聪明（崩溃了不会把机
器永久锁在高功耗状态），但会让人写出"写完就 close，然后纳闷为什么没用"的
代码。

配套还有调频策略（governor）：

```sh
# 注意路径是 policy0 不是 cpuN —— Pi 5 上四个核共用一个 policy，
# 写 cpuN/cpufreq/... 会直接返回 EIO
echo performance > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
```

`ondemand`/`schedutil` 会在负载上来时才升频，那个升频过程本身就是延迟。测
延迟一律先钉死 `performance`，否则测的是调频器的反应速度。

### 坑四：`SCHED_FIFO` 的优先级要跟内核线程比

这是最容易忽略的一点：**你的实时线程不是跟其他用户进程竞争，是跟内核线程
竞争。** 尤其在 `PREEMPT_RT` 上，大量原本不可抢占的内核工作被做成了普通的
内核线程，它们也有 `SCHED_FIFO` 优先级：

```sh
ps -eo pid,cls,rtprio,comm | grep -E 'FF|RR'
```

会看到这些：

| 内核线程 | 干什么 | 典型优先级 |
| --- | --- | --- |
| `irq/<n>-<dev>` | 线程化的中断处理（RT 上几乎所有中断都是） | 50 |
| `ktimers/<cpu>` | 线程化的软定时器 | 1 左右 |
| `rcuc/<cpu>`、`rcub/<n>` | RCU 的宽限期处理 | 低 |
| `ksoftirqd/<cpu>` | 软中断 | 低 |

**踩到的具体后果**（`case-09`）：把忙等线程设成 FIFO 80 跑在核 3 上，
`rcuc/3` 优先级比它低、又必须在核 3 上跑，于是永远得不到 CPU。RCU 宽限期推
不动，最后内核出手 → **130 ms 停顿**。

所以选优先级的规则是：

- **比你依赖的内核线程高，比你不依赖的高，但别比你必须让它跑的那些高。**
  最典型的就是：你的线程优先级不该高过负责你自己设备中断的那个 `irq/` 线程
  ——你压住了它，数据就送不到你手上。常见配置是 `irq/` 用 50，自己的处理线
  程用 40-49。
- **如果一定要忙等，就必须把那些内核线程从这个核上挪走**（`rcu_nocbs` 把
  RCU 回调挪到别的核，`irqaffinity` 把中断挪走），否则就是在跟它们抢一个核。
  **`rcu_nocbs` 和忙等是配套的，不是可选项。**
- 一个实用的自检：调优之后跑 `ps -eo cls,rtprio,comm` 看一遍自己在这张表里
  的位置，而不是只看自己那一行。

### 怎么系统地做这件事

顺序（每一步都比下一步便宜，且效果常常更大）：

1. **先测出瓶颈在哪**——是调度抖动、是内存、是中断、还是根本就是 I/O 本身
   慢。`case-07` 的教训：花力气比较 RT 和非 RT，结果瓶颈在 SPI 事务的固有开
   销上，两边当然一样。
2. **调频钉死 `performance`，关 C-state**，否则后面测什么都是噪音。
3. **进程层四件套**（`SCHED_FIFO` + 亲和性 + `mlockall`），改代码即可。
4. **内核命令行隔离**（`isolcpus`/`nohz_full`/`rcu_nocbs`/`irqaffinity`），
   **一定回读确认生效**。
5. **最后才考虑换 `PREEMPT_RT` 内核**。它对**没法逐个调优的代码**收益巨大
   （实测未调优进程 p99.9 改善约 100 倍），但对已经隔离 + 提优先级的关键路
   径几乎没有增量收益，而且**中位延迟会变差**（实测 6.1 µs vs 3.9 µs——线程
   化中断和可睡眠自旋锁买来的是有界最坏情况，代价是平均变慢）。

例子：`experiments/rt-kernel/`（自建内核 + tryboot 安全部署）、
`userspace/devbus/bench/run_rt_matrix.sh`（矩阵实验脚本）、
`docs/devbus-experiments.md`（数据），`docs/debugging/case-08`、`case-09`
（两个坑的完整追查过程）。

### 坑五：慢速串口控制台本身就是一个延迟源

**2026-09-20 查清的一件事，值得单独记**：内核往串口控制台打印，是**同步**
的——`printk` 会把当前这个核卡在那儿，直到字符全部从 UART 发出去。

算一下就知道有多慢：115200 波特率，一行 80 字符 = 80 × 10 bit ÷ 115200 =
**6.9 ms 一行**。一条 20 行的内核报告（RCU stall、`WARN_ON` 调用栈、驱动
probe 失败）就是 **~140 ms**，而且是砸在**打印它的那个核**上。

实测对照（同一段 RCU stall 报告，内容完全一样）：

| 板子 | 控制台 | 每行 | 整段 20 行 |
| --- | --- | --- | --- |
| Yocto 卡 | 走 115200 串口 | 6.51 ms | **123.7 ms** |
| Raspberry Pi OS 卡 | 不走慢速 UART | 0.003 ms | 0.045 ms |

**后果**：一个内核层面的异常，在延迟百分位里会表现成"应用程序偶尔卡一下
130 ms"，而且**很容易被归因到应用自己头上**。case-09 最初就是这么归因的，
后来才发现那 130 ms 是控制台，不是 RCU。

两条实用规则：

1. **量延迟之前，先确认内核消息打到哪儿去了。** `cat /proc/consoles`，
   看有没有一个慢速串口在列。要么临时提高 `loglevel` 门槛，要么把串口
   控制台从命令行里拿掉，**但要记得这会让你看不到崩溃现场**——这是个真
   权衡，不是纯优化。
2. **延迟直方图干净不等于内核干净。** 反过来也成立：Pi OS 那张卡上 RCU
   机制饿死了三分钟，应用层指标一点异常都没有。**`dmesg` 要当成测量的一
   部分去读，不是只在数字看起来不对的时候才去翻。**
