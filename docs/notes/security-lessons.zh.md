## 学习方法

- **从项目出发，不从书本出发**：每个概念都落到项目里的一个具体文件、一条实测输出上。
- **不学数学**：每个密码学工具只问三个问题——**它保证什么？不保证什么？需要什么秘密？**
  工程上的问题几乎都出在"密钥放哪"和"误以为它保证了它不保证的东西"。
- 想系统补的时候：Bootlin 的 Embedded Linux security 培训资料（免费，最贴近）；
  *Serious Cryptography*（Aumasson，第 2 版）；*Security Engineering*（Ross Anderson，第 3 版，挑章节看）；
  欧盟 CRA（网络韧性法案，德国公司大概率会问）。

## 1. 威胁模型是干什么的 📖

`docs/security/threat-model.md`（中文版 `security-zh/threat-model.zh.md`）是整个安全专项的起点，
相当于**体检报告 + 治疗方案 + 复查结果**：

- **分析**：谁会来攻击（A1 网络 / A2 技师 / A3 二手买家 / A4 供应链）、他们想要什么（资产）、从哪下手（信任边界）
- **结论**：14 条漏洞 F1–F14，排好修复顺序
- **路线图**：后面每篇文档都是在修其中几条，开头会写"本文修复 F4"
- **验收**：§8 回头再审一遍，哪条修好了、哪条没有、为什么

关键场景：设备装在客户现场、由第三方技师维护、最后会被转卖——**物理接触是日常，不是极端攻击**。
所以"A1 决定优先级（能规模化），A2/A3 决定设计（一定会出现）"。

### 1.1 第 1 课正式讲：威胁模型的四个问题 ✅（Q70、Q71，2026-09-26）

用户在第 0 课之后自己总结出的直觉："没有绝对的安全，要看防的是谁；某个攻击者不值得防，那一块弱一点也没关系"——
**基本就是威胁模型的核心**。正式说法是四个问题，`threat-model.md` §2–§5 就是按这个顺序写的：

| 问题 | 文档里 | 我们的答案（举例） |
| --- | --- | --- |
| 1. 保护什么？ | §2 资产 | 采集数据、固件、设备身份、签名密钥、WiFi 密码…… 每样标上要的是完整性还是机密性 |
| 2. 防谁？ | §3 攻击者 | A1 网络、A2 技师、A3 二手买家、A4 供应链，每个写清楚**能碰到什么、想要什么** |
| 3. 从哪进来？ | §4 信任边界 | 网络↔设备、SD 卡↔启动链、Linux↔MCU…… 数据跨过边界的地方就是要检查的地方 |
| 4. 现在哪里不行、先修哪个？ | §5–§6 发现 F1–F14 + 修复顺序 | |

**第 0 课里的"转移"和威胁模型的关系**：每个工具都是把问题从一处挪到另一处（哈希 → "标准答案放哪"；HMAC → "密钥放哪"；
签名 → "私钥放哪"；LUKS → "口令从哪来"）。挪完之后的那个地方够不够好，**只能对着具体的攻击者判断**——这就是威胁模型的用处。

**用户的例子，要修正的一点**：在我们的场景里，二手买家 A3 **恰恰是要防的**（F7 WiFi 密码、F8 数据 → LUKS）。
因为场景是"装在客户现场、第三方技师维护、最后被转卖"，所以**物理接触是日常，不是极端情况**（§1）。

但"某个攻击者拿到某样东西也无所谓"这个思路完全对，项目里真实的例子：

| 弱点 | 谁能利用 | 为什么接受 |
| --- | --- | --- |
| MCU 用 RDP level 1，读过论文的人能抠出 K（CVE-2020-8004） | A3 有无限时间，做得到 | 一机一密：抠出来只能冒充这一块已经退役的 MCU，**拿到了也没价值** |
| F13 devbus 订阅者能改彼此的共享内存 | A1，但要先攻破一个订阅者 | 前提条件高、影响有限（Low）；修它要改 devbus 设计，成本高 |
| LUKS 防不住攻破内核的人（11.2e） | 需要先在设备上拿到内核权限 | 磁盘加密本来只负责"静止的数据"，运行时靠其他层（只读根、沙箱、最小权限） |

判断"不防"要同时看三件事：**他做不做得到 × 做到了能得到什么 × 修它要花多少**。
而且"不防"必须是**写下来的决定**（叫 accepted risk，接受的风险），不是忘了——威胁模型 §7 专门列了"这块硬件修不了的"。

**严重度和修复顺序**：
- 严重度 = 容易程度 × 得到什么。Critical = 不用凭据远程就能打；High = 光靠物理接触就能完全拿下某样资产。
- **修复顺序 ≠ 严重度排序**，还要看依赖和成本：F1（空密码 root 远程登录）排第一，技术含量最低但最便宜、不修其他都白搭；
  F4 secure boot 是 dm-verity 的锚，却排在后面，因为最后一步烧 OTP 不可逆。
- A1 决定**优先级**（能规模化，一次打一千台）；A2/A3 决定**设计**（这个场景里他们一定会出现）。

## 2. SD 卡上的东西是怎么组织的 ✅（Q48）

### 2.1 最底层：一长串字节

SD 卡就是一长串格子，每格一个字节，从 0 开始编号。512 字节为一个**扇区**。
我们的镜像 1.63 GB = 3,416,064 个扇区。

**烧录/刷写** = 把镜像文件（"SD 卡应该长什么样"的逐字节复制品）从第 0 个字节开始原样抄到卡上。
`dd` 和 Raspberry Pi Imager 做的都是这件事，它不关心内容。

### 2.2 分区

卡的开头有一张**分区表**，记录每一段从哪开始、多长。1.2.2 镜像的真实分区表（`sfdisk -l`）：

```
分区  起始扇区   大小     文件系统   用途
p1      8192     8 MB    FAT      autoboot.txt：这次从 A 还是 B 启动
p2     24576   166 MB    FAT      启动分区 A：boot.img + boot.sig
p3    368640   166 MB    FAT      启动分区 B
p4    (容器)                       MBR 最多 4 个主分区，p5–p7 装在这个扩展分区里
p5    712704   144 MB    ext4     根文件系统 A（挂成 /，真正的 Linux 系统）
p6   1015808   144 MB    ext4     根文件系统 B
p7   1318912     1 GB    LUKS     数据分区（加密），开机后挂在 /data
```

按功能是 4 类：选槽（p1）、启动（p2/p3）、系统（p5/p6）、数据（p7）。
启动和系统各有 A/B 两份：更新时只写没在用的那一套，写坏了不影响正在用的。

### 2.3 文件系统 ✅（Q55）

分区内部"怎么放文件"的规则。用哪种取决于**谁来读它**：

- **FAT**：非常简单，固件（很小的程序）只懂这个。U 盘、PC 的 UEFI 启动分区也用它。→ p1、p2、p3
- **ext4**：功能全（权限、符号链接、日志），给 Linux 用。→ p5、p6

### 2.4 boot.img 是"盒子里的盒子" ✅（Q50）

```
p2 分区（FAT）
 ├─ config.txt       （只有一行 boot_ramdisk=1）
 ├─ boot.sig         签名
 └─ boot.img         一个文件，但它里面又是一个完整的 FAT 文件系统：
      ├─ kernel_2712.img   Linux 内核（55 MB，里面嵌着 initramfs，initramfs 里有 dm-verity 根哈希）
      ├─ *.dtb、overlays/  设备树（V3 学过的"硬件说明书"）
      ├─ config.txt        给固件看的配置（加载哪些 overlay、A/B 各用哪个 cmdline）
      └─ cmdline-a.txt     给内核看的参数：root=/dev/mmcblk0p5 rauc.slot=A ...
```

**为什么套一层**：为了对"启动需要的所有东西"只签一个名。任何一个字节变了签名就对不上。
如果内核签名了、旁边的 cmdline 没签，攻击者加一句 `init=/bin/sh` 就能开机直接拿 root shell。

这是 Raspberry Pi 官方的 secure boot 设计，不是我们发明的。

**boot.img 怎么来的**（签名主机上，`security/signing/make-signed-ab-release.sh`）：
bitbake 构建镜像 → 把启动文件放进一个目录 → `mkfs.vfat -C` + `mcopy` 打包成 FAT 镜像文件 = boot.img →
`rpi-eeprom-digest -H pkcs11-hsm-wrapper` 用 HSM 里的私钥签名得到 boot.sig（私钥不离开 HSM）→
`dd` 写进整盘镜像的 p2 和 p3。第一次整盘刷进 SD 卡；以后通过 RAUC 更新包写进空闲槽。

### 2.5 内核、程序、驱动 ✅（Q51）

- **内核** = Linux 内核，整个系统最核心的程序：管理 CPU、内存、进程、硬件。它在 boot.img 里。
- **普通程序**（`ls`、`sshd`、`device-service`……）跑在内核之上，文件在 p5。
- **驱动**比较特殊：它是**内核的一部分**，运行在内核里。有两种放法——
  - 直接编进内核镜像（在 boot.img 里），比如 6.12 里的 RP1 驱动
  - 编成**内核模块**（`.ko` 文件），文件放在 p5 的 `/lib/modules/` 下，开机时**加载进内核**运行。
    我们的 `custom_acq.ko` 就是这种。
  所以驱动的**文件**可能在 p5，但它**运行时**是内核的一部分，不是普通程序。
  这也是为什么内核加固要开 `MODULE_SIG_FORCE`：p5 上的模块文件必须带签名，内核才肯加载。

## 3. 开机顺序和信任链 ✅（Q52、Q53；3.5 除外）

### 3.1 SD 卡之前还有两段代码，都在板子上

```
【BCM2712 主芯片内部】
  BootROM   —— 芯片制造时刻进电路的代码（mask ROM），物理上不存在"写"这个操作
  OTP       —— 一次性可编程熔丝，写入 = 烧断熔丝，只能 0→1，不能改回
【板子上一颗单独的小芯片：SPI EEPROM】
  bootloader 固件（bootsys + bootmain）—— 树莓派公司出厂写入，可以重刷
                                         （rpi-eeprom-update，或 USB 接电脑用 rpiboot）
【SD 卡】 p1 … p7
```

（Pi 4/5 才有 EEPROM；老的 Pi 3 bootloader 也在 SD 卡上。）

### 3.2 上电后的接力

```
1. BootROM        → 读 EEPROM 里的 bootloader，【检查它的签名】，交给它
                    （BootROM 从不读 SD 卡）
2. bootloader     → 读 SD 卡 p1 的 autoboot.txt：从 p2 启动
                  → 读 p2 的 boot.img + boot.sig，【验证签名】（OTP 烧了才强制）
                  → 打开 boot.img，取出内核，交给它
3. 内核           → 按 cmdline 找到 p5，用根哈希设置 dm-verity，把 p5 挂成 /
4. Linux 系统     → 解密 p7 挂成 /data，启动 device-service……
```

规则只有一条：**交棒之前，先检查下一棒有没有被动过；检查不过就不交。**
每一环的可信都来自上一环 = **信任链**。

### 3.3 信任根：为什么到 BootROM 就可以停

EEPROM 能重刷，所以要 BootROM 去检查它。那 BootROM 谁来检查？——不需要：它物理上改不了。
OTP 也改不了，所以把"我们的公钥的哈希"烧进 OTP，BootROM 就知道该信哪把钥匙。
**一个物理上改不了的起点 = 信任根（root of trust）。** 没有它，"检查者由谁来检查"就没有尽头。

代价：BootROM 有 bug 也修不了。例子：任天堂 Switch 的 Tegra X1 BootROM 漏洞（2018，CVE-2018-6242），
能在验签之前执行任意代码，卖出去的机器永远修不好，只能出新芯片。

### 3.4 我们这块板子的真实状态

**OTP 没烧。** 所以 BootROM 不知道我们的公钥，bootloader 不强制检查 boot.img 签名；
拿到板子的人重刷 EEPROM 或换 boot.img 都会被放行。

我们做完了**从 boot.img 往后的所有环节**（签名 boot.img、dm-verity、签名更新），也在主机上生成并验证了
反签的 EEPROM 镜像，**只差最前面那一下"把公钥哈希烧进 OTP"**——不可逆，烧了这块板子就只能跑我们签过名的东西，
而我们还要在上面跑自己编的实验内核。
这就是威胁模型的主线结论：**软件这边每一层都做了，唯独信任根是模拟的。**

### 3.5 不同硬件的 secure boot 📖

思想一样（ROM 起步、一环验一环、公钥哈希烧在熔丝/OTP），具体做法每家不同：

| 平台 | 流程 | 特点 |
| --- | --- | --- |
| 树莓派 5 | ROM → EEPROM bootloader → 一个签名的 boot.img → 内核 | 最简单：一把密钥、一个签名文件 |
| 大多数 ARM64 芯片（NXP i.MX8、TI、瑞芯微，用 TF-A） | ROM(BL1) → BL2 → BL31 + BL32(OP-TEE) + BL33(U-Boot) → 内核 | 多级 X.509 证书，有防回滚计数器 |
| U-Boot 验证启动 | U-Boot 验证 FIT 镜像（内核+设备树+initramfs 打成一个包） | 要签"组合"，否则能把合法内核和另一个合法设备树混搭 |
| Xilinx Zynq | ROM 验证并**解密** FSBL | 密钥放 eFUSE（永久）或电池 RAM（可故意销毁） |

U-Boot FIT 和 Pi 5 的 boot.img 是同一个思路：打成一个包再签，防止只换掉某个没签名的零件。
面试讲法：我在 Pi 5 上做通了整条链，原理和 TF-A/U-Boot 一样，能说清两者对应在哪、差在哪。

## 4. 两类最基本的安全属性 ✅（Q49）

| 想防的 | 叫 | 用什么 |
| --- | --- | --- |
| 被**改**（改了要能发现） | **完整性** | 哈希、HMAC、签名、dm-verity |
| 被**看** | **机密性** | 加密 |
| 冒充（确认是谁发的） | 真实性 | HMAC、签名 |
| 搞瘫 | 可用性 | 冗余、A/B 回退 |

**加密只防看，不防改**；两件事互相独立。对照分区：

| 分区 | 有秘密吗 | 怕被改吗 | 保护手段 | 内容是明文吗 |
| --- | --- | --- | --- | --- |
| p2/p3 boot.img | 没有 | 怕（改 cmdline 拿 root） | 签名 | 是，谁都能读 |
| p5/p6 系统 | 没有（每台设备都一样） | 怕（植入后门） | dm-verity | 是，谁都能读 |
| p7 数据 | **有**（采集数据、WiFi 密码、SSH 主机密钥、MCU 配对密钥） | 也怕 | LUKS 加密 + dm-integrity | 否 |

所以 p2 和 p5 根本没加密——它们不是秘密，只要保证没被改过。只有 p7 加密。
p7 除了加密还要加完整性（dm-integrity）：改动密文，解密出来是乱码，文件系统照读不误，光加密发现不了。

### p1 为什么可以不保护 ✅（Q54）

`autoboot.txt` 是个没签名的普通文本文件，谁都能改。之所以还算安全，是因为它只能在 p2 和 p3 之间选，
而**两边都只放签名过的 boot.img**——攻击者最多在两个合法系统之间切换，塞不进自己的东西。
设计思路：**与其保护每一样东西，不如让没保护的东西只能在安全的选项里选。**
（遗留问题：如果另一个槽里是一个**旧版本**的合法系统呢？→ 防回滚那一课。）

## 5. 工具 1：哈希（SHA-256）

### 5.1 哈希是什么 📖

把任意长度的数据变成固定 32 字节的"指纹"。自己试：

```bash
echo -n "hello" | sha256sum
echo -n "hellp" | sha256sum     # 改一个字母，结果面目全非（雪崩效应）
```

保证：同样的输入永远同样的输出；改一个比特输出全变；单向（反推不出原数据）；
抗碰撞（几乎不可能找到两份不同数据有同样的指纹）。
**不需要任何秘密，谁都能算。**

### 5.2 为什么没有 secure boot 的 dm-verity 发现不了攻击者 ✅（Q47）

攻击者不走"让不同数据算出相同哈希"（碰撞，做不到）这条路，而是**改掉数据，重新算出新的根哈希，
再把设备上用来对照的根哈希也一起换掉**。比方：包裹外贴着"重量 2.3 kg"的纸条，攻击者换掉里面的东西，
再把纸条换成"3.1 kg"。问题不在秤，而在**纸条放在哪**。
所以根哈希要放进签名的 boot.img：改它 = 改 boot.img = 签名失效，没有私钥重签不了。

### 5.3 dm-verity 和 Merkle 树 📖

- **dm-verity 是 Linux 内核的标准功能**，不是我们起的名字。dm = device-mapper（在真实磁盘上"套一层"虚拟磁盘的框架），
  verity = 验证。Google 为 ChromeOS 开发，每台 Android 手机都在用。LUKS 用的 dm-crypt 是同一框架下的另一个成员。
- **不是取样，是全部都哈希、用到时才验证**：
  - 构建时：**每一个** 4 KiB 块都算哈希，建成树，得到根哈希
  - 运行时：哪个块被读到，就在读到那一刻验证哪个块。没读过的块没被用过，无所谓。
    任何一个块在被使用之前一定先被验证过——覆盖 100%，只是时间推迟了。
- **Merkle 树**解决的是：只需信任一个 32 字节的根哈希，就能间接信任所有块；验证一个块只要沿一条路径算几次哈希。
  Git 的提交、区块链也是这个结构。
- 实测：卡上改 1 字节 → 内核报 `data block 75372 is corrupted`，和主机上预先算出的块号一致（case-10）。
  188 MB 数据的哈希树只占 1.46 MB（0.79%）。

## 6. 工具 2：HMAC（带密钥的哈希）✅（Q56：身份验证部分）

### 6.1 为什么需要它

哈希谁都能算，所以要靠"标准答案存在一个改不了的地方"。dm-verity 可以这样做，因为根文件系统固定不变，
答案能提前算好放进签名的 boot.img。

但 MCU 认证这种场景——Pi 想确认 SPI 那头是**我们配对过的那块 MCU**——用哈希不行：
DEVICE_ID 是公开的，克隆板也能算它的哈希。**哈希证明不了"你是谁"。**

HMAC = `HMAC(密钥, 数据)`，**没有密钥就算不出正确的值**：

```bash
echo -n "hello" | openssl dgst -sha256 -mac HMAC -macopt key:secret1
echo -n "hello" | openssl dgst -sha256 -mac HMAC -macopt key:secret2   # 结果完全不同
```

| | 哈希 | HMAC |
| --- | --- | --- |
| 谁能算 | 任何人 | 只有持有密钥的人 |
| 要防篡改需要保护 | "标准答案"不被**改**（完整性） | 密钥不被**看到**（机密性） |
| 能证明是谁 | 不能 | 能（但双方都能算） |
| 适合 | 内容固定、答案能提前存好（dm-verity） | 证明身份、答案每次不同（MCU 认证） |

HMAC 多了"证明身份"的能力，代价是问题换了形式：从"答案放哪才改不了"变成"**密钥放哪才偷不走**"。
整个项目最后都卡在这个问题上（F103 没有安全存储，Pi 的 OTP 没烧）。

### 6.1b HMAC 内部是怎么算的（面试前追问，2026-09）📖

**就是 SHA-256 算两遍，钥匙在两遍里各混进去一次**（RFC 2104）：

```
内层 = SHA-256( (K ⊕ ipad) ‖ 消息 )        ipad = 0x36 重复 64 次
外层 = SHA-256( (K ⊕ opad) ‖ 内层 )        opad = 0x5c 重复 64 次
HMAC = 外层
```

K 先补零到 64 字节（SHA-256 一次吃 64 字节），和两个固定常数分别异或，得到两把"变形"的钥匙。

手算和标准库一致（scratchpad 实测）：

```
手算  HMAC = b6fc7109a6ee3b33…   ← K="secret-key", 消息="sector 1687560 data"
标准库 HMAC = b6fc7109a6ee3b33…
普通哈希    = d5b38197bf36bc4a…   ← 不带钥匙，谁都能算
换一把钥匙  = a65ac92d52f2f3cb…   ← 钥匙差一个字母，结果全变
```

**为什么不直接 SHA-256(K ‖ 消息)？** 长度扩展攻击：SHA-256 是一块一块往下算的，最终结果就是算到最后的内部状态。
攻击者拿到 `SHA-256(K ‖ 消息)`，不知道 K，也能**接着往后算**，得到 `SHA-256(K ‖ 消息 ‖ 填充 ‖ 他加的内容)` 的正确值——
也就是伪造一条更长的、"带着正确印章"的消息。HMAC 外面再包一层带钥匙的哈希，把内层结果封住，接着算就没用了。
这也是原则 15"不要自己发明密码学"的例子：直觉上对的写法，恰好是错的。

MCU 固件里的 HMAC 就是按这个结构手写的（`devauth`），用 RFC 4231 标准测试向量 + Python 对拍 321 项 0 差异（18.1）。

### 6.2 不保证的

1. 不保证机密性：数据还是明文，HMAC 只是附在后面的"印章"
2. 双方共享同一把密钥：验证的一方也能伪造。要"所有人能验、只有一人能签"得用签名
3. 不防回放：旧消息连同旧 HMAC 原样重发照样通过。MCU 认证用 nonce 防回放；
   LUKS integrity 没防回放（文档老实写了"不防回放旧扇区"）

### 6.3 项目里：MCU 挑战-应答

```
Pi：  生成 16 字节随机数 nonce ─────►  MCU：HMAC(K, "acq-auth-v1" ‖ DEVICE_ID ‖ FW_VERSION ‖ nonce)
Pi：  自己也算一遍，比较       ◄─────  返回前 16 字节
```

真实代码：设备上 `device-service` 启动前的那道门
`yocto/meta-device-platform-verity/recipes-support/device-platform-ab/files/device-platform-mcu-auth`。

| 成分 | 为什么要有 |
| --- | --- |
| K | 克隆板没有 K，答不对 |
| nonce | 防回放：录下上次的回答也没用 |
| "acq-auth-v1" | 域分隔：这个 HMAC 只能用于这一种用途 |
| DEVICE_ID、FW_VERSION | 把回答绑定到具体设备和固件版本 |

**用 HMAC 派生密钥**（`tools/pair-mcu.sh`）：`K = HMAC(master, "acq-pairing-v1" ‖ MCU 的 UID)`。
每块 MCU 的 UID 不同 → K 不同 → 从一块 MCU 里抠出 K 只能冒充这一块。这叫"一机一密"。

## 7. 签名的直觉，以及"反签" ✅（Q57）

（签名的完整讲解在第 0 课下半段，这里只是直觉。）

**签名**：一对钥匙——私钥只有签名者有，用来签；公钥公开，用来验。验过就知道"确实是私钥持有者签的，签完没被改过"。
像盖章：谁都能看出是不是这个章盖的，但只有拿着章的人能盖。

**反签（counter-sign）**：在别人已经签过名的东西上再签一次自己的名。

- EEPROM 里的 bootsys 是树莓派公司写的，本来就有树莓派的签名。
- **Pi 4**：BootROM 只检查树莓派的签名。
- **Pi 5 安全模式**：还要求**产品厂家（我们）**的签名，我们的公钥是否可信看 OTP 里的哈希。两个都对才运行。
  像公司付款：财务盖章（正规单据）+ 老板签字（我同意付）。

**为什么要多这个章**：只有树莓派一个章时，**任何官方签过名的 bootloader 都能在你的产品上跑**，
包括有已知漏洞的老版本、不检查 boot.img 签名的版本。攻击者不用伪造任何东西，刷一个官方老版本就绕过了保护
（**降级攻击**，和 F6"旧版本也是合法签名的"是同一类问题）。
有了反签，**决定这台设备能跑哪个 bootloader 的是产品厂家，不是板子供应商。**

项目里：`update-pieeprom.sh -f -H pkcs11-hsm-wrapper -p public.pem` 用 HSM 里的 boot 密钥反签官方 bootsys，
生成产线要刷的 EEPROM 镜像；再拆开核对"镜像里的公钥哈希 == HSM 里公钥的哈希"（`fe0144747838fcf8…`）。
这是烧 OTP 前最重要的检查——烧进去的哈希就是从这个镜像里的公钥算的，用错密钥这块板子就永远只认错的那把。
镜像没刷进板子：OTP 没烧之前，Pi 5 上反签过的 EEPROM 镜像根本不运行。

## 8. 验证到底在做什么 📖

### 8.1 哈希、HMAC、签名都不是加密

| | 做的事 | 能还原成原文吗 | 原文还能看吗 |
| --- | --- | --- | --- |
| 加密 | 把内容变成乱码 | 能，有密钥就能解密 | 不能 |
| 哈希 / HMAC / 签名 | 算一个"指纹/印章"附在数据旁边 | 不能，也不需要 | 能 |

boot.img 和 p5 都没加密，拔出卡就能读。整个过程没有"解密"，只有**验证 = 自己重新算一遍，和参照值对比**。
项目里真正用到加密的只有 p7（LUKS）。

### 8.2 参照值（"标准答案"）在不同场景叫什么

通用叫法是**参照值 / 期望值**（reference value / expected value）。"根哈希"只是 dm-verity 里那个参照值的名字
（哈希树最顶上的点，树倒过来画，顶上是根）。

| 场景 | 参照值是什么 | 为什么攻击者换不掉 | 验证需要什么 |
| --- | --- | --- | --- |
| dm-verity 验证 p5 | 根哈希 | 放在签名的 boot.img 里 | 什么都不要 |
| 验证 boot.img | boot.sig 里的签名 | 没有私钥造不出来 | 公开的公钥 |
| 下载的 ISO 旁边的 `.sha256` | 哈希值 / 摘要（digest） | 靠从可信渠道拿到它 | 什么都不要 |
| MCU 认证、dm-integrity | 没有预存的，验证方用密钥**当场算** | 攻击者没有密钥 | 保密的共享密钥 |

它们一环扣一环：**签名保护 boot.img → boot.img 里有根哈希 → 根哈希保护 p5 的每一块。**

### 8.3 为什么攻击者随便编一把密钥算 HMAC 没用（p7 dm-integrity 的例子）

dm-integrity 给 p7 每个扇区算一个"指纹"，**就存在同一张卡上、数据旁边**，攻击者两样都能改。

```
用哈希：  攻击者改数据 → 重算哈希写到旁边 → 设备重算哈希对比 → 一样 → 发现不了
用 HMAC： 攻击者改数据 → 用自己编的密钥算 HMAC 写到旁边
          → 设备用【自己的真密钥】重算 → 和旁边的不一样 → 发现了
```

关键：**验证方从来不用攻击者的密钥，用的是自己的。** 所以 HMAC 比哈希多两个能力：
能验证身份；参照值可以和数据放在一起、放在不可信的地方。

### 8.4 boot.img 的签名是怎么做出来的（真实数据，1.2.2 版本）

boot.sig 的真实内容：

```
7edeb3e6922b628535745ec7df848f00a1ba5daba187075e6106a692f176a57c   ← = sha256sum boot.img
ts: 1790274981                                                      ← 签名时间
rsa2048: 2151d108cc70ca20…（512 个十六进制字符）                    ← 签名本体
```

- **签名**（签名主机）：对 boot.img 算 SHA-256 → 把指纹交给 HSM，HSM 里的私钥对它做一次运算 → 得到签名 →
  写成文本文件 boot.sig。"写入"就是用 `mcopy` 把它和 boot.img 一起拷进 p2。
- **验证**（bootloader）：自己对 boot.img 算一遍 SHA-256 → 用公钥检查"这个签名是不是那把私钥对这个指纹签的"。
- **签名 = 哈希 + 私钥运算**：先用哈希把大文件压成小指纹，再用私钥给指纹"盖章"。

### 8.5 私钥 vs 共享密钥

| | 私钥 / 公钥 | 共享密钥 |
| --- | --- | --- |
| 属于 | 非对称（asymmetric） | 对称（symmetric） |
| 几把 | **一对**：私钥只有持有者一个人知道，公钥给所有人 | **一把**，双方各持一份**相同**的副本 |
| 项目里用在 | 签名（boot.img、更新包、证书） | HMAC（MCU 认证、dm-integrity）、对称加密（LUKS 的 AES） |

"私钥"这个词只在非对称场景下用；HMAC 里的叫"密钥 / 共享密钥"。
（注意别说反："成对"的是公钥+私钥；共享密钥是同一把钥匙的两份拷贝。）

### 8.6 MCU 认证为什么要 nonce

只算 `HMAC(K, 设备号)` 的话结果每次都一样，攻击者在 SPI 线上录下一次正确回答，以后原样播放就能冒充（回放攻击）。
所以 Pi 每次生成新的随机 nonce，MCU 算 `HMAC(K, "acq-auth-v1" ‖ 设备号 ‖ 固件版本 ‖ nonce)`，
正确答案每次都不同，录下来的旧回答没用。

### 8.7 共享密钥存在哪？安不安全？

**存在哪：**

| 谁 | 密钥在哪 | 怎么放进去的 |
| --- | --- | --- |
| MCU | 自己 flash 的最后一页，地址 `0x0807F800`（链接脚本 `STM32F103xx_FLASH.ld` 专门留出来） | 配对时 `tools/pair-mcu.sh` 通过 SWD 调试口写进去 |
| Pi | `/data/devauth/mcu.key`（p7 加密分区上，root 0600） | 配对时拷过去 |
| 签名主机 | 主密钥 `pairing-master.key` + 每块 MCU 的 K | 由主密钥 + MCU 的 UID 派生 |

**安不安全：不太安全，而且这正是这一块的核心弱点**（威胁模型 F10）。实测（`results/security/device-auth/rdp-level1-demo.txt`）：

- **RDP level 0**（默认）：调试器接上 SWD 直接读出了密钥：`0x0807f800: 61b413d4 a88f1b26 …`
- **RDP level 1**：同样的读取报 `Failed to read memory`。解除 level 1 会**整片擦除**（密钥和固件一起没了）。
  但 F103 的 level 1 有公开的绕过方法（CVE-2020-8004），拿着论文和调试器还是能读出来。
- **RDP level 2**：永久锁死调试口，不可逆，唯一一块 MCU 不用。
- 板子现在停在 level 0（开发要用）。

**已经做的减损**："一机一密"——K 由 MCU 的 UID 派生，每块不同，抠出一块的 K 只能冒充这一块。
**真正的解决办法在硬件**：外接安全芯片（ATECC608 这类，密钥在里面、MAC 由它算），或者换带 TrustZone-M 的 MCU（Cortex-M33）。
Pi 这边的密钥真正该放的地方是 OTP 设备密钥（没烧）。
这又回到同一句话：**用了密钥，问题就变成"密钥放哪"。**

### 8.8 HSM（硬件安全模块）

**HSM = Hardware Security Module：一个装着私钥的保险箱，能让它用私钥干活，但永远拿不到私钥本身。**

```
你："帮我签这个指纹"  ──►  HSM（私钥在里面生成，永远不出来）  ──► 签名
你："把私钥给我"       ──►  没有这个操作
```

- **为什么需要**：签名私钥是整个系统最值钱的秘密（威胁模型 §2）。放在构建服务器上的文件，服务器被黑就被复制走，
  可能还不知道；放在 HSM 里，黑客最多趁你不知情**借用**它签几次，**带不走**。
- **长什么样**：U 盘大小（YubiHSM、Nitrokey HSM）、机架设备（Thales Luna）、云服务（AWS CloudHSM）。
  程序通过标准接口 **PKCS#11** 和它对话。
- **在哪里**：HSM 在**厂家这边**（签名主机、产线），不在设备上。设备上对应的东西是 TPM、安全芯片、TEE（OP-TEE 那一课）。
- **我们项目**：用 **SoftHSM2**（软件模拟，接口一样，换真 HSM 只改一行指向驱动库）。5 把密钥：
  01 boot 密钥（签 boot.img）、02 Device CA、03 Update CA、04 release-1（已吊销）、05 release-2（在用）。
  生成时设了 `never extractable`，连我们自己也导不出私钥；PIN 从不放在命令行上。
- **诚实说**：SoftHSM 的私钥其实是加密后存在硬盘上的文件，只是模拟。真 HSM 多的是物理防护、防拆、安全备份。
- 为什么要 02、03 这种 CA、要一堆钥匙：下半段"证书和 CA"。

### 8.9 能不能不在 MCU 上存密钥？ 📖

**想法**：Pi 事先算好 `HMAC(K, MCU 的 ID)`，只把结果写进 MCU，MCU 不存 K。

**不行，两个原因**（✅ Q63）：
1. **答案固定，会被回放**：攻击者不用碰 MCU，在 SPI 线上录一次就能永远重放。
   要答案每次不同，MCU 就得当场把 nonce 算进去，这需要 K。
2. **结果本身变成了新密钥**：从 flash 读出这个值写进克隆板，克隆板就能冒充。
   它和 K 地位一样，而且更弱——它就是个每次都在线上明文传输的密码。

原理：**要证明"我有某个秘密"，就必须真的拥有这个秘密。** 挑战-应答 = 每次出新题，只有持有秘密的人能答对；
不持有秘密就只能背答案，背下来的答案能被偷、被重放。

**业界的真实方案——不是不要密钥，而是换个比 flash 难读的地方放：**

| 方案 | 密钥在哪 | 为什么更难偷 |
| --- | --- | --- |
| 安全芯片 secure element（ATECC608 这类） | 一颗专门的小芯片 | 芯片自己算 HMAC/签名，密钥不出芯片，有防物理攻击设计 |
| TrustZone-M（Cortex-M33 级 MCU） | MCU 里隔离的安全区 | 普通代码和调试器访问不到 |
| PUF（physically unclonable function，物理不可克隆函数） | **不存储**：用芯片制造时的微小物理差异（如 SRAM 上电初值）每次开机现场算出 | 断电后密钥不存在于任何地方，拆芯片也读不到，换一颗算出来就不一样 |

PUF 最接近"不存密钥"的直觉，NXP、ST 的一些新 MCU 已内置。F103 太老，三样都没有。

### 8.10 一机一密时，Pi 怎么知道该用哪把 K？ 📖

**先澄清："一机一密"是每块 MCU 的 K 不一样，不是 K 会变。** 某一块 MCU 的 K 配对时定下来，之后一直不变。

**K 是怎么来的**（配对时，`tools/pair-mcu.sh`）：

```
1. 通过 SWD 读 MCU 的 UID（芯片出厂自带的 96 位唯一编号，地址 0x1FFFF7E8）
       例：35ffdb05334d523717702051
2. K = HMAC(master, "acq-pairing-v1" ‖ UID)      ← master 是一把主密钥
3. 把 K 写进这块 MCU flash 的最后一页（0x0807F800）
4. 记一条配对日志（时间、操作员、UID、K 的指纹）
```

**Pi 验证时拿 K 的两种办法：**

| | 现在的实现 | 设计上的做法 |
| --- | --- | --- |
| Pi 手里有什么 | 只有**它配对的那一块** MCU 的 K：`/data/devauth/mcu.key` | 主密钥 master（理想情况是 Pi 的 OTP 设备密钥，通过固件 HMAC 服务使用，永远读不出来） |
| 验证时 | 直接用这把 K | 读 MCU 的 UID，现场算 K = HMAC(master, "acq-pairing-v1" ‖ UID) |
| 为什么可行 | 一台 Pi 只配一块 MCU，一对一，只需要一把 K | K 可以随时重新算出来，Pi 上根本不用存 K |

**为什么能限制损失：**

- 从 MCU 1 里抠出 K1，只能冒充 MCU 1。
- 想得到 MCU 2 的 K2 就必须有 master；而 HMAC 是单向的，从 K1 反推不出 master。
- 现在的实现里 Pi 也只存一把 K，所以攻破一台 Pi 也只暴露一对。
- **代价**：master 变成了"一把钥匙开所有锁"的那把，必须放在最好的地方。现在它是签名主机上的一个文件
  （`pairing-master.key`，替代品）；设计上是 Pi 的 OTP 设备密钥，或者厂家的 HSM。

这就是"**密钥派生**"（key derivation）：一把保护得最好的主密钥，派生出很多把分散的、各管一台设备的子密钥。
子密钥丢了只损失一台，主密钥永远不出最安全的地方。

### 8.11 为什么不能直接 K = SHA-256(UID)，省掉 master？ 📖

**master 是什么**：厂家手里的一把随机生成的秘密（32 字节随机数），不写进任何设备，只用来"算出"每块 MCU 的 K。
项目里是签名主机上的 `pairing-master.key`。

**只用 UID 不安全**：UID 不是秘密——任何人拿调试器接上 SWD 就能读，它还会出现在日志、配对记录里；
SHA-256 又是谁都能算的公开算法（原则 1：算法要假设攻击者全知道）。
所以攻击者读出 UID → 自己算 SHA-256(UID) → 就得到了 K，**连 MCU 的 flash 都不用读**，任何一块板子都能这样算出来。
这时 K 看起来每块不同，实际上等于没有秘密。

**加上 master 之后**：`K = HMAC(master, "acq-pairing-v1" ‖ UID)`。UID 照样公开，但没有 master 就算不出 K。
攻击者只能一块一块地去抠 flash（8.7 的 RDP 问题），而且抠出 K1 也反推不出 master，算不出 K2。

一句话：**"每块不同"不等于"保密"。派生密钥时，输入里必须有一样东西是保密的，公开的 UID 只负责让结果每块不同。**
（和 5.1/6.1 是同一件事：哈希谁都能算，证明不了什么；HMAC 的力量全部来自密钥。）

## 9. 安全设计的基本原则 📖

这些原则在整个项目里反复出现，换任何项目都适用。每条附项目里的例子。

### 关于秘密

1. **安全只能建立在密钥上，不能建立在"算法没人知道"上**（Kerckhoffs 原则）
   —— 算法要假设攻击者全都知道。SHA-256、HMAC、RSA 都是公开标准；我们的代码也在 GitHub 上。
   唯一需要保密的是密钥。反面叫 "security through obscurity"（靠隐藏来保安全），不算安全。
2. **秘密一旦说出来就不再是秘密**
   —— 所以**证明你有秘密，但永远不交出秘密**：挑战-应答只交出"用密钥算出的答案"，从不传密钥本身；
   HSM 只交出签名，从不交出私钥；OP-TEE 的 TA 连自己读私钥都会被强制 panic。
   固定答案 = 密码 = 每次都在交出秘密（8.9）。
3. **要证明你有秘密，就得真的有秘密**（8.9）
4. **把要保护的东西缩到最小**
   —— 哈希树把"整个 p5 可信"缩成"32 字节根哈希可信"；签名把"整个 boot.img 可信"缩成"私钥没泄露"；
   HMAC 把"标准答案存哪"缩成"一把密钥存哪"。秘密越小越少，越容易保护。
5. **用了密钥，问题就变成"密钥放在哪"**
   —— 整个项目的"受硬件限制"都卡在这：Pi 的 OTP 没烧、F103 没安全存储、LUKS 密钥是从序列号推的替代品。

### 关于信任

6. **信任必须有一个物理上改不了的起点**（信任根）
   —— BootROM、OTP。没有它，"检查者由谁检查"就没有尽头。我们这块板子的信任根是模拟的。
7. **一环验一环，下一级的依据来自上一级**（信任链，Q59）
   —— 签名 → boot.img → 根哈希 → p5 每一块。链上任何一环没验，后面全部不可信。
8. **验证的依据要放在攻击者碰不到的地方**
   —— 根哈希放进签名的 boot.img（Q47）；设备上信任的是 CA 证书，放在经过验证的 rootfs 里。

### 关于时间

9. **答案必须是新鲜的**（freshness）
   —— 旧的正确答案被重放，照样能通过。对策：每次一个新 nonce（MCU 认证）或只增不减的计数器。
10. **旧版本也是合法签名的**（防回滚）
    —— 同一个"新鲜性"问题放到版本上：去年的固件签名照样有效，攻击者装回去就能利用去年的漏洞。
    所以要 `min-bundle-version`，最终要一个攻击者无法重置的单调计数器（OTP 位 / RPMB / TPM）。
    **任何靠"可重写存储"执行的规则，都能靠回滚那份存储来撤销**（OP-TEE 生成了第二个身份）。

### 关于损失

11. **一处泄露，只有一个后果**（限制破坏半径，blast radius）
    —— 一机一密（MCU 的 K 由 UID 派生）；每把钥匙只干一件事（boot 密钥、Device CA、Update CA、release 密钥分开）；
    域分隔（"acq-auth-v1" 前缀让这个 HMAC 不能被挪作他用；TA 只签带固定前缀的挑战，不签任意数据）。
12. **最小权限**（least privilege）
    —— device-service 从 root 降到专用用户 `acq`，只留 2 个 capability，暴露评分 9.4 → 1.8；
    内核模块从 1808 个减到 31 个。没有的东西不会被攻击。
13. **纵深防御**（defense in depth）：不指望任何一层完美
    —— 只读根 + dm-verity + 沙箱 + 模块签名，一层被突破，下一层还在。
14. **失败时要关上，而不是敞开**（fail closed）
    —— MCU 认证失败 → device-service 不启动 → 健康检查不过 → 更新不提交、自动回滚；
    OP-TEE 发现存储被回滚 → 整个安全存储拒绝使用。代价：发现攻击变成了拒绝服务（可用性换完整性）。

### 关于工程

15. **不要自己发明密码学**（don't roll your own crypto）
    —— 用标准的 HMAC-SHA256、RSA、ECDSA，不自创算法。MCU 上的 SHA-256 是按标准（FIPS 180-4 / RFC 2104）手写的，
    所以要用 RFC 4231 测试向量 + Python 对拍 321 项，0 差异才敢用。
16. **完整性和机密性是两回事**：加密不防改（Q49），签名不防看。先问清楚要防的是哪个。
17. **配置是请求，不是确认**：必须读回验证
    —— Yama 编进去了却没启用；ramoops overlay 静默无效；CRL 只有 30 天。每一个都是"构建成功、看起来对"，只有读回才发现。
18. **没有绝对的安全，只有提高攻击成本**；诚实说出局限
    —— RDP level 1 挡住普通调试器，挡不住读过论文的人（CVE-2020-8004）。
    文档里每处"受硬件限制"都写清楚了还差什么，这比假装做完更可信。

## 10. 工具 3：对称加密（AES）✅（Q64）

（第 0 课下半段从这里开始。）

### 10.1 三个问题

| | |
| --- | --- |
| 做什么 | `密文 = AES(密钥, 明文)`，`明文 = AES⁻¹(密钥, 密文)`。加密、解密用**同一把**密钥 → 对称 |
| 保证 | 没有密钥看不懂内容（**机密性**） |
| 不保证 | 内容没被改过（完整性）；是谁写的（真实性） |
| 需要的秘密 | 那把共享密钥。算法（AES）是公开标准 |

和前面的工具对比：哈希/HMAC/签名是"在数据旁边附一个印章"，原文照样能看；
加密是"把原文本身变成乱码"，而且**能还原**（8.1）。

AES = Advanced Encryption Standard，2001 年的美国标准，现在几乎所有加密都用它。
一次处理 16 字节（一个"块"）；密钥 128 或 256 位。CPU 普遍有硬件指令（Pi 5 的 Cortex-A76 有 Armv8 加密扩展，
内核里叫 `xts-aes-ce`），所以 p7 加密只慢了 7%（`integrity-and-encryption` §5）。

### 10.2 实测：AES-XTS（p7 用的就是这个模式）

`python3` + `cryptography` 库，随机 512 位密钥，32 字节明文（= 2 个 AES 块）：

```
明文                   57494649 5f50534b 3d4d7953 65637265 74506173 73313233 3b3b3b3b 3b3b3b3b | WIFI_PSK=MySecretPass123;;;;;;;;
密文                   45e9a120 8232ced5 83f267bb ec40ff88 64889e1c b932fab8 b82f7620 68c0908f | E.. .2....g..@..d....2.../v h...
正确密钥解密           57494649 5f50534b 3d4d7953 65637265 74506173 73313233 3b3b3b3b 3b3b3b3b | WIFI_PSK=MySecretPass123;;;;;;;;
错误密钥解密           ca510829 a0342565 501cf446 47600b00 9940e005 7fac836b bd64ecb5 1130d314 | .Q.).4%eP..FG`...@.....k.d...0..
改密文 1 个比特后解密  57494649 5f50534b 3d4d7953 65637265 dee42b88 8e441488 bfa4d628 5a0572f8 | WIFI_PSK=MySecre..+..D.....(Z.r.
同样明文放在第 2 号扇区 b8408c71 fea0a4a8 a7732f67 29730912 85ea7389 e16f7eb9 d3ed83bb 9523396d | .@.q.....s/g)s....s..o~......#9m
```

看出来的四件事：

1. **错误密钥解密不报错**，只是吐出乱码。AES 本身不知道"解对了没有"。
2. **改密文不报错**：被改的那个 16 字节块解出乱码，另一个块完好无损。文件系统会把乱码当正常数据读下去
   → 这就是 Q49"加密不防改"的现场，也是 p7 要再加 dm-integrity 的原因（8.3，`integrity-and-encryption` §6）。
3. **同一段明文放在不同扇区，密文不同**：XTS 把扇区号算进去（叫 tweak），攻击者没法通过"两处密文一样"推出"两处内容一样"。
   这是 XTS 专门为磁盘设计的地方：按扇区独立加解密、密文和明文一样长（磁盘上没地方多放东西）。
4. 密钥 512 位 = 两把 256 位 AES 密钥（XTS 一把加密数据、一把加密扇区号），所以 `--key-size 512` 实际是 AES-256。

### 10.3 项目里：p7 的密钥是怎么来的——正好是 8.11 的反面教材

`device-platform-data`（首次开机建 LUKS、之后每次开机打开 p7 的脚本）：

```sh
key() {
	serial=$(tr -d '\0' < /proc/device-tree/serial-number)
	printf 'device-platform-data-v1:%s' "$serial" | sha256sum ...
}
```

`密钥 = SHA-256("device-platform-data-v1:" ‖ 序列号)` —— 和 8.11 里 `SHA-256(UID)` 一模一样的错误：
序列号是公开的（印在板上、任何系统都能读），SHA-256 谁都能算。拔走 SD 卡的人查到序列号就能解开 p7。
脚本开头自己用大字写着 `KEY STAND-IN, NOT SECURE`。

设计上的正确做法：`密钥 = HMAC(OTP 设备密钥, 序列号 ‖ eMMC CID)`，由固件算、密钥读不出来，算完就锁到下次重启
（`integrity-and-encryption` §3）。又是同一句话：**序列号只负责"每台不同"，保密要靠一把真正的秘密**；
而那把秘密要放在 OTP 里——没烧，所以用了替代品。加密做得再标准，密钥能被算出来就等于没加密。

## 11. LUKS：p7 上的加密是怎么组织的 📖

### 11.1 三层

```
/data（ext4，普通文件）
  └─ /dev/mapper/data        dm-crypt：读时解密、写时加密（AES-XTS）   ← 应用看到的是明文
       └─ /dev/mapper/data_dif  dm-integrity：每个 512 字节扇区配一个 32 字节 HMAC
            └─ /dev/mmcblk0p7   卡上真实的字节：LUKS 头 + 密文 + 标签
```

应用和文件系统完全不知道底下有加密——和 dm-verity 一样是 device-mapper "套一层虚拟磁盘"的思路（5.3）。

### 11.2 LUKS 头：为什么有两级密钥

LUKS = Linux Unified Key Setup，是"加密分区的标准格式"，规定分区开头放一个**头**：

```
LUKS 头（p7 开头）
 ├─ 加密参数：aes-xts-plain64、512 位、integrity hmac-sha256
 └─ 钥匙槽 keyslot 0..31：每个槽里放着"用某个口令加密过的卷密钥"
数据区：用【卷密钥】（volume key，随机生成，一直不变）加密的扇区
```

- 真正加密数据的是**卷密钥**，luksFormat 时随机生成，存在头里但被口令加密着。
- 我们脚本给的 `SHA-256(序列号)` 只是**口令**，用来解开钥匙槽拿到卷密钥。
- 好处：换口令只要重写一个钥匙槽，不用把 1 GB 数据全部重新加密；可以有多个口令（比如一个日常用、一个售后恢复用）。
- 我们的卷密钥是 768 位 = 512（XTS）+ 256（integrity 的 HMAC 密钥）（`integrity-and-encryption` §6）。
- `--pbkdf pbkdf2 --pbkdf-force-iterations 1000`：PBKDF 是"把人类口令慢慢算成钥匙"的函数，故意算得慢来防暴力猜口令。
  我们的口令本来就是 256 位随机值，不怕猜，所以用快的，开机快。
- 开机打开后，卷密钥一直在内核内存里——任何磁盘加密都是这样。

### 11.2b 重讲：LUKS 头到底是什么（实测）✅（Q69）

第一遍讲得太抽象，用户没听懂。重讲，从字节开始。

**先想一个问题**：p7 的数据用 AES 加密，AES 需要一把密钥。开机时这把密钥从哪来？
不能明文存在卡上（拔卡就读走了），所以卡上存的是**被口令锁住的密钥**，开机时用口令打开。
存放这些东西的地方，就是分区开头的一块区域，叫 **LUKS 头**。

**比喻**：保险柜（数据区）只有一把真钥匙（卷密钥）。真钥匙不挂在外面，而是锁在门口的**小钥匙盒**（钥匙槽）里，
小钥匙盒用密码（口令）打开。可以有好几个小钥匙盒，每个用不同的密码，里面放的都是**同一把**真钥匙。

在 scratchpad 里用 32 MB 的文件建了一个和 p7 同参数的 LUKS2（没加 integrity，那个要 root）：

```
开头的字节（xxd）:  4c55 4b53 babe 0002 ...  "LUKS..."   ← 分区开头就是 LUKS 头，魔数 "LUKS" + 版本 2

cryptsetup luksDump:
  Data segments:  offset: 16777216 [bytes]  cipher: aes-xts-plain64   ← 前 16 MiB 是头，数据从这之后开始
  Keyslots:
    0: luks2   Key: 512 bits   PBKDF: pbkdf2   Salt: d5 db 7d ...      ← 0 号钥匙盒：用口令锁着的卷密钥
  Digests:  0: pbkdf2  Digest: 38 31 8d 5f ...                          ← 卷密钥的指纹，用来判断"解对了没有"
```

三个实验：

```
错误口令:                    No key available with this passphrase.     ← 被 Digest 识别出来了
正确口令 my-passphrase:      卷密钥 = 00 82 57 98 ea 3f 5d a0 ...
luksAddKey 加第二个口令后:   Keyslots: 0: luks2   1: luks2
第二个口令 service-pass:     卷密钥 = 00 82 57 98 ea 3f 5d a0 ...       ← 同一把！
```

- 卡上真正的数据是用**卷密钥**加密的，卷密钥是 luksFormat 时随机生成的 512 位，之后永远不变。
- 口令只用来打开钥匙槽。加口令、换口令只改头里的钥匙槽，**数据区一个字节都不动**。
- 注意第一行：直接用 AES 解错了不报错（10.2），LUKS 却能说"口令不对"——因为头里存了卷密钥的指纹（Digest），
  解出来的卷密钥对不上指纹就拒绝。这是 LUKS 在 AES 外面加的一层方便，不是 AES 自己的能力。

**对应到我们的 p7**：口令 = `SHA-256("device-platform-data-v1:" ‖ 序列号)`（10.3 那个不安全的替代品）。
所以攻击者要的不是卷密钥本身——算出口令，头里的钥匙槽会自己把卷密钥交出来。
（设计上口令应该来自 OTP 设备密钥的 HMAC，`integrity-and-encryption` §3。）

### 11.2c 纠正："卷"不是把数据切成很多份 ✅（Q69）

用户复述时理解成"数据分成很多卷，每卷一个 LUKS 头 = 一个小钥匙盒"。不对：

- **卷（volume）= 一整块被当成磁盘用的区域**。我们这里一个卷就是整个 p7。**一个 p7 → 一个 LUKS 头 → 一把卷密钥。**
- **LUKS 头 ≠ 小钥匙盒**。LUKS 头是门口整面墙，**钥匙盒（keyslot）是挂在这面墙上的几个盒子**（LUKS2 最多 32 个），
  每个盒子用不同的口令锁着，里面放的都是**同一把**卷密钥。
- 多个钥匙盒 = 多个口令都能开同一个保险柜（日常口令、售后恢复口令），不是多份数据。

```
p7 的字节:
[ LUKS 头 16 MiB                                  ][ 数据区：全部用同一把卷密钥加密 ...... ]
   ├ 参数：aes-xts-plain64, 512 位
   ├ 钥匙盒 0：口令 A 锁着的卷密钥   ← 我们只用了这一个
   ├ 钥匙盒 1：口令 B 锁着的卷密钥   （实验里 luksAddKey 加的）
   └ Digest：卷密钥的指纹
```

（如果真有好几个加密分区，那才是每个分区各有一个 LUKS 头、各有一把卷密钥。）

### 11.2d 口令从哪来

每次开机，`device-platform-data` 脚本**现场算出**口令，通过管道交给 cryptsetup，不落盘：

```sh
serial=$(tr -d '\0' < /proc/device-tree/serial-number)          # 板子序列号，固件写进设备树
printf 'device-platform-data-v1:%s' "$serial" | sha256sum        # = 口令
key | cryptsetup open --key-file - /dev/mmcblk0p7 data           # 口令 → 打开钥匙盒 0 → 卷密钥 → /dev/mapper/data
```

首次开机（p7 还不是 LUKS）时，同一个口令交给 `luksFormat`：生成随机卷密钥、用口令锁进钥匙盒 0、写头。

- **现在**：序列号公开 + SHA-256 公开 → 谁都能算出口令（10.3，和 8.11 同一个错误）。
- **设计上**：initramfs 里 `rpi-fw-crypto hmac` 用 **OTP 设备密钥**算 `HMAC(设备密钥, 序列号 ‖ eMMC CID)` 当口令，
  打开后立刻 `set-key-status … HMAC_LOCKED|READ_LOCKED`，到下次重启之前连 root 也算不出第二次。
  设备密钥在芯片 OTP 里、读不出来 → 口令只有这块芯片算得出来 → 卡拔走插到别的机器上打不开。
  前提：OTP 烧了 + secure boot（否则攻击者改掉 initramfs，让它把口令打印出来）。

### 11.2e 用户的好问题：口令既然被算出来交给 cryptsetup，不就能被读到吗？📖

**能。这个质疑是对的。** 口令算出来的那一刻在内存里；打开之后**卷密钥**一直在内核内存里（dm-crypt 要用它加解密每个扇区）。
所以要问的不是"能不能被读到"，而是"**谁**能读到"——回到威胁模型，先说清楚防谁。

**为什么要"现场算"而不是存起来**：存在卡上 = 拔卡的人也能读到。现场算，而且算的原料里有一样**只在这块芯片里**的东西
（OTP 设备密钥，读不出来），口令就只在"这块芯片正在运行我们的代码"时才存在。
→ 用户的理解是对的：**把数据绑定到这块硬件上**，防的是"卡被拔下来插到别的机器上"。

**口令算不算密钥**：算，它就是一个秘密。但这里 HMAC 的用途不是"验证身份"——没有谁在验证谁——
而是**派生密钥**（和 8.10 里 `K = HMAC(master, UID)` 一样）：用一把藏好的主密钥 + 公开的序列号，算出一个只有持有主密钥才算得出的值。
同一个工具，两种用法：MCU 认证里 HMAC 是"证明我有密钥"，这里是"从密钥里生出另一把密钥"。

**按攻击者分（设计方案：OTP HMAC + 用完即锁 + secure boot）**：

| 攻击者 | 能拿到口令/卷密钥吗 | 为什么 |
| --- | --- | --- |
| A3 拔走 SD 卡，插到别的机器 | **不能** | 别的芯片没有这把 OTP 设备密钥，算不出口令 |
| 改 initramfs 让它把口令打印出来 | **不能**（有 secure boot 时） | initramfs 在签名的 boot.img 里，改了不启动 |
| 开机后在设备上拿到 root | 算不出口令（已锁）；但**数据本身已经挂在 /data，root 直接读文件就行** | 加密防的是"关机状态的卡"，不防"运行中的系统" |
| 攻破内核 | **能** | 卷密钥就在内核内存里；OTP 也挡不住内核（Pi 文档原话） |

- 所以磁盘加密的本质是**保护"静止的数据"**（data at rest）：卡被拿走、设备被转卖、报废。系统运行中，数据本来就是解开的。
- "用完即锁"缩小的是时间窗口：只有开机那几秒口令能被算出来。
- 想连内核都防住：密钥交给 TEE（OP-TEE 那一课）；但即便 TPM/TEE，dm-crypt 打开后卷密钥照样在内核内存里——这是所有 Linux 磁盘加密的共同局限
  （`integrity-and-encryption` §3 最后一条）。
- 原则 18：没有绝对的安全，只有"对哪个攻击者安全"。

### 11.2f 多个钥匙盒能干什么 📖

用户的想法：**每个钥匙盒对应一个被授权的硬件**，各自的口令都能取出同一把卷密钥。原理上成立——口令由硬件派生时，
加一个钥匙盒就等于多授权一块硬件（比如售后换主板，把卡插到新板子上还能打开）。要精确一点：**一个口令开它自己的那个钥匙盒**，
不是多个口令开同一个盒子。

实际中更常见的用法：

| 用法 | 钥匙盒 0 | 钥匙盒 1 |
| --- | --- | --- |
| 自动解锁 + 恢复 | 硬件派生（TPM / OTP HMAC），开机自动 | **恢复口令**，打印出来锁在保险柜，硬件坏了用它救数据 |
| 换口令（轮换） | 旧口令 | 先加新口令，确认能开，再删旧的 |

PC 上的真实例子：`systemd-cryptenroll --tpm2-device=auto` 加一个 TPM 钥匙盒，`--recovery-key` 再加一个恢复口令钥匙盒；
Windows BitLocker 的"恢复密钥"也是同一回事。

两个要注意的地方：

- **最弱的那个钥匙盒决定整体安全**：任何一个口令都能拿到卷密钥，恢复口令保管不好，硬件绑定做得再好也白搭。
- **删掉钥匙盒不能收回已经泄露的卷密钥**：谁拿到过卷密钥，就能一直解密，删口令没用。要真正换掉卷密钥得把整个分区重新加密
  （`cryptsetup reencrypt`，1 GB 要写一遍）。

### 11.3 待解答问题：为什么不干脆全部加密？

| 分区 | 能加密吗 | 为什么 |
| --- | --- | --- |
| p1、p2/p3 | **不能** | bootloader 要在任何密钥可用之前读它们；而且里面没有秘密，只怕被改 → 签名 |
| p5/p6 | 能，但没意义 | 每台设备内容都一样、源码在 GitHub，没秘密；加密又不防改 → dm-verity |
| p7 | 要 | 只有它有秘密（采集数据、WiFi 密码、SSH 主机密钥、MCU 配对密钥）|

再加上：加密就要密钥，密钥要放在攻击者拿不到的地方——这件事本身就是整个项目最难的（原则 5）。
**多加密一个分区，就多一个"密钥放哪"的问题，却换不来任何防改能力。**

## 12. 工具 4：数字签名 📖

### 12.1 三个问题

| | |
| --- | --- |
| 做什么 | 私钥对（数据的哈希）做运算 → 签名；任何人用公钥检查签名和数据是否匹配 |
| 保证 | 数据没被改过（完整性）+ 确实是私钥持有者签的（真实性） |
| 不保证 | 机密性（原文照样能看）；新鲜性（旧版本的签名照样有效 → 防回滚）；私钥没被偷 |
| 需要的秘密 | 只有签名方的私钥。验证方只要公钥，**公钥可以公开** |

### 12.2 实测

一把临时的 P-256 密钥（`openssl genpkey` / `openssl dgst -sign / -verify`）：

```
签名长度: 71 字节
原文件 + 公钥验证:                          Verified OK
改 1 个字符后验证:                          Verification failure
攻击者用自己的私钥重签，设备用我们的公钥验:  Verification failure
```

对比 10.2：**AES 被改了不报错，签名被改了一定报错。** 第三行和 8.3 是同一个道理——验证方只用自己手里的公钥，
攻击者换一把钥匙签没有用。

### 12.3 和 HMAC 比：最大的差别在"谁能签"

| | HMAC | 签名 |
| --- | --- | --- |
| 钥匙 | 一把共享密钥，双方都有 | 私钥只在签名方，公钥给所有人 |
| 验证方能不能伪造 | **能**（它也有密钥） | 不能（它只有公钥） |
| 设备上要保护什么 | 密钥不被**看到** | 公钥不被**换掉** |
| 适合 | 两方之间（Pi ↔ MCU）、快、MCU 算得动 | 一方签、成千上万台设备验：boot.img、更新包 |

所以更新包必须用签名：如果用 HMAC，每台设备都得有那把密钥，**从任何一台设备里抠出来就能给所有设备造固件**。
用签名，设备上只有公钥，抠出来也没用。

项目里的签名：boot.img（RSA-2048，01 号钥匙）、RAUC 更新包（P-256 ECDSA，05 号 release-2）、证书本身（见 13）。
RSA 和 ECDSA 是两种签名算法，效果一样；ECDSA 的钥匙和签名都更短（71 字节 vs boot.sig 里的 256 字节）。
Pi 5 的 bootloader 只支持 RSA-2048，所以 boot 钥匙是 RSA。

## 13. 证书和 CA ✅（Q65、Q66）

### 13.1 签名留下的问题：设备凭什么信这把公钥？

设备里放一把公钥，信它签的东西——那如果这把私钥泄露了、或者两年到期了，要换钥匙怎么办？
要把新公钥发给所有设备，而"发给设备"本身就是一次更新，得用……旧钥匙签。泄露的情况下这就很尴尬。

**证书**（certificate，X.509 格式）= 一把公钥 + 关于它的说明（名字、有效期、能干什么）+ **另一把钥匙对这些内容的签名**。
签发证书的那把钥匙叫 **CA**（certificate authority，证书颁发机构）。

设备不再信任具体的签名钥匙，而是信任 **CA**：凡是 CA 签过证书的钥匙，我都信。

### 13.2 项目里的真实证书（`~/.device-platform-signing/update/`）

```
update-ca.cert.pem   ← 设备上信任的就是这一张（RAUC keyring，放在经过 dm-verity 的 rootfs 里）
  subject=CN = device-platform Update CA
  issuer =CN = device-platform Update CA        ← 自己签自己 = 根证书，信它是因为它被预装在设备上
  有效期 2026-09-23 → 2036（10 年）
  CA:TRUE, pathlen:0      ← 能签发证书，但它签出来的证书不能再签证书
  Key Usage: Certificate Sign, CRL Sign

release-2.cert.pem   ← 真正签更新包的钥匙（HSM 05 号）
  subject=CN = device-platform release signing 2
  issuer =CN = device-platform Update CA        ← 由 Update CA 签发
  有效期 2026-09-24 → 2028（2 年）
  CA:FALSE                ← 不能再签证书
  Key Usage: Digital Signature；Extended: Code Signing   ← 只能用来签代码
```

`openssl verify -CAfile update-ca.cert.pem release-2.cert.pem` → `OK`。

限制写在证书里（CA:FALSE、Code Signing）就是原则 11"每把钥匙只干一件事"：
就算 release 钥匙泄露，攻击者也不能用它签发新证书。

### 13.3 换钥匙和吊销（实测，`results/security/update/key-rotation-and-revocation.txt`）

- **轮换**：release-1 → release-2，CA 签一张新证书就行，**设备上什么都不用改**，两种包都被接受。
- **吊销**：release-1 标记为泄露（keyCompromise），CA 签一份 **CRL**（certificate revocation list，吊销列表），
  里面写着 release-1 的序列号：

```
openssl verify -crl_check:  release-1.cert.pem → error 23: certificate revoked
                            release-2.cert.pem → OK
RAUC:  release-1 包 → REJECTED  Verify error: certificate revoked
       release-2 包 → ACCEPTED
```

- CRL 自己也有坑（原则 17）：CRL 有有效期（我们 30 天），**过期了所有更新都被拒**；设备没有 RTC、开机时钟在 2025 年，
  会报 "CRL is not yet valid"；配置里不打开 `check-crl`，CRL 放进去也不生效。

### 13.4 为什么要这么多把钥匙（HSM 里的 01–05）

| 编号 | 钥匙 | 签什么 | 谁信它 |
| --- | --- | --- | --- |
| 01 | RSA-2048 boot 钥匙 | boot.img、反签 EEPROM | Pi 5 OTP 里的公钥哈希（**没有 CA 这一层**） |
| 02 | P-256 Device CA | 每台设备的身份证书（OP-TEE 那一课） | 后台服务器 |
| 03 | P-256 Update CA | 只签 release 证书 | 每台设备（RAUC keyring） |
| 04/05 | P-256 release-1（已吊销）/ release-2 | 更新包 | 通过 Update CA |

- **一处泄露一个后果**：Device CA 泄露，攻击者能伪造设备身份，但不能发固件。
- **01 最要命**：Pi 5 的 OTP 直接钉死一把公钥的哈希，中间没有 CA，不能轮换、不能吊销。丢了或泄露了，已出厂的板子没救。
  这也是 01 放在 HSM 里最该保护的原因。
- 证书链：**CA（根，预装在设备上）→ 签发 → release 证书 → 签 → 更新包**。和启动的信任链（原则 7）是同一个思想：
  一环验一环，起点必须放在攻击者改不了的地方（原则 8）。

### 13.5 用户复述后的补充：CA 到底是什么 ✅（Q67、Q68）

**CA 本身也是一对钥匙**（私钥在 HSM 里，03 号），只是它的工作很特别：**不签更新包，只签证书**。
"CA"这个名字说的是这把钥匙的**角色**，不是另一种技术。

比喻：身份证。

| 身份证 | 我们的更新 |
| --- | --- |
| 公安局 | Update CA（03 号钥匙） |
| 身份证 = 照片 + 姓名 + 有效期 + 公安局的防伪章 | release-2 证书 = 公钥 + 名字 + 有效期 + 用途 + CA 的签名 |
| 本人 | release-2 私钥（05 号），真正签更新包 |
| 酒店前台：不认识你，但认识公安局的章 | 设备：不认识 release-2，但预装了 CA 的证书 |
| 身份证过期/挂失 → 补办一张，前台不用改任何东西 | release-1 泄露 → 吊销 + CA 签 release-2，设备什么都不用改 |

设备验一个更新包要做两次签名验证：
1. 用预装的 **CA 公钥**验 release-2 **证书**上的签名 → 证书是真的，里面的 release-2 公钥可信
2. 用证书里的 **release-2 公钥**验**更新包**的签名 → 包没被改过，是 release-2 签的

**两处纠正**：
- "证书会更新"更准确的说法：**签名钥匙可以换，设备信任的 CA 不变**。证书是换钥匙时的"介绍信"。
- HSM 里的 01–05 **全都是签名钥匙，没有一把是用来加密的**。签 boot.img、签证书、签更新包——都是"盖章"（防改 + 证明是谁），
  不是"变乱码"。项目里真正的加密只有 p7 的 LUKS，它的密钥不在 HSM 里，在设备上。

## 14. 第 2 课：secure boot（修 F4）📖

文档：`security-zh/secure-boot.zh.md`。启动顺序、信任根、反签在 §3、§7 已讲，这里只讲新东西。

### 第 2 课一页总结

第 2 课就三件事：**OTP 是什么**（14.0、14.0b、14.2）、**secure boot 的完整流程**（下图）、
**我们做到哪、差什么、为什么不烧**（14.3–14.6）。

```
【出厂 / 产线，只做一次】
  HSM 里的 01 号私钥 ──► 对应的公钥 ──► 算指纹 ──► 烧进 OTP（program_pubkey=1，不可逆）   ← 我们没做
  公钥本身写进 EEPROM；bootloader 用 01 号私钥反签

【每次构建发布】
  boot.img（内核 + initramfs(含根哈希) + 设备树 + config/cmdline）──► HSM 签名 ──► boot.sig
  两个一起写进 p2/p3

【每次开机】
  ① BootROM：SHA-256(EEPROM 里的公钥) == OTP 里的指纹？  → 否：停
             用这把公钥验 bootloader 上我们的反签            → 否：停
  ② bootloader：用同一把公钥验 boot.sig 和 boot.img      → 否：不从这里启动
  ③ 内核（从 boot.img 里取出）：用根哈希 + dm-verity 挂 p5，读到哪块验哪块 → 不对：I/O 错误 / 重启回退
  ④ 系统：p5 里的 Update CA 证书之后验更新包；p7 解密 …
```

OTP 空着时，①② 的检查不强制——签名都在，但没人查（我们的板子现在的状态）。

### 14.0 重讲：secure boot 和 OTP 是什么关系 ✅（Q72）

第一遍直接从细节讲起，用户没跟上（"secure boot 还有 OTP 都是怎么回事，是其中一部分吗"）。重讲：

**secure boot 是一整套机制，OTP 是这套机制里的一个零件。**

- **secure boot（安全启动）= 一个目标**：开机时**只运行我们签过名的软件**，别人改过的一律不跑。
  做法就是第 3 节的接力：每一棒交棒前，先检查下一棒的签名。
- **OTP = 芯片里一小块只能写一次的存储**（烧断熔丝，写了就改不回来）。它在这套机制里只干一件事：
  **记住"该信哪把钥匙"**。

比喻：公司大楼门禁。

| 门禁 | secure boot |
| --- | --- |
| 保安 | BootROM（芯片里出厂就刻死的程序，第一个运行） |
| 每个人的工牌上盖着章 | 每一级软件（bootloader、boot.img）都带着签名 |
| 保安要知道"真章长什么样"才能验 | BootROM 要知道"我们的公钥是哪把"才能验签名 |
| **墙上刻着真章的样子，刻上去就擦不掉** | **OTP 里烧着我们公钥的指纹** |
| 墙上什么都没刻 → 保安没法验 → **谁都放进来** | OTP 空着 → BootROM 不知道该信谁 → **不检查，什么都放行** |

所以：**烧 OTP = 把"我们的钥匙"刻进芯片，同时把 secure boot 的检查打开，而且永远关不掉。**

我们的板子：签名全都做了（每一级都带着章），但 OTP 空着（墙上没刻）→ 保安不检查 →
**secure boot 实际上没生效**。不烧是因为不可逆：烧了以后这块板子只能跑我们签过的东西，自编实验内核也得签，钥匙丢了板子就废了。

物理位置（再看一眼第 3.1 节）：

```
BCM2712 主芯片 ┬ BootROM（保安，出厂刻死）
               └ OTP（墙，烧一次就定了）  ← 我们的板子：客户钥匙那几行还是空的
板上 EEPROM    ─ bootloader（第二棒）
SD 卡          ─ boot.img + boot.sig（第三棒）→ 内核 → p5
```

### 14.0b 纠正："所有验证都用 OTP 里的公钥"？✅（Q72、Q73）

用户的理解："签名、指纹、加密，都得有东西去验证或解密，这个东西就是刻在 OTP 里的公钥；解密用的钥匙也是它？"
**一半对**。对的是：**所有验证最终都追溯到 OTP**。不对的有三处：

**1. OTP 只直接验第一环，后面每一环用的是上一环交下来的依据**（信任链，Q59）：

| 谁验谁 | 用什么验 | 这个依据放在哪 | 它为什么可信 |
| --- | --- | --- | --- |
| BootROM 验 bootloader / boot.img | 我们的公钥 | EEPROM 里 | 哈希和 **OTP** 对得上 |
| 内核验 p5 每一块 | 根哈希（不用钥匙） | boot.img 里 | boot.img 被上一行验过 |
| RAUC 验更新包 | Update CA 证书 | p5 里 | p5 被上一行验过 |
| Pi 验 MCU | 共享密钥 K（HMAC） | p7 里 | p7 由 LUKS 加密保护 |

像多米诺骨牌倒着看：只有第一块钉在 OTP 上，其余每块靠前一块撑着。**直接用 OTP 的只有第一环，但每一环最终都挂在它上面。**

**2. OTP 里存的是公钥的指纹（哈希），不是公钥本身**——公钥太大（294 字节），放在 EEPROM；OTP 里 32 字节的指纹负责确认"EEPROM 里这把是真的"。

**3. 解密用的不是这把，也不可能是它**：
- **公钥只能验签名，不能解密**，它是公开的——谁都有的东西解不开秘密。
- p7 的 LUKS 用的是**对称密钥**（卷密钥），由口令打开钥匙盒得到（§11）。
- OTP 里**另外**可以放一把**设备私钥**（保密的），设计上用它派生 LUKS 口令（§11.2d）。我们也没烧。

| OTP 里的两样东西 | 公开还是保密 | 干什么 | 我们烧了吗 |
| --- | --- | --- | --- |
| 客户公钥的指纹 | 公开 | secure boot：确认该信哪把钥匙 → **验签名（防改）** | 没有 |
| 设备私钥 | 保密，读不出来 | 派生 LUKS 口令 → **解密 p7（防看）** | 没有 |

同一块 OTP，两件互不相干的事——和"完整性 vs 机密性是两回事"（Q49）对应。

### 14.1 实测：真实的 1.2.2 boot.img

```
boot.sig:   7edeb3e6…a57c            ← SHA-256(boot.img)
            ts: 1790274981
            rsa2048: 2151d108cc70…   ← HSM 01 号钥匙做的签名

rpi-eeprom-digest -k public.pem -i boot.img -v boot.sig     → Verified OK
在偏移 100000 改 1 个字节后                                 → Verification failure

签名主机审计日志（pkcs11-hsm-wrapper 每签一次记一行）:
2026-09-24T20:36:21+02:00 orbis sha256=7edeb3e6…a57c        ← 就是这个 boot.img
```

bootloader 在板子上做的就是第二行那件事——前提是 OTP 烧了（它才会**强制**做）。

### 14.2 OTP 里存的是公钥的**哈希**，不是公钥

```
EEPROM（可重刷）:  完整公钥，RSA-2048，294 字节
OTP（只能写一次）: SHA-256(公钥)，32 字节
BootROM:           SHA-256(EEPROM 里的公钥) == OTP 里的值？ 相等才用这把公钥验签
```

- 为什么：OTP 很小、只能写一次；公钥放 EEPROM，OTP 只"钉住"是哪一把。
- 攻击者把 EEPROM 里的公钥换成自己的 → 哈希对不上 OTP → 拒绝。要找一把哈希恰好相等的钥匙 = 碰撞，做不到。
- 这就是 Q47 那句话的最终形态：**参照值要放在攻击者改不了的地方**——最终那个地方是 OTP 熔丝。
  32 字节的熔丝保护一把公钥，公钥保护 boot.img，boot.img 里的根哈希保护 p5（原则 4：把要保护的东西缩到最小）。

### 14.3 在 Pi 5 上能测什么、不能测什么

- Pi 4 可以先刷签名 EEPROM 试，再烧 OTP；**Pi 5 不行**：OTP 没烧，签名的 EEPROM 镜像根本不运行，板子起不来。
  所以 Pi 5 没有"强制验签但还能撤回"的测试模式。
- **能测的**：签名的 boot.img 格式对、内容全、能把整台设备启动起来（`boot_ramdisk=1`）。
- **测不了的**：被改过的 boot.img **会被拒绝**——没烧 OTP 时固件不检查签名，改过的照样启动。
- 文档里把这两句分开写：证明了什么、没证明什么。不把"能启动"说成"secure boot 生效了"。

### 14.4 调试故事：tryboot 启动签名 ramdisk（面试可讲）

用一次性 tryboot 试，失败了断电重启就回到原系统。三次：

1. 重启后没网络，没控制台，**猜**是缺 D0 步进的 overlay。加上，没变化——猜错了。
2. 接 HDMI 屏幕看 bootloader 输出：`Loading tryboot.img ... Error 6`。**tryboot 模式加载的是 `tryboot.img` 不是 `boot.img`**。
   文档有写，但在 autoboot 那一页，不在 secure boot 那一页。
3. 改名后**启动成功**，`/proc/cmdline` 里有标记 `bootimg=signed-test`——但 `device-service` 卡住：`spi0.0` 不存在，
   **所有 dtoverlay 都没生效**。原因：tryboot 模式下固件读 ramdisk 里的 `tryboot.txt`，而 ramdisk 里只有 `config.txt`。
   放一份副本进去 → SPI 出现、MCU 应答 `0xac00acc0`。

教训：第 3 次是更危险的那一类——**系统起来了、看起来健康，只是某个外设悄悄没了**（原则 17：读回验证）。
先拿到证据（屏幕输出）再改，别凭猜（项目的调试习惯：先怀疑环境/配置）。

### 14.5 为什么不烧，以及烧之前必须检查什么

烧 `program_pubkey=1` 之后：只有我们签的 bootloader 和 boot.img 能跑；**不能撤销，也不能换钥匙**。
项目只有一块 Pi 5，还要跑自编的实验内核 → 烧了这块板子上其他实验就结束了。

烧之前最要紧的几条（完整清单在文档 §5）：

| 检查 | 为什么 | 状态 |
| --- | --- | --- |
| EEPROM 镜像里公钥的哈希 == 要烧的值（`fe0144747838fcf8…`） | 烧错了，板子永远只认错的钥匙 | ✅ |
| 签名的 boot.img 在目标板上能启动 | 烧完起不来 = 变砖 | ✅（14.4） |
| **01 号私钥有备份** | 私钥丢了，所有锁定的设备**永远无法再更新**；这正是真 HSM 存在的意义（备份/克隆） | ⬜（SoftHSM 替代） |
| 开发钥匙和产线钥匙分开 | 开发钥匙管得松，不能让它能给出厂设备签名 | ⬜ |
| 有反签过的 `recovery.bin` | 锁定后这是 bootloader 唯一的救砖途径 | ⬜ |
| 先锁一块板，跑通完整的更新和回滚，再锁更多 | | ⬜ |

注意 01 号和 13.4 的对比：更新钥匙有 CA 这一层，可以轮换、吊销；**boot 钥匙直接钉在熔丝里，丢了和漏了都没救**。

### 14.6 回到威胁模型：F4 现在是什么状态

- 做完的：签名 boot.img（A/B 两个槽、每个更新包里都是）、根哈希在签名内核里、dm-verity、反签 EEPROM 镜像、HSM 签名 + 审计日志。
- 差的：**第一环"固件强制验签"**。所以**在这块板子上**，拿着 SD 卡的 A2 仍然能换掉 boot.img（连带换掉根哈希）→ 后面全部失效。
  dm-verity 现在能发现**损坏**，发现不了**攻击者**（Q47）。
- 面试讲法：**软件这边每一环都做了并验证了，唯独信任根是模拟的——因为那一步不可逆，而且我能说清楚烧之前要检查什么。**

## 15. 第 3 课：完整性与加密（修 F5、F7、F8）📖

文档：`security-zh/integrity-and-encryption.zh.md`。原理在第 0 课讲过（dm-verity 5.3、dm-integrity 8.3、LUKS §11），
这一课回答三个问题：**卡上被改了一个字节，设备怎么发现？发现之后怎么办？代价多少？**

### 15.1 p5 被改：实测（case-10，`results/security/dm-verity/on-target-tamper-demo.txt`）

```
挑一个开机从来不用的文件：btrfs.ko.xz，sha256 1b441078…
它在卡上的位置：p2 + 77180928 字节，原值 0x13     （当时是早期的 verity 镜像，根分区在 p2；A/B 镜像里是 p5）

1. root 直接往底下的原始分区写 0xff（绕过 dm-verity）
2. 通过 / 读这个文件：
   sha256sum: can't read '.../btrfs.ko.xz': Input/output error
   内核: device-mapper: verity: 179:2: data block 75372 is corrupted      ← 77180928 / 1024 = 75372，和预先算的一致
3. 把 0x13 写回去 → 文件又能读了，sha256 还是 1b441078…
```

- **ext4 自己发现不了**（主机上的演示：普通挂载会照常交出被改过的程序）。发现的是 dm-verity，**在读到那一块的那一刻**。
- **它没有记忆**：改回去就又合法了。它只回答"这一块现在对不对"。
- 为什么挑不用的文件：改的是系统正在用的东西，结果就是下一节。

### 15.2 发现之后怎么办：新内容 ✅（Q74）

dm-verity 发现坏块有几种反应（出错模式），写在内核命令行上（签名的 boot.img 里）：

| 模式 | 反应 | 问题 |
| --- | --- | --- |
| 默认（EIO） | 这一次读取失败，系统继续跑 | 系统半残地活着：某个程序打不开、某个功能悄悄没了 |
| `restart_on_corruption`（我们从 1.1.0 起用的） | **立刻重启** | 单独用更糟：坏的是正在用的槽 → 重启还是它 → **无限重启** |

**重启只有和 A/B 配合才对**，针对的场景是"一次更新装进了坏的/被篡改的内容"：

```
新版本装进 A，还没"确认"（commit），只用一次性 tryboot 启动 A
  → A 里有坏块 → 读到就重启
  → tryboot 是一次性的，已经用掉 → 固件启动上一次确认过的 B
  → 设备回到旧的好系统，A 永远不会被确认
```

实测（1.1.0，`on-target-signed-ab.txt`）：在主机上算出 systemd（PID 1，开机必读）第一个块在卡上的位置，
改 1 个字节，tryboot 进 A → **14 秒后设备又在 B 上跑了**。没用到健康检查、看门狗、网络——内核自己就完成了。

**证据问题**：重启了，怎么知道是因为 verity？失败那次的日志只在内存里活了几秒。
→ 加 **pstore/ramoops**：内存里留 256 KiB，重启不清空，下次开机从 `/sys/fs/pstore` 读出上一次的内核日志：

```
[4.905102] device-mapper: verity: 179:5: data block 61755 is corrupted     ← 主机上预测的就是 61755
[4.939623] reboot: Restarting system with command 'dm-verity device corrupted'
```

**局限（写明，没解决）**：如果坏的是**已经确认过**的槽（比如卡慢慢老化），还是会无限重启。
要打破需要固件级的启动计数器（Pi 5 bootloader 目前没有），或 panic + 恢复分区。

### 15.3 p7 被改：LUKS + dm-integrity（`luks2-integrity-tamper.txt`）

```
在原始分区 p7 上改 1 个字节（fe → ff）
读 → dd: Input/output error
     device-mapper: crypt: INTEGRITY AEAD ERROR, sector 1687560
改回去 → 又能读
```

没有 dm-integrity 时同样的改动不会报错，只会解出一块乱码（10.2 的实验）。
局限：dm-integrity 按扇区号认证、不带版本号 → **把一个旧扇区连同旧标签原样写回，能通过**（回放，6.2）。防回放需要计数器（OP-TEE 课）。

### 15.4 代价（Pi 5 实测，每项 3 次）

| | 读 | 写 |
| --- | --- | --- |
| 原始 SD 卡 | 85 MiB/s | 30–43 MiB/s |
| dm-verity（p5） | **−16%** | 只读，不写 |
| LUKS 只加密 | **−7%**（CPU 有 AES 硬件指令） | ≈ 不变 |
| LUKS + integrity（p7） | **−24%** | **≈ −50%** |

- 写慢一半：dm-integrity 默认**每个扇区写两次**（先写日志），保证突然断电时数据和标签不会对不上。
  设备会毫无预警地断电，所以宁可慢一半。——**用速度换断电安全，是有意的选择。**
- 瓶颈是 SD 卡本身（约 83 MiB/s），这些数字是"在这种存储上"的代价。
- verity 从 −27% 降到 −16%：把 SHA-256 的硬件加速编进内核而不是做成模块——verity 在 initramfs 里建立，那时模块还加载不了。

### 15.2b tryboot 是什么 ✅（Q75）

**是树莓派固件（bootloader）自带的一个功能，不是我们写的脚本**：
"**下一次开机，按另一套配置启动一次；只此一次。**"

- 触发：`reboot "0 tryboot"` → 在一个重启后还保留、但断电就清零的寄存器里记一个标志。
- bootloader 看到标志 → 这次用 tryboot 那套配置 → 标志**自动清掉**。
- 再重启一次（或断电）→ 回到正常配置。

真实的 p1 `autoboot.txt`（1.2.2 镜像，`mtype` 读出）：

```
[all]
tryboot_a_b=1
boot_partition=2        ← 平时：从 p2（A 槽）启动
[tryboot]
boot_partition=3        ← 带着 tryboot 标志的那一次：从 p3（B 槽）启动
```

A/B 更新就是靠它（下一课细讲）：
1. 新版本写进空闲的槽（比如 B）
2. `reboot "0 tryboot"` → 这一次从 B 启动
3. B 起来了、健康检查通过 → **提交**（commit）：把 `[all]` 下面改成 `boot_partition=3`，B 成为以后的默认
4. B 起不来 / 半路重启 → 标志已经用掉 → 下一次自动回到 `[all]` 里的 A

所以 15.2 的"重启"配合 tryboot 才有出路：**坏的新版本只有一次机会，重启 = 自动回到旧的好版本**。

### 15.5 两个"构建成功但没生效"（原则 17）

- 重启模式的脚本差点没进镜像：另一个层的同名文件优先级更高，把我们的覆盖了。构建成功，只有解开 initramfs 才看出来。
- ramoops 用通用 overlay 时，`dtoverlay=ramoops` 被接受、**静默无效**：没有节点、没有 pstore。只有读回 `/proc/device-tree` 才发现，最后写了 Pi 5 专用的 overlay。

## 16. 第 4 课：更新与密钥管理（修 F6、F14）📖

### 16.1 A/B 的好处（用户自己猜对了）✅（Q76）

| 好处 | 说明 |
| --- | --- |
| 不变砖 | 更新只写没在用的槽；中途断电、写坏，坏的只是空闲槽，正在用的一直完好 |
| 能回退 | 新版本起不来/不健康 → 不确认 → 自动回到旧槽（tryboot，15.2b） |
| 停机时间短 | 在系统运行时写空闲槽，只需要重启一次 |
| 代价 | 存储翻倍：p2/p3、p5/p6 各两份 |

对比：只有一套系统时，更新 = 在正在用的系统上改，断电就半新半旧，设备变砖，只能派人去现场。
对一台装在客户那里、没人管的设备，这是生死问题——所以威胁模型说 F6"没有更新机制 → 其他所有问题在现场都是**永久的**"。

补充 Q75 的一个细节：**试启动成功也只是这一次**。不确认（commit）的话，下次重启还是回到旧槽。
确认 = 改写 p1 `autoboot.txt` 的 `[all]`，只有健康检查通过才做。

### 16.2 一个更新包的一生 📖

文档：`security-zh/update-and-provisioning.zh.md` §2–3。工具：**RAUC**（开源的嵌入式 Linux 更新器，
同类还有 SWUpdate、Mender、OSTree）。更新包 = `.raucb` 文件，里面是新的 boot.img + rootfs 镜像 + 一张清单（manifest）+ 签名。

```
【厂家这边】
 ① 构建服务器（bitbake）出包，用**开发钥匙**签              ← 构建服务器碰不到正式钥匙
 ② 签名主机：先验开发签名 → 用 HSM 里的 release 钥匙重签 → 记审计日志
       （只肯给"构建出来的东西"签，不给随便递过来的东西签）

【设备这边】
 ③ rauc install：用 p5 里的 Update CA 验签名 + 证书（13 节）          ← 不对：直接拒绝
                  检查版本号 ≥ min-bundle-version（16.3 防回滚）
 ④ 写进**空闲**的那一对槽（比如 p3 + p6），正在用的 A 不动
 ⑤ reboot "0 tryboot" → 这一次从 B 启动
 ⑥ 健康检查：device-service 在跑 **且 MCU 应答**（MCU 认证不过，服务不起，检查就不过——fail closed）
      过 → rauc mark-good → 改 autoboot.txt 的 [all] = 3 → B 成为默认（确认 / commit）
      不过 / 起不来 / verity 重启 → 什么都不改 → 下次重启自动回 A（回退 / rollback）
```

板上实测（`results/security/update/on-target-ab.txt`）：

| 测试 | 结果 |
| --- | --- |
| 正常更新 1.0.2 装进 B | 装约 15 秒 → tryboot 进 B → 开机 30 秒健康检查 → `marked slot(s) rootfs.1 as good` → `autoboot.txt: [all] boot_partition=3` |
| **失败的更新**（B 里的镜像 SSH 起不来） | 设备不可用 → **断电一次 → 回到 A**，autoboot.txt 从没改过 |
| 装旧版本 0.9.0 | `Version mismatch: Expected at least '1.0.0' but bundle manifest has '0.9.0'` |

失败的那次不是故意的：那个包来自一个有真实 bug 的旧镜像——**设计要防的情况，真的发生了一次，也真的救回来了**。

板上才发现的坑（原则 17 又一次）：**健康检查从来没运行过**——systemd 的启动顺序绕成了一个环，
systemd 为了打破环每次开机都把它丢掉，只留下一行日志。失败方向是安全的（什么都没确认），但"确认的那道门"根本不存在。
另外，meta-rauc 自带的 `rauc-mark-good` 会**无条件**把每个启动过的槽标成 good——被我们去掉了，否则回退永远不会发生。

### 16.3 防回滚：旧版本也是合法签名的 ✅（Q77，只含更新器那一半；SD 卡那一半用户暂不深究）

**问题**：去年的 1.0.0 有个漏洞，今年修了。但 1.0.0 当时也是我们签的名——签名到今天照样有效。
攻击者把 1.0.0 装回去，就能利用去年的漏洞。**签名只证明"是我们发的"，不证明"是最新的"**（原则 10，和 nonce 防回放是同一个问题：新鲜性）。

**对策分两层，看攻击者从哪进来**：

| 攻击者 | 怎么装旧版本 | 我们的防护 | 状态 |
| --- | --- | --- | --- |
| 通过更新器（远程/本地调 rauc） | `rauc install old.raucb` | `system.conf` 里的 `min-bundle-version`：每个新版本都把下限抬高，旧的装不上 | ✅ 板上验证 |
| 拿着 SD 卡的人 | 不走更新器，直接把旧的整盘镜像 `dd` 到卡上 | 需要一个**他改不了的计数器**：OTP 位（每个版本多烧一位）、eMMC 的 RPMB、TPM | ⬜ Pi 5 的 SD 卡没有 RPMB，OTP 没烧 |

- 下限写在 p5 的 `system.conf` 里——p5 被 dm-verity 保护，所以只要当前系统可信，这个下限就可信。
- 但下限本身在**可重写的存储**上：拿着卡的人把整张卡换成旧的，下限也跟着变回旧的。
  → **任何靠"可重写存储"执行的规则，都能靠回滚那份存储来撤销。** 计数器必须在物理上只能往上走（OTP 熔丝只能 0→1）。
- 两个注意：真的要退回旧功能时，要把旧内容**用新版本号**重新发布；RAUC 的 D-Bus 接口有 `ignore-version-limit` 选项，
  所以必须限制谁能调它，否则 root 可以直接跳过检查。

### 16.3b 用户的好问题："OTP 只能烧一次，那以后发新版本怎么办？" 📖

用户的推理："出厂烧了'最低版本 2'，后来发了 3、4、5，别人拿着版本 2 的卡照样能过 OTP 检查"——
**如果 OTP 真的是整块只能写一次，这个推理完全正确。** 关键在于：**"只能写一次"是按"位"算的，不是按整块 OTP 算的。**

- OTP 是很多行，每行 32 个位；**每一位**都能从 0 烧成 1，一次，不能改回 0。没烧的位以后还能烧。
- 防回滚计数器 = 专门拿一行，**烧了几个 1 就代表版本几**（温度计式）：

```
出厂        0000 0000 0000 0011    ← 版本 2
装上 v3 后  0000 0000 0000 0111    ← 设备在确认 v3 之后，自己再烧一位
装上 v5 后  0000 0000 0001 1111    ← 版本 5
```

- 启动时，验证者（固件）读出"烧了几位" = 允许的最低版本；镜像里带着自己的版本号（**在签名覆盖的范围里**，改不了）；
  镜像版本 < 计数器 → 拒绝。拿着 v2 的卡 → 2 < 5 → 起不来。
- 攻击者要想"退回"，得把 1 变回 0 → 物理上做不到。**这就是为什么计数器只能放在 OTP 这种地方。**

代价和实际做法：
- 位数有限（一行 32 位，最多记 32 次）→ 只在**修了安全漏洞**的版本才加一，这个数叫**安全版本号**（SVN），
  和给人看的版本号（1.2.2）分开。
- 烧的时机：新版本**确认**之后再烧（没确认就烧，新版本一坏，就回不去旧的了）。
- 检查必须由**攻击者绕不过的那一环**做：固件/bootloader，而不是被替换掉的系统自己。
  TF-A 就是这样做的（证书里的计数器 vs 熔丝里的计数器，14 节表格）；**Pi 5 固件目前没有给 boot.img 用的通用计数器**，
  所以这是文档里写明的缺口，不是我们做完了。
- 和 secure boot 的公钥指纹是**不同的行**：那几行出厂烧一次就定了；计数器那一行是一点点往上烧的。

### 16.3c 追问：能不能更新确认后，由软件自动烧一位？📖

**能，而且业界就是这么做的**（Android Verified Boot 的 rollback index、TF-A 的 NV counter 都是"启动成功后由可信的一环往上推"）。
树莓派提供了从 Linux 写"客户 OTP 行"的固件接口（`vcmailbox` 的 set-customer-OTP 调用，8 行 × 32 位）。

但要回答三个问题，否则白烧：

1. **谁来检查？** 烧了没人查等于没烧。Pi 5 固件不查 → 检查只能放在**签名的 boot.img 里的 initramfs**：
   开机读 OTP 计数器，和 initramfs 自己带的安全版本号比，小于就拒绝继续启动。
   妙处：**旧版本 v2 的 initramfs 也是签过名的、带着这段检查**，它会诚实地拒绝自己（2 < 5）；攻击者改不了它（签名）。
   前提：从第一个版本起每个版本都带这段检查 + secure boot 生效（OTP 公钥指纹烧了）。
2. **谁能烧？** 如果 Linux 里的 root 都能烧，攻击者拿到 root 就能**把剩下的位全烧满** → 所有现有版本都被拒 → 设备变砖。
   烧不会让系统"退回"，但能用来**搞瘫**（攻击可用性）。所以烧的权限要收紧（只在确认流程里、由可信组件做；有条件的平台放进 TEE）。
3. **什么时候烧？** 新版本**确认之后**（健康检查过了）才烧；而且只在安全版本号真的变了时烧（位数有限）。

一句话：**软件可以往上推计数器，但"推"的权限和"查"的位置，决定了它是防回滚还是新的攻击面。**

（产线烧录 / provisioning 依赖设备身份，挪到第 5 课 OP-TEE 一起讲。）

## 17. 第 5 课：OP-TEE 和设备身份（修 F12）✅（Q78，上半段）

文档：`security-zh/optee.zh.md`。代码：`security/optee-ta/device_identity/`。全新内容，分两段讲：
上半段（本节 17.1–17.4）= 它是什么、我们的 TA 做了什么；下半段 = 存储回滚 / RPMB、产线烧录、真硬件的区别。

### 第 5 课一页总结（用户说"太乱、没有系统认识"后重讲）✅（Q79）

**整课只有一条故事线，五步：**

```
① 问题   后台收到数据，怎么知道是"我们发出去的那台设备"发的？（F12）
            ↓ 需要
② 身份   设备里有一把只属于它的私钥；后台发随机数，设备签名，后台用公钥验
            ↓ 私钥放哪才偷不走？
③ TEE    CPU 里的安全区：私钥在里面生成、在里面签名，Linux（连内核）都拿不到
            ↓ 但 TEE 没有硬盘
④ 缺口   私钥加密后存成 Linux 上的文件：Linux 看不懂、改不了，但能"换回旧的"
         → 设备以为自己从没有过身份 → 生成第二个身份
            ↓ 补
⑤ RPMB   闪存里一个只能往上加的计数器，记住"现在是第几版"，旧的放回来就被发现
         （Pi 5 用 SD 卡，没有 RPMB → 写明的缺口）

另外一条支线：公钥怎么让后台认识？
   产线工站：让 TA 生成身份 → 拿公钥 → Device CA 签发证书（设备的身份证）→ 后台凭证书认设备
```

一句话：**TEE 给设备一个偷不走的身份；它唯一的弱点是存储能被回滚，要靠 RPMB 补；产线用证书把这个身份登记到后台。**

### 17.1 先回答：为什么需要它——还是"密钥放哪"

F12：设备没法向后台证明"我是哪一台"。要证明身份就得有一把**只属于这台设备的私钥**（原则 3：要证明有秘密，就得真的有）。
这把私钥放哪？把前面见过的地方排一排：

| 放在哪 | 谁能偷走 |
| --- | --- |
| 普通文件（p7 里） | 设备上拿到 root 的人 |
| Pi 的 OTP + 固件服务（`rpi-fw-crypto`） | root 挡住了；**攻破内核的人**能直接读 OTP（Pi 文档原话） |
| 外接安全芯片（ATECC608） | 几乎没人——但要多一颗芯片 |
| **TEE（可信执行环境）** | **连攻破了 Linux 内核的人也拿不到** —— 在同一颗 CPU 上，不用加芯片 |

### 17.2 TEE 是什么：同一颗 CPU，两个世界

**比喻：银行柜台。** 你（Linux）站在玻璃外面，把单子从窗口递进去；柜员（TA）在玻璃后面用保险箱里的章盖好递出来。
你能让柜员**用**章，但永远**看不到、拿不到**章。——和 HSM 一样的思路（8.8），只是这个"保险箱"在设备自己的 CPU 里。

- **TrustZone**：ARM CPU 的硬件功能。CPU 可以运行在**普通世界**或**安全世界**；内存可以标成"安全"，
  普通世界（包括 Linux 内核）去读，**总线硬件直接拒绝**。不是软件规则，是电路。
- **OP-TEE**：跑在安全世界里的一个开源小操作系统。
- **TA（trusted application，可信应用）**：跑在 OP-TEE 上的小程序。我们写了一个：`device_identity`。
- **怎么调用**：Linux 里的程序 `devid` → Linux 的 TEE 驱动 → 一条特殊指令（SMC）→ TF-A 里的"安全监控器"切换世界
  → OP-TEE → TA → 结果原路返回。和 14 节表格里 TF-A 的 BL31/BL32 是同一套东西：BL32 就是 OP-TEE。

**为什么在 QEMU 上跑**：OP-TEE 没有维护中的 Pi 5 移植。所以在 OP-TEE 官方的开发环境——QEMU 模拟的 Armv8 机器——上做，
先跑它自带的测试：`xtest: 143 test cases of which 0 failed`。依赖真硬件的部分单独列出来（下半段）。

### 17.3 我们的 TA：三个命令

| 命令 | 做什么 |
| --- | --- |
| `PROVISION` | **在 TA 里面**生成一对 P-256 钥匙，私钥标记为"只能签名、不可导出"，存起来，只把**公钥**交出来。已经有了就拒绝 |
| `GET_PUBKEY` | 交出公钥 |
| `SIGN_CHALLENGE` | 签 `SHA-256("device-platform/devid-challenge/v1" ‖ nonce)`，nonce 必须 16–64 字节 |

和 MCU 认证（6.3）是同一个挑战-应答，区别：MCU 用 HMAC（双方共享 K），这里用**签名**——后台只需要公钥，
后台被黑也造不出设备的回答（12.3）。

固定前缀 `"device-platform/devid-challenge/v1"` = 域分隔（原则 11）：Linux 里的 root **能调用** TA，
所以 root 能用它证明"我是这台设备"——但 TA 只签"带这个前缀的挑战"，root 没法借它去签一个更新包、一张证书，或任何别的东西。

### 17.4 实测（`results/security/optee/demo.txt`、`verifier.txt`）

```
1. 还没生成就要公钥      devid: pubkey: 0xffff0008            ITEM_NOT_FOUND
2. provision             PUB=04063dbc84f231ea…dec9            ← 私钥在 TA 里生成，出来的只有公钥
3. 再 provision 一次     0xffff0003                           ACCESS_CONFLICT，拒绝换身份
4. 签后台给的 nonce      verify (correct nonce): VALID
                         verify (other nonce):   INVALID      ← 换个 nonce 就不对，防回放
5. nonce 只有 8 字节     0xffff0006                           BAD_PARAMETERS
6. TA 自己去读私钥       0xffff3024 (TA panicked: key is not extractable)
7. TA 被杀后重新加载     PUB2=04063dbc…dec9                   ← 同一把，还在
```

第 6 步最关键：**连 TA 自己都读不出私钥**——一读，OP-TEE 内核直接把 TA 杀掉（GlobalPlatform 标准规定的）。
这是 TEE 的内核强制的，不是靠 TA 自觉。原则 2："证明你有秘密，但永远不交出秘密"——在这里是被硬性执行的。

### 17.5 下半段：私钥"永远不出来"，那它存在哪？📖

**存在 Linux 文件系统上的普通文件里**——加密的。

```
ls -l /var/lib/tee/            （实测：37 个文件，属主 tee，权限 0600）
-rw-------  1 tee tee 16384  0
-rw-------  1 tee tee 16384  1
hexdump dirf.db:  f8 f2 f1 1a df 2e ed 40 …    ← 密文，看不懂
```

- 安全世界自己没有硬盘，存东西要**托普通世界代劳**：OP-TEE 把加密好的数据交给 Linux 里的 `tee-supplicant` 进程写成文件。
- 加密和完整性用的钥匙，由**硬件唯一密钥 HUK** 派生——HUK 烧在芯片熔丝里，**只有安全世界能读**。
  所以 Linux 拿到文件也解不开、改了会被发现。（又是 11.2d 的思路：用一把硬件里的秘密派生出真正用的钥匙。）
- 诚实：QEMU 上 HUK 是**全零常量**，拿到文件 + OP-TEE 源码就能解开。真芯片上才是熔丝。

**但 Linux 能做的不止"读"——它能删、能改、能回滚这些文件。** 加密挡住了看，MAC 挡住了改，挡不住**换回旧的**。

### 17.6 回滚实验：生成了第二个身份

```
第 2 步之前：先把 /var/lib/tee 整个复制一份（那时还没有身份）
第 2 步：    provision → 身份 04063dbc…
第 9 步：    把旧副本放回去
             devid pubkey    → ITEM_NOT_FOUND        ← OP-TEE 认为"从来没生成过"
             devid provision → 0442af90…              ← 第二个、不同的身份！
```

"只能 provision 一次"（第 3 步）的规则被绕过了：规则靠的是"存储里已经有一把钥匙"，而存储被换回了"还没有钥匙"的时候。
OP-TEE 开机时自己就警告了：

```
I/TC: WARNING (insecure configuration): Failed to get monotonic counter for REE FS, using 0
```

意思：每个文件都加密、认证了，但**没有一个 Linux 改不了的地方记着"现在是第几版"**——和 dm-integrity 防不了回放旧扇区（15.3）、
`min-bundle-version` 挡不住换整张卡（16.3）是**同一个问题**：

> **任何靠"可重写存储"执行的规则，都能靠回滚那份存储来撤销。** 需要一个只能往上走的计数器。

### 17.7 RPMB：那个"只能往上走的计数器"

**RPMB**（Replay Protected Memory Block，防回放存储块）= eMMC 闪存芯片里一块特殊的小分区：
- 里面有个**写计数器**，每写一次加一，由闪存芯片自己维护，谁都减不了；
- 写入要用一把**认证密钥**（只有安全世界有），Linux 写不进去。

OP-TEE 把"目录文件的哈希"存进 RPMB。旧副本放回去 → 哈希对不上 RPMB 里的 → 拒绝。

用**模拟的** RPMB 重跑同一个实验（`results/security/optee/rpmb-emulated/`）：

| | 只有普通文件 | 加上 RPMB（模拟） |
| --- | --- | --- |
| 开机日志 | `Failed to get monotonic counter` | 警告消失：`RPMB: Using test key`… `Found working RPMB device` |
| 第 9 步把旧副本放回去 | 接受，**生成第二个身份** | **拒绝**：`TEEC_OpenSession: 0xf0100001`（CORRUPT_OBJECT） |

- **失败即关闭**（原则 14）：攻击者拿不到第二个身份，但设备也**失去了自己的身份**和安全存储里的一切，要重新 provision。
  发现攻击 → 变成拒绝服务。和"每个文件改一个字节 → CORRUPT_OBJECT"（第 10 步）是同样的取舍：完整性守住了，可用性没守住。
- 诚实三点：这个"RPMB"是 `tee-supplicant`（Linux 里的进程）模拟的，root 重启它就得到一块空白的——所以演示的是**机制**不是**属性**；
  用的是测试密钥；**Pi 5 用 SD 卡，SD 卡根本没有 RPMB**，要 eMMC/UFS。

### 17.8 产线烧录（provisioning）：新设备怎么拿到"身份证"

`tools/provision-device.sh` = 工厂工站。**工站从不碰设备的私钥**：

```
1. 读设备序列号；已经在记录里 → 拒绝（一台设备只发一次）
2. 让设备的 TA 生成身份 → 拿到公钥（设备说"我已经有身份了" → 拒绝：那不是我们发的）
3. 持有证明：发一个新 nonce，让设备签，用它报上来的公钥验
      （防止设备报一把别人的公钥，自己其实没有私钥）
4. HSM 里的 Device CA（02 号）给这把公钥签发证书：subject = 序列号，CA:FALSE，用途 clientAuth
5. 记一行日志：时间、工站、操作员、序列号、公钥指纹、证书指纹
```

之后后台验证设备：设备出示证书 → 后台用 Device CA 验证书（13 节，同一套）→ 用证书里的公钥验设备对 nonce 的签名。
证书 = 设备的身份证，Device CA = 发证的公安局。

测试（对着一个明确标注的软件替身，`results/security/provisioning/station-tests.txt`）：

```
PASS  new device is provisioned and certified            proof of possession: OK
PASS  same serial a second time is refused               already in the provisioning log
PASS  device with an identity we never issued is refused
PASS  device that can't prove possession is refused      the device does not hold the key it reported
PASS  certificate carries the device's key, not the throwaway CSR key
PASS  exactly one log record
```

### 17.9 真硬件上的区别，以及 TEE 防不了什么

| QEMU 上 | 真芯片上 |
| --- | --- |
| HUK 全零 | 熔丝里，只有安全世界能读 |
| 内存隔离是模拟的 | TZASC 硬件把内存区域标成安全，总线拒绝普通世界 |
| 没有 RPMB | eMMC 的 RPMB |
| 没有 secure boot | ROM → BL2 → BL31/BL32(OP-TEE) 一环验一环；**谁能替换 OP-TEE，谁就拥有它的所有钥匙** |

TEE 防不了：TA 或 OP-TEE 自己的 bug；侧信道；启动链被攻破；普通世界对存储的控制（17.6）；
以及"TA 说 valid、但做决定的是普通世界的程序"——**决定在哪做，保护就只到哪**。

## 18. 第 6 课：设备认证（修 F9、F10）✅（Q80）

文档：`security-zh/device-authentication.zh.md`。原理在 6.3、8.6、8.7、8.9、8.10、8.11 讲过。

### 第 6 课一页总结

```
① 问题   Pi 怎么知道 SPI 那头是"我们配对过的那块 MCU"，不是一块说同样协议的克隆板？（F9）
            ↓
② 方案   挑战-应答：Pi 发 16 字节随机数，MCU 用共享密钥 K 算 HMAC，Pi 自己也算一遍比对
         认证不过 → device-service 不启动（一道门）
            ↓ K 放在哪？
③ 缺口   K 在 MCU flash 最后一页；F103 没有安全区，调试器接上就能读（F10）
            ↓
④ 补救   RDP level 1：普通调试器读不出（挡不住读过论文的人，CVE-2020-8004）
         一机一密：抠出一块的 K 只能冒充这一块
            ↓
⑤ 真解法 换硬件：安全芯片（ATECC608）或带 TrustZone-M 的 MCU——和第 5 课 TEE 同一个思路
```

它**防**：换一块克隆板（没有 K 答不对）；录下旧回答重放（每次新 nonce）。
它**不防**：认证通过**之后**有人在 SPI 线中间改数据——那需要每一帧/每一批数据都带 MAC，没做。

### 18.1 实测（`results/security/device-auth/on-target-auth.txt`，固件 v1.4）

```
nonce 6d6da6f4…03d6 -> 38162d44…8954  VALID  wrong-key check: rejected  cycles=35110
nonce 560cff22…d056 -> a7593524…0d45  VALID  wrong-key check: rejected  cycles=35111
…
10/10 valid, answers distinct per nonce: True              ← MCU 空闲
100/100 valid (1000 Hz 采集进行中)
before/after: rearm_fail=0 spi_errors=0 kfifo_overflow=0   ← 认证没有干扰采集
device-service: rate=1000.2/s gap_count=0
```

- 每个 nonce 的回答都不同（防回放）；换一把随机的错钥匙验证都失败（K 真的在起作用）。
- 代价：一次 HMAC 在 72 MHz 的 Cortex-M3 上约 **487 µs**（采集时 561–580 µs，因为被中断抢占）。
- **HMAC 在主循环里算，不在 SPI 中断里算**：case-01/02 的教训——SPI 中断必须在两帧之间的空隙里赶紧重新准备好，
  任何拖慢中断的东西都会丢帧。所以是"认证给采集让路"，上面的计数器全是 0 就是证明。
- MCU 上的 SHA-256 是手写的 C（没有硬件加速、不用库），先在电脑上对照 Python 的 `hashlib/hmac` 测：
  RFC 4231 标准测试向量 + 0–129 字节每种长度，**321 项 0 差异**（原则 15：不自己发明密码学；自己实现就必须用标准向量验证）。

### 18.2 RDP 读保护实测（`rdp-level1-demo.txt`）

| 状态 | 调试器读密钥那一页 |
| --- | --- |
| level 0（默认） | `0x0807f800: 61b413d4 a88f1b26 …` ← 直接读出来，F10 被演示 |
| level 1 | `Failed to read memory`；设备照常认证（要**断电重启**一次才生效，按复位键不够） |
| 从 level 1 降回 0 | **整片擦除**：密钥和固件都变成 `ffffffff`（"降级即擦除"）；用 `pair-mcu.sh` 重新配对（同一 UID → 同一 K） |

局限：F103 的 level 1 有公开的绕过（CVE-2020-8004）；level 2 永久锁死调试口，唯一一块 MCU 不用。

### 18.3 这道门装在哪：`ExecStartPre`，不在驱动里

- 现在：`device-platform-mcu-auth` 作为 `device-service` 的启动前检查（systemd `ExecStartPre=+`），用 BusyBox + `openssl` 命令行：

```
right key : mcu-auth: OK - MCU 0xac00acc0 fw 0x00010400 answered the challenge
random key: mcu-auth: FAIL - wrong answer from MCU (not the paired device, or not paired)
no key    : mcu-auth: FAIL - no pairing key at …
```

- **和第 4 课连起来**：认证失败 → 服务不起 → 健康检查不过 → 更新不确认 → 自动回滚。一个把配对弄坏的更新会自己退回去（原则 14 fail closed）。
- **为什么不挪进内核驱动**（看起来更强）：难点不是代码，是**内核从哪拿到 K**——

| K 从哪来 | 值多少 |
| --- | --- |
| 编译进驱动模块 | 一文不值：模块是 p5 上的文件，每台都一样 |
| 开机时从文件加载进内核 keyring | 和现在一样：秘密还是一个文件，挪动的只是检查的位置 |
| Pi 的 OTP 设备密钥 + 固件 HMAC 派生 | 真正有价值——但要烧 OTP |
| TEE 里的 TA | 正确答案——但 Pi 5 没有 OP-TEE |

  结论：**信任根一样的话，把检查挪进内核只是看起来更强。** 所以不做（决定写进了文档）。
- 另一个限制：检查只在服务启动时做，运行中途换掉 MCU，要到下次服务重启才抓到；两次检查之间的数据只有逐帧 MAC 能保护。

### 18.4 调试插曲（面试可讲）

- 固件烧进去后只有寄存器 0x00 能读——用 SWD 看 MCU 接收缓冲区，每帧都是全零 → **MOSI 杜邦线松了**。重烧固件、重启都没用，插紧就好。
  （项目习惯：先怀疑硬件/环境。）
- sysfs 写入全部失败——ftrace 看 SPI 传输，写的是 `1000`、发出去的是 `1`：BusyBox 上 `echo 1000 | sudo tee` 没把值一次写完。
  换 `sudo sh -c "printf 1000 > attr"` 就好。驱动和链路从头到尾没问题。

## 19. 第 7 课：系统加固（修 F1、F2、F3、F11，F5 前一半）✅（Q81）

文档：`security-zh/hardening.zh.md`。和密码学关系不大，核心是**"没有的东西不会被攻击"**。

### 第 7 课一页总结：从外往里四层 + 一条纪律

```
开发镜像：root 空密码、SSH 接受空密码、串口直接 root、系统可写、服务是全权 root
   → 网络上任何人都能拿下设备（F1，威胁模型唯一的 Critical）

① 门口：谁能进来          SSH 只认密钥、不许 root、不许密码、不许端口转发；串口不给登录
② 进来之后能干什么        系统只读；采集服务降成普通用户 + 沙箱；setuid 程序 15 → 8
③ 家里有多少东西可被攻击  软件包 1919 → 171；内核模块 1808 → 31；内核加固配置 15/44 → 36/44；
                          只加载签过名的模块
④ 已知的洞                CVE 检查：用户态 16 → 4（每条有理由）；内核 3602 条 → 答案是"跟 stable"
纪律：每一项都在板子上读回来确认（原则 17）——好几项"配了但没生效"就是这样发现的
```

对应原则：最小权限（12）、纵深防御（13）、没有的东西不会被攻击。
开发镜像和产线镜像**跑的是同一套软件**，只改"能怎样被访问和修改"，所以 bug 在两边都能复现。

### 19.1 门口（F1、F3）——实测（`first-boot-prod.txt`）

```
dev   /etc/shadow  root::              dropbear 参数 -B（接受空密码）
prod  /etc/shadow  root:*  admin:*     dropbear 参数 -w -s -j -k（禁 root、禁密码、禁两种端口转发）
```

| 在板子上试 | 结果 |
| --- | --- |
| admin 用密钥登录 + sudo | 成功 |
| root 用同一把密钥 | `Permission denied (publickey)` |
| admin 用密码 | `Permission denied (publickey)`——服务器根本不提供密码方式 |
| 通过设备转发到路由器管理页面 | `administratively prohibited`（钥匙被偷也没法把设备当跳板进客户网络） |
| 监听端口 | 只有 22 |
| 串口登录 | `masked` |

小坑：密码字段用 `*` 不用 `!`——dropbear 把 `!` 开头当"锁定账户"，连密钥登录都拒。

### 19.2 进来之后（F5 前一半、F11）

- **系统只读**：`/` 是 `ext4 (ro)`，写 `/etc` → `Read-only file system`。改过的程序重启后不会留下来。
- **采集服务的沙箱**：原来是 root、什么都能碰。现在：
  - 以专用用户 `acq` 运行（udev 规则把 `/dev/acq0` 和两个 sysfs 属性交给它的组）
  - 只留 2 个 capability（`CAP_SYS_NICE`、`CAP_IPC_LOCK`，实时调度和锁内存要用）：`CapEff = 0x804000`
  - 没有网络（自己的网络命名空间）、只能看到 `/dev/acq0`、系统调用白名单（seccomp）、看到的 `/` 只读
  - `systemd-analyze security`：**9.4 UNSAFE → 1.8 OK**
  - 有意**不**开 `ProtectKernelTunables`：它会让 `/sys` 只读，而背压正要往 `/sys` 写 `sample_rate`。
    **照抄通用加固清单最容易在这种地方把产品弄坏。**

### 19.3 攻击面

- 只装板子真正用到的内核模块（从运行中的 `lsmod` 得到，再去掉蓝牙、摄像头）：**1919 个包 → 171，1808 个模块 → 31**。
  （这次精简顺手去掉了 `install` 命令，一个脚本依赖它 → SSH 挂了 → 第 4 课那次"失败的更新自己回滚"。）
- 内核配置（44 项 KSPP 建议的子集）：**15 → 36**。例子：
  - 堆/拷贝加固：把内核内存破坏 bug 从"可利用"变成"崩溃"
  - `STRICT_DEVMEM`：原版 Pi 内核上 root 能通过 `/dev/mem` 读写全部物理内存，其他防护全白搭
  - `MODULE_SIG_FORCE`：只加载签过名的模块，从 `/tmp` `insmod` 不行了（2.5 节）。先确认自己的 `custom_acq` 签名被接受，再开
  - 关 `COMPAT`、`IO_URING`：确认镜像里没人用
  - 有意不开的也写了理由：`FTRACE`（case-04/09 靠它破案，产线应单独出一个去掉它的构建）
- 编译期加固（`binary-hardening-report.py` 扫所有 ELF）：PIE、full RELRO、NX 100%；canary 96.6%。poky 默认就给了。
  BTI/PAC 标记了但 Pi 5 的 A76（Armv8.2）不支持，在这块芯片上等于空指令。

### 19.4 已知漏洞（F2）

- `cve-check` 对 NVD 数据库：3,869 条未修补——**分诊之前这个数字毫无意义**。
- 用户态 16 → 4：逐条对照镜像实际内容。例：openssh 6 条都在 ssh 客户端/sshd 里，镜像里的 SSH 服务是 dropbear → 不适用。每条理由写进 `CVE_STATUS`。
- 内核 3,602 条（过滤掉没编译的代码之后），其中 1,102 条在**后续的 6.6 stable 版本里已经修了**——内核落后 94 个 stable 版本。
  → "怎么处理一百个内核 CVE"的答案是**流程**：跟 stable、重编、跑回归；只对 stable 没覆盖的做逐条分析。
- 升级到 6.12：分诊后 3,602 → 1,789。但它也已落后 18 个版本——**升级只是清零，跟 stable 才能保持低位。**

### 19.5 读回验证抓到的问题（原则 17 的集中体现）

| 配置了什么 | 读回发现 | 修法 |
| --- | --- | --- |
| Yama（`ptrace_scope=1`） | 编进内核了，但 `/sys/kernel/security/lsm` 只有 `capability`——Pi 的默认配置 `CONFIG_LSM=""` = 一个都不启用 | `CONFIG_LSM="yama"`，通过 A/B 更新 1.1.1 下发 |
| 只读根 | **SSH 主机密钥每次开机都变**（在 tmpfs 上）→ 管理员被训练成无视"主机密钥变了"的警告 → 正是中间人攻击需要的 | 主机密钥放到 p7 持久保存，每台设备自己生成 |
| 只读根 | **IP 每次开机都变**：machine-id 每次重新生成 → DHCP 以为是新设备 | `ClientIdentifier=mac` |
| `FORTIFY_SOURCE` | 第一次开机就在 WiFi 驱动里报了一个越界风格的 memcpy 警告（老式 `mask[1]` 写法，实际没越界） | 这正是它的用途：在别人的代码里找编译器无法证明大小的拷贝 |

**编进去不等于启用了；配了不等于生效了。**

## 附：纯软件的信息安全讲什么（题外，2026-09-26）📖

**工具和思路完全一样**（哈希、HMAC、签名、加密、证书；威胁模型的四个问题），变的是**攻击者从哪进来**：
嵌入式的特点是"攻击者手里有设备"；纯软件（Web、后台服务、App）一般假设服务器在可信机房，攻击者**在网络那头**，
能碰到的只有"你暴露出来的接口"和"你的用户"。

| 方向 | 讲什么 | 和我们项目的对应 |
| --- | --- | --- |
| **应用安全**（AppSec） | 程序怎么处理**不可信的输入**：SQL 注入、命令注入、XSS、反序列化；C/C++ 的内存安全（缓冲区溢出、use-after-free）。清单：OWASP Top 10、CWE Top 25。手段：代码审查、静态分析、fuzzing、换 Rust 这类内存安全语言 | 信任边界 §4：驱动校验 `sample_rate`、devbus 把订阅者写回的索引当不可信输入；编译加固（hardening） |
| **身份与权限** | 你是谁（登录、MFA、密码怎么存——bcrypt/Argon2，和 LUKS 的 PBKDF 同一个思路：故意算得慢）；你能干什么（授权，越权访问是最常见的漏洞之一）；会话和令牌（OAuth2/OIDC、JWT = 一段带签名或 HMAC 的 JSON） | MCU 挑战-应答、设备身份证书、最小权限 |
| **通信安全** | TLS（HTTPS）：证书 + CA 证明服务器是谁，对称加密保护内容；双向 TLS（mTLS）让客户端也出示证书 | 第 13 节证书/CA 原封不动；Device CA 就是给 mTLS 用的 |
| **数据安全** | 数据库/云存储加密、密钥管理（云上的 KMS = 托管的 HSM）、隐私合规（GDPR） | LUKS；"密钥放哪"；HSM |
| **供应链** | 第三方依赖的漏洞（Log4Shell，CVE-2021-44228）、被投毒的包、SBOM（软件物料清单）、制品签名（Sigstore）、CI 被攻破 | A4、F2 CVE 检查、更新包签名 |
| **运维 / 云安全** | 配置错误（公开的存储桶）、密钥被提交进 git、权限给太大、容器隔离、及时打补丁 | F1 空密码、F14、只读根、systemd 沙箱 |
| **检测与响应** | 日志、告警（SIEM）、出事之后怎么查、怎么止损 | pstore、健康检查 + 回滚 |

- 现实里的入侵大多不是破解密码学，而是：**偷到的凭据、没打补丁的已知漏洞、配置错误、钓鱼**。
- 嵌入式多出来的难点：攻击者有物理接触 → 需要硬件信任根；设备装出去很难更新 → 签名更新和防回滚是生死问题。
- 对 Linux userspace / 系统软件工程师最相关的是：**内存安全 + 输入校验 + 最小权限 + 依赖/CVE 管理**，这几块项目里都有落地。
