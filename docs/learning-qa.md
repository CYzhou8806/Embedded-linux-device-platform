# 学习问答笔记

V3（Device Tree + kernel driver）过程中的问答记录。只记最终确认正确的
理解，不记对话过程。复习用。

---

## Q1：Device Tree 里的"节点"是什么？

节点是 Device Tree 这棵树上的某一个分支，描述的是某一块硬件的信息——
可以理解成一份硬件说明书。它只描述硬件本身（型号暗号、地址、片选号等
属性），不描述、也不认识任何 driver。

## Q2：`status = "disabled"` 是什么意思？为什么要这么做？

把一个节点的 `status` 设成 `"disabled"`，意思是这份说明书现在失效。因
为一块硬件（比如某个 SPI 片选位置）要靠一份有效的说明书才能匹配到对应
的 driver，把原来的说明书（`spidev@0`）废掉之后，这个物理位置就空出来
了，我们才能在同一位置写一份新的说明书，让它去匹配自己写的 driver。

## Q3：新说明书写完之后，是谁负责让它生效、匹配上 driver？

写完新的节点信息之后，bootloader（树莓派固件）会把它加载、合并进最终
的 Device Tree，交给内核。后续的处理是内核做的：内核遍历这份合并后的
树，用节点的 `compatible` 暗号去匹配已注册的 driver，匹配上之后调用该
driver 的 `probe()` 函数。

## Q4：driver 是 out-of-tree 模块（没有编译进内核、没设成开机自动加载）
时，"匹配"这个动作到底是谁、在什么时候触发的？

匹配永远是内核自动完成的事件驱动过程，不是我们手动执行的动作。重启时
内核解析合并后的 Device Tree，看到 `custom-acq@0` 这个节点，无条件地
为它创建一个 `spi0.0` 设备对象——这一步内核固定会做，跟有没有对应的
driver 无关。这时候系统里还没有任何声明 `edp,custom-acq` 暗号的
driver，这个设备对象就晾在那儿，无人认领。

后面手动执行 `insmod custom_acq.ko`，本质是让这个 driver 作为一个
module 被内核看到、完成注册。driver 一旦注册，内核会自动触发一次扫
描，把它和已经存在、还没被认领的设备对象（`spi0.0`）进行匹配，匹配上
就自动调用 `probe()`。我们手动控制的只是 driver 出现在系统里的**时
机**，不是"匹配"这个动作本身——如果 driver 是随内核启动自动加载的，
同样的自动匹配过程会在开机早期就发生，机制完全一样，只是时间点提前
了。

## Q5：driver 代码里，函数是怎么被内核"接上"、后续怎么被调用的？

这份代码里出现了两种完全不同的绑定机制，容易混，要分开记：

**机制一：结构体里的函数指针字段（`.probe = custom_acq_probe`）**——这
是我们自己手动搭的一张"虚函数表"，`struct spi_driver` 是内核 SPI 子系
统定义好的结构体类型，`.probe` 是里面一个函数指针字段。我们把自己写
的函数名字（不加括号）赋值给它，编译器会自动把函数名转换成这个函数在
内存里的地址（这是 C 语言规则：函数名不加括号使用时会退化成指向它的
指针，跟数组名退化成指针是同一类规则）。内核匹配成功、想调用 probe
的时候，就是从这张表里按字段位置取出这个地址去调用——**认的是字段位
置，不是函数名字符串**，函数名本身随便改都没问题，只要把赋值那行也
一起改。

**机制二：`DEVICE_ATTR_RO(device_id)` 这类宏**——这个是真的靠命名约定
自动生效：宏要求你必须先写好一个名字为 `<传入名>_show` 的函数（比如
`device_id_show`），宏内部通过预处理器的名字拼接，自动生成变量、自动
把这个函数接进去。这里函数名不能随便改，因为宏是靠字符串拼接找到它
的。

**这些函数后续怎么被调用**：`probe()` 是内核 SPI 子系统内部匹配成功
后自动调用的，userspace 全程接触不到。`device_id_show()` 是通过
VFS + sysfs 间接触发的——用户执行 `cat /sys/.../device_id` 走
`read()` 系统调用，VFS 发现是 sysfs 文件，sysfs 子系统查到对应的属性
回调，调用我们写的 `_show` 函数。目前这份代码还没有 `file_operations`
（`open`/`read`/`poll` 那一套），那是以后 `/dev/acq0` 字符设备阶段才
会加。

## Q6：内核模块编译能不能用 cmake 代替 make？

技术上 cmake 可以套一层，但没意义。编译内核模块不是简单把 `.c` 编译成
`.o`，必须完全复用当前运行内核自己的构建规则和 ABI 版本信息（跟内核
编译时用的一样的编译选项、符号版本），不然编译出来的 `.ko` 装不上。我
们 `Makefile` 里 `-C $(KDIR) M=$(PWD) modules` 这行的本质就是"借用内核
源码树自己的构建系统来编译这一个外部模块"，这是 kbuild 定死的接口，不
是风格选择。cmake 就算用，最终也是去调同一套 `make -C ... M=...`，多一
层没有收益。

## Q7：C 语言里"手搓虚函数表"这套语法规则，具体是怎么实现的？

**函数名不加括号使用时，会自动退化成指向这个函数的指针**——这是 C 语
言的固定规则，跟数组名会自动退化成"指向第一个元素的指针"是同一类规
则：

```c
custom_acq_probe(spi);   // 加括号 → 调用这个函数
custom_acq_probe;        // 不加括号 → 这个函数的地址（一个函数指针值）
```

`struct spi_driver` 里的 `probe` 字段，类型是"函数指针"（形如
`int (*probe)(struct spi_device *)`）。写 `.probe = custom_acq_probe`
时，编译器看到左边是函数指针类型，就自动把右边的函数名转换成地址填进
去，等价于手写 `.probe = &custom_acq_probe`（对函数取地址时 `&` 可以
省略，是 C 对函数类型的特殊照顾）。这个地址具体是什么数字不需要关心，
是编译器/链接器决定的（内核模块这种可重定位目标文件，最终地址其实是
`insmod` 加载进内核内存那一刻才敲定的，这个过程叫重定位，全程自动，
不用 driver 作者操心）。

**所以"手搓虚函数表"的本质**：找一个普通结构体，把它的某些字段声明成
函数指针类型，逐个手动赋值成自己写的函数（不加括号，靠退化规则自动
变成地址）。内核想调用某个回调时，就从这个结构体按字段位置取出对应的
函数指针去调用。整个过程没有语言层面的"虚函数"机制参与，纯粹是"结构
体 + 函数指针字段 + 手动赋值"这几个 C 基础特性组合出来的效果。

## Q8：验证 DATA_READY 这根新线的过程里，"测线通不通"和后来"加三个
driver 接口去测试"，是同一件事的两个阶段吗？

不是，是两件性质不同的事，容易被误认成一件事的先后两步。

**第一件事：这根线本身通不通（纯物理层面）**。这个问题在手动把线接到
一个已知的 `3V3` 电源脚（不管是碰 MCU 上的还是接 Pi 自己的）、看 Pi
那边电平会不会变，就已经在原理上回答了——只要注入电压能让 Pi 读到变
化，线就是通的，跟固件代码写得对不对完全无关。

**第二件事：固件操作这根线的逻辑对不对（软件/逻辑层面）**。线确认通
了之后，新的问题是：MCU 真正干活的时候，它驱动这根线的方式，是不是
符合预期——预期是"有数据=高电平、没数据=低电平"。要测这个，得让 MCU
真的进入工作状态（启动采集、产生数据、被读走），不能只读几个固定不变
的寄存器（比如 `device_id`），因为那样根本不会触发 FIFO 相关的逻辑。

为了测第二件事，在自己写的 `driver/custom-acq/custom_acq.c` 里加了三
个新函数/sysfs 接口（`control` 可写、`fifo_level`/`data_val` 只读），
分别对应固件本来就有的三个寄存器：写 `control` 触发 MCU 启动/停止采
集，读 `fifo_level` 看队列还剩多少，读 `data_val` 会真正从 FIFO 弹出
一条数据（同时触发 MCU 重新计算 DATA_READY 电平）。测试时不是运行一
个保存好的脚本，是直接在命令行里现场敲一串指令（写 `control`、读
`data_val` 若干次），一边执行一边用 `gpiomon` 盯着这根线的电平变化，
观察结果符不符合预期。

## Q9：给 driver 加 GPIO 中断支持，是不是等于写了一个新的 GPIO 驱动？

不是。GPIO 控制器本身的驱动（树莓派上是 `pinctrl-rp1`）内核里早就有
了，不需要、也不应该自己再写。这次做的事情，是在已有的 `custom_acq.c`
（SPI 驱动本身）的 `probe()` 里，调用了几个内核已经提供好的、专门给
"想使用某根 GPIO 线"的驱动调用的函数（`devm_gpiod_get`、
`gpiod_to_irq`、`devm_request_threaded_irq`）。

准确的身份是：这个驱动是 GPIO 子系统的**使用者/消费者**（consumer），
不是 GPIO 的**驱动开发者**。这跟 SPI 的关系是同一个套路——没有自己写
SPI 总线控制器的驱动，只是调用内核提供好的 `spi_sync_transfer()` 去
"用" SPI；这次只是换了一个子系统，做法一样：调用内核封装好的接口，
不用关心底层硬件寄存器怎么操作。

## Q10：`custom_acq_irq_thread()` 是怎么被内核"调用"到的？触发它的是
不是系统调用？

不是靠名字匹配，也不是通过系统调用触发，两点分开说：

**内核怎么找到这个函数**：靠的是 Q5 笔记里说的"机制一"——直接把函数
名（会退化成地址）当参数传给 `devm_request_threaded_irq()`：
```c
devm_request_threaded_irq(&spi->dev, irq, NULL, custom_acq_irq_thread, ...)
```
跟 `.probe = custom_acq_probe` 是同一类做法，内核只认我们传进去的这个
地址，不关心函数叫什么名字（改个名字完全没问题，只要调用点跟着改）。
这跟 `DEVICE_ATTR_RO(device_id)` 那种靠字符串拼接、必须叫
`device_id_show` 的"机制二"是两回事，不能混。

**触发它的是硬件中断事件，不是系统调用**：这是内核处理硬件事件的一条
独立工作流——硬件检测到电平变化 → 中断控制器发出中断信号 → 内核异
步调度我们注册的处理函数去跑，全程不需要任何用户态程序发起
`read()`/`write()` 之类的系统调用，甚至这时候可能根本没有用户程序在
运行。这跟"用户态系统调用 → VFS → `file_operations` → 驱动"是两条不
同性质的路——后者是未来 `/dev/acq0` 字符设备要走的路，两者不是一回
事，也不是谁调用谁：中断处理函数只负责把数据塞进 `kfifo`（生产者），
`/dev/acq0` 的 `read()` 以后负责从 `kfifo` 里取（消费者），中间靠这
个队列传递数据，两边互不调用。

## Q11：GPIO 电平变化，是怎么一路触发到我们自己写的中断处理函数的？

完全是硬件电路自动完成的，中间没有任何软件在轮询等待：

1. GPIO 控制器芯片里，每根引脚背后有专门的 edge detection（边沿检
   测）电路，纯电子层面感应"电压从低变高"这个物理事件，感应到的瞬
   间自动翻转一个硬件信号——不是被谁"看"到的，是电路设计成这样。
2. 这个信号通过芯片内部真实的电气连线，送到 interrupt controller
   （中断控制器，ARM 上通常叫 GIC），由它决定 priority（优先级）、
   要不要现在打断 CPU。
3. CPU 硬件本身内置"每执行完一条指令顺便看一眼有没有中断"的电路，
   发现有中断会自动跳转到一个固定地址（interrupt vector，中断向
   量），这个跳转是硬件行为，不是软件循环。
4. 到了这个固定地址，内核预先写好的通用"入口代码"开始跑——查表找
   到这次是哪个中断号、该调用谁。这一段就是 hard IRQ（硬中断）部
   分，环境极度受限（不能睡觉、必须极快）。

从针脚电压变化到 hard IRQ 入口代码开始跑，全程是硬件自动完成的，我
们完全没写这部分逻辑；我们只写了 hard IRQ 结束之后要调用的那个函数
（`custom_acq_irq_thread`），可以理解成一个"回调"——`devm_request_
threaded_irq()` 第三个参数传 `NULL`，就是告诉内核"hard IRQ 这部分
我不自定义，用默认的（唤醒线程）就行"。内核 scheduler（调度器）随
后找机会把我们的线程真正调度上 CPU 去跑，这时候环境正常了，可以睡
觉、可以做 SPI 通信，这就是 threaded IRQ（线程中断）部分。

## Q12：加中断之后暴露的 SPI 并发 bug（case-04），根本原因是 priority
没设对吗？加锁具体保护的是什么？

不是 priority（优先级）问题，是真正的并发访问问题，锁保护的是"一次
完整的寄存器读写操作"这个共享资源，不是任何调度层面的东西。

**为什么不是 priority**：树莓派是多核 CPU（Pi 5 有 4 核），用户态触
发的操作（写 `control`）和中断触发后被调度执行的线程，完全可能被分
到两个不同的核心，在同一微秒真的同时运行——这是物理层面的真并行，
不是"谁该排在前面"的调度 priority 问题，调整 priority 解决不了两个
核心同时访问同一个资源的冲突。

**更进一步：就算把所有任务锁定在同一个核心上跑，也不能保证问题消
失**——因为寄存器读写操作本身包含 `usleep_range()`（真的会让出
CPU、进入睡眠），这段睡眠期间，哪怕只有一个核心，scheduler（调度
器）也完全可能把这个核心切换去运行另一个就绪的任务（比如中断线
程）。所以问题的本质不是"有几个核心在同时跑"，而是"这段多帧操作中
途会让出 CPU 控制权，而让出的这段时间没有任何机制阻止别人插进来动
同一个资源"。

**锁到底保护什么**：不是保护"SPI 总线硬件"本身（单次 `spi_sync_
transfer()` 本来就是原子的，硬件层面不会被打断），保护的是**"一次
完整的寄存器读写"这个逻辑操作**——地址帧 + 中间的睡眠 + NOP 帧，这
三步必须被别人当成一个不可拆分的整体，谁在做这套流程，其他人就得等
它做完才能开始自己的流程。这正是 mutex（互斥锁）而不是"设 priority"
或"绑核心"能解决这个问题的原因：它直接锁的是"这个资源在这段时间内
只能有一个使用者"，不依赖任何关于调度顺序的假设。

## Q13：启动采集（写 `control`）之后，为什么几乎立刻就会触发
DATA_READY 中断？完整因果链是什么？

因为 SPI 是主从总线，MCU 没法主动找树莓派说话，所有通信永远由树莓派
（主机）发起——所以看似"两件事都是树莓派发起的"，实际是这条真实的因
果链：

1. 树莓派写 `control=1`（这是 A）→ 通过 SPI 把"开始采集"命令发给 MCU。
2. MCU 收到命令，启动内部定时器，开始产生采样数据，存进它自己的硬件
   FIFO。
3. 第一条数据一入队，MCU 把 DATA_READY 这根线拉高（这是 MCU 唯一能
   "主动"做的事——它管不了树莓派，只能改变一根线的电平，等着对方自己
   发现）。
4. 树莓派自己的 GPIO 硬件检测到这根线电平变化，触发树莓派自己的中断。
5. 内核唤醒中断处理线程（这是 B）开始跑，第一件事就是发 SPI 去问
   "现在有几条数据"。

所以 A 和 B 之间不是巧合，是一条环环相扣的因果链：A 直接导致 MCU 产
生数据，数据导致电平变化，电平变化导致树莓派自己的硬件中断，中断导
致 B 发生。也正因为这条链条很短、每一步都很快，A 和 B 在时间上几乎
紧挨着发生，才会撞进"两帧之间那 500us 空隙"，引出 case-04 那个并发
bug。

## Q14：MCU 有没有可能被中断？这次说的"树莓派被中断"是不是唯一的方式？

MCU 理论上完全可以被中断——它自己也有处理器（Cortex-M3），也有自己
的 interrupt controller（中断控制器，NVIC）。这次的设计里，是我们主动选择让**树莓派**去处
理"DATA_READY 电平变化"这件事，不是"中断天生只能由谁来处理"。触发方
式是硬件层面的：GPIO 硬件检测到电压抬高，把这个物理事件当成一次中断
信号，交给对应芯片（这里是树莓派）去处理。哪颗芯片会因为这根线而被
中断，取决于哪颗芯片把这根线配置成了"中断输入"——MCU 把 `PA8` 配置
成输出（只管拉高电平），树莓派把 `GPIO17` 配置成输入并监听边沿，所以
只有树莓派会被这次事件中断。

## Q15：hard IRQ（硬中断）能不能自己写？"不能睡眠"这条规矩的本质是什么？

可以自己写（`devm_request_threaded_irq()` 的第二个参数）。"不能睡
眠、priority 最高、不能被打断"这些说法，都只是**外在表现**，本质原
因是：hard IRQ 这个阶段运行在一种叫 atomic context（原子上下文）的
状态里，在这个状态下，**scheduler（调度器）根本不介入工作**——不
是"轮不到它"，是这时候压根不存在"调度"这件事。既然调度都不发生，
priority 这个概念自然也无从谈起（priority 是 scheduler 用来决定"下
一个该轮到谁"的依据，scheduler 都不工作了，就没有"谁优先"可言）。
这条规矩没有编译器强制检查，只有内核在调试模式
（`CONFIG_DEBUG_ATOMIC_SLEEP`）下才会帮你发现违反它的代码。

## Q16：为什么寄存器读写协议要发两帧，不能一次搞定？

根本原因是 SPI 全双工的物理特性：**发送的同时必然会收到点什么**，
不存在"只发不收"这回事。所以哪怕这次的目的只是"取数据"，也必须发点
什么才能触发接收动作——这就是第二帧（NOP，内容本身没有意义，纯粹为
了触发一次接收）存在的原因。

两帧之间留一段时间（`INTER_FRAME_US`），是特意给 MCU 处理的空间：
第一帧发送的同时收到的数据，**不是**对这次命令的回应——因为 MCU 这
时候还没来得及处理、算出结果，你收到的只能是它之前处理完的、还没被
取走的旧结果。只有等中间这段时间过去、MCU 真正处理完，第二帧才能收
到"这次命令"对应的正确结果。如果这个"一发一收"的节奏被打乱（比如被
别的操作插了一帧），收到的数据就会跟自己刚才发的对不上，协议本身设
计了检查（回显字节比对）能发现这种错位，检测到就直接报错，不会把错
位的数据当成正确结果用。

## Q17：hard IRQ（硬中断）能不能 preempt（抢占）正在跑的线程/workqueue？

能，而且是无条件的。这是两套完全独立的机制，不能混在一起想：**调度
器**负责"正常执行流"（普通线程、workqueue、用户进程）之间谁先谁
后；**interrupt controller（中断控制器）**负责 hard IRQ 怎么触发、
路由给哪个核心，这条路完全不经过 scheduler（调度器），scheduler 管
不着它。不管目标核心当前在跑什么（哪怕是内核线程、workqueue、用户
进程），只要中断信号到达、这个核心当前没有关闭本地中断，CPU 硬件
会立刻暂停当前执行、跳去处理 hard IRQ——这不是调度器"临时把中断调
度成更高 priority"，是 hard IRQ 压根不参与 scheduler 的排队游戏，属
于比 scheduler 更底层的机制。

## Q18：hard IRQ（硬中断）会不会因为"其他核心都在忙"而排队等待？

会等待的唯一情况，是目标核心自己当前处于"本地中断已关闭"的状态——
最典型的就是这个核心正好正在处理**另一个** hard IRQ（核心进入 hard
IRQ 处理时，会自动关闭自己的本地中断接收能力，防止被新中断打断到
一半），这时候新中断只能挂起，等这个核心处理完当前的、重新打开本
地中断的那一刻立刻触发。因为 hard IRQ 处理函数被要求写得极短，这种
等待通常是微秒级的，不是"排队等空闲核心"这种调度层面的等待。

## Q19：`mutex` 和 `spinlock`，为什么 hard IRQ（硬中断）能"合法"调用
后者、不能调用前者？这跟 deadlock（死锁）风险有什么关系？

`mutex` 抢不到锁时，要靠 scheduler（调度器）把当前执行流程"睡"过
去，而 hard IRQ 上下文压根没有 scheduler 介入的余地（Q16），所以
`mutex_lock()` 在 hard IRQ 里是**明确不允许**的，调试模式下会被直
接检测报错。

**容易搞混的一点**：这里的"不允许"**不是编译期的**——`mutex_lock()`
写在 hard IRQ 处理函数里，编译完全能通过，代码也能跑起来。真正拦截
它的，是内核在调试模式（`CONFIG_DEBUG_ATOMIC_SLEEP`）下的**运行时**
检测，跑到这行才会报错；非调试模式下编译和运行都不会主动拦，会直接
导致未定义行为/内核状态损坏。没有任何编译器层面的类型系统会替你拦
下这种错误用法。

`spinlock` 完全不碰 scheduler——抢不到锁就原地死循环不断检查，纯粹
是 busy-wait（忙等）。正因为它不需要 scheduler，语法上在任何上下文
（包括 hard IRQ）都能合法调用、编译运行都没问题。**但这恰恰是它危
险的根源**：如果 hard IRQ 处理函数里用 `spin_lock()` 去抢一把正被
"自己所在这个核心、当前被打断的那段代码"占着的锁，它会陷入真正的
死循环——而释放这把锁的代码，正是被这次 hard IRQ 打断、动弹不得的
那段代码，谁都没法继续，这个核心永久卡死。

## Q20：hard IRQ（硬中断）如果不检查锁、直接碰被锁保护的资源，会发
生什么？这引出什么最佳实践？

锁只是一个"大家都要主动检查"的约定，不是物理屏障。如果 hard IRQ 处
理函数里的代码压根没写"检查这把锁"这一步，直接去读写被锁保护的变
量，那这把锁对它**完全无效、畅通无阻**——不会 deadlock（死锁），
但会导致数据在没人知情的情况下被同时改坏（比如正常线程正改到一
半，被 hard IRQ 插进来又改了一次），而且不会有任何报错提示，是最
难排查的一类 bug。

由此引出的最佳实践：**hard IRQ 处理函数最好完全不碰被锁保护的共享
资源；如果必须碰，也必须用锁保护，不能因为"反正能绕过去"就跳过加
锁这一步。** 这条实践不只对 hard IRQ 成立——任何会去碰一个被锁保护
的资源的执行体（普通线程、workqueue、hard IRQ）都适用：只要有别的
地方也会碰这个资源、且用锁保护着，自己这边就必须也用锁，否则同样
会构成 data race（数据竞争）。

## Q21：`spin_lock_irqsave()` 只关闭"当前核心"的本地中断，如果同一
把锁被别的核心的 hard IRQ（硬中断）抢，这样够用吗？

够用，不需要额外机制保证 hard IRQ 一定在同一核心处理。因为 deadlock
（死锁）只发生在**同一个核心自己打断自己**这一种情况——核心 A 拿着
锁，被自己核心上的 hard IRQ 打断，这个 hard IRQ 又想抢同一把锁，这
时候"能释放锁的代码"和"想抢锁的 hard IRQ"挤在同一个核心上，谁都让
不了谁，才会永久卡死。

如果是核心 B 的 hard IRQ 来抢核心 A 持有的这把锁，核心 B 只会正常
"自旋等待"，这不是 deadlock——核心 A 是完全独立、仍在正常运行的另
一颗核心，不会因为核心 B 在等就停下来，会按自己的节奏正常执行完临
界区、正常释放锁，核心 B 等一小会儿就能拿到。跨核心的自旋是安全
的、暂时的等待，只有"同一核心的自我打断"才是致命的，而这正是
`_irqsave` 只需要关闭"当前核心"本地中断就足够解决的问题。

## Q22：`mutex` 能不能"挡住"其他线程访问被它锁定的资源？

不能，`mutex` 跟 `spinlock`（Q19–Q21）有完全相同的局限：它们都只是
一个"大家说好要检查"的约定，不是物理屏障。如果另一个线程压根没调用
`mutex_lock()`，直接去读写那个变量，`mutex` 一样拦不住——跟 hard IRQ
绕开 `spinlock` 是同一种漏洞，只是这次换成"某段代码没写好、忘了先拿
锁"。

`mutex` 和 `spinlock` 唯一的区别，只在于遵守约定的调用者抢不到锁时
怎么等：`mutex_lock()` 抢不到锁会把当前线程交给 scheduler 去睡眠
（sleep）；`spin_lock()` 抢不到锁是原地忙等（busy-wait），不会睡。
"锁能不能真正挡住别人"这件事，两者半斤八两，都取决于每一处会碰这个
资源的代码，是不是都老老实实先去检查了这把锁。

## Q23：Scheduler / Interrupt Controller / Priority 这几个反复出现
的词，到底怎么区分？

三个是完全独立的子系统，管的是不同层面的事，混在一起想就会绕不出来：

- **Scheduler（调度器）**：只负责在"可以被睡眠、可以被换出 CPU"的
  执行体（普通线程、内核线程、threaded IRQ handler）之间决定"现在该
  谁用 CPU"。`mutex` 抢不到锁时依赖的就是它——把线程放去睡眠，之后
  再择机唤醒。**Priority（优先级）是 scheduler 内部的概念**，决定
  "多个都想跑的线程里，先让谁跑"，只在 scheduler 管辖的范围内才有意
  义。
- **Interrupt controller（中断控制器，ARM 平台上通常是 GIC）**：一
  个独立的硬件模块，负责收集所有外部中断信号（比如 GPIO 边沿变化产
  生的信号）、决定优先级、路由给某个 CPU 核心。它完全不经过
  scheduler，是比 scheduler 更底层的机制——一次硬件中断能不能立刻
  preempt（抢占）某个核心，看的是这个核心当前"本地中断使能"开没
  开，不看 scheduler 那边有没有更高优先级的线程在跑。
- **Hard IRQ（硬中断）**：中断控制器把信号路由到某个核心后，那个核
  心真正开始执行的、极度受限的一小段代码（不能睡眠、必须极快）。它
  运行在 atomic context（原子上下文）里，这个状态下 scheduler 压根
  不介入工作。
- **Threaded IRQ（线程中断）**：硬中断结束后，交给 scheduler 去调
  度、真正执行我们写的处理逻辑（可以睡眠、可以做 SPI 通信）的那部
  分——这部分才重新回到 scheduler 的管辖范围。

一句话理清关系：**中断的"触发和 preempt"归 interrupt controller
管，完全绕开 scheduler；只有"preempt 之后、进入 threaded IRQ 阶
段"，才轮到 scheduler 接手，priority 也只在这个阶段才有意义。**

## Q24：真正的 C++ 虚函数表也是这么实现的吗？

底层机制完全一样——都是"一张函数指针表，按位置取出来调用"。区别只在
于谁来搭这张表：我们的内核代码是自己手写结构体、手动赋值；C++ 是编译
器自动帮每个带 `virtual` 函数的类生成一张 vtable，并给每个对象偷偷塞
一个隐藏指针（vptr）指向对应的表，调用虚函数时自动"取 vptr → 按下标
取函数指针 → 调用"，跟我们 `driver->probe(spi_dev)` 是同一种机器码模
式，只是全自动、还多了继承带来的动态绑定（同一个基类指针能调出不同子
类的实现）。理解了我们这份手搓版，基本就理解了 C++ 虚函数调用底层在
干什么。

## Q25：`/dev/acq0` 是靠什么机制让用户空间能拿到内核里缓存的数据的？

在这之前（`probe()` 里注册 GPIO 中断、把数据存进 kfifo 那部分），全都
是纯 kernel space（内核空间）的行为——IRQ 线程把采集到的数据塞进
kfifo 后，用户空间没有任何入口能把这些数据取出来。

这次新加的 `/dev/acq0`，是通过 misc device（混杂设备）框架注册了一个
字符设备文件，核心是一张叫 **file operations**（`struct
file_operations`）的函数指针表，把 `open`/`read`/`poll`/`release`
这几个操作分别绑定到我们自己写的函数上。用户空间调用 `read()`、
`poll()` 这些 system call（系统调用）时，内核顺着 VFS（虚拟文件系统）
找到 `/dev/acq0` 这个设备文件，再查这张表，直接跳转执行对应的内核函
数（比如 `custom_acq_read()`）。

这跟 sysfs 的 `xxx_show`/`xxx_store`、以及 `spi_driver` 的 `.probe`
是同一套思路——都是"把内核函数地址填进结构体字段里，注册成一张表，
用户/系统的调用来了内核负责按表分发"，不是靠函数名字匹配。区别只是
sysfs 用的是按命名约定生成的 show/store 函数，这里用的是标准的 file
operations 这张表，因为 `/dev/acq0` 要支持的是 `read()`/`poll()` 这
种更通用的"像读文件一样读设备"的语义。

效果就是：把"用户空间发起的系统调用"和"内核里管理 kfifo 数据的函数"
关联了起来，原来困在内核空间、用户完全碰不到的数据，现在有了一条明确
的出口能被读出来。

## Q26：misc device 跟 character device（字符设备）是什么关系？

misc device 就是 character device 框架之上的一层"快捷封装"，不是另
一套独立机制。

字符设备是更底层、更通用的框架：任何想做字符设备的 driver，理论上都
要自己申请一个 major number（主设备号）、自己管理 minor number（次
设备号）、自己调用 `cdev_init()`/`cdev_add()` 把 `file_operations`
挂到具体设备号上——这套流程比较繁琐，适合"一个驱动要管理一大批同类
设备、需要用不同 minor 区分"的场景。

misc device 是内核在字符设备框架之上封装的"懒人接口"，专给"只需要
一个简单设备节点，不需要复杂编号体系"的场景用。所有 misc device 共
享同一个固定的 major number（10——测试时 `ls -la /dev/acq0` 看到的
`crw------- 1 root root 10, 264` 里那个 `10` 就是这个），
`misc_register()` 内部自己维护一张表，自动分配 minor number
（`MISC_DYNAMIC_MINOR` 就是"你不用管，内核自己挑一个没被占用的"的意
思）。驱动只需要填一个 `struct miscdevice`（名字 + `file_operations`）
再调一次 `misc_register()`，cdev 注册、设备号分配这些底层细节都由
misc 框架代劳。

所以两者的关系是：**misc device 是 character device 框架的一个子集
封装，底层的绑定机制（VFS → `file_operations` 分发）完全一样，只是
省掉了手动管理主/次设备号这一层**，作用都是让用户空间能够通过标准的
`open`/`read`/`poll` 调用摸到内核驱动里的数据。

## Q27：从 V3 第一版到第四版，整体是怎么一步步搭起来的？

- 第一版：probe/remove 骨架 + 最基础的 SPI 寄存器读写（`device_id`/
  `fw_version` 这类"硬件身份信息"通过 sysfs 暴露出来）。
- 第二版：加 GPIO threaded IRQ，让驱动能响应 MCU 那边触发的硬件中
  断。
- 第三版：加 kfifo 环形缓冲——中断触发后，把数据从 MCU 搬进内核自己
  维护的一个缓冲区里存起来。
- 第四版（`/dev/acq0`）：到这一步，业务功能已经齐了（怎么响应中断、
  怎么把数据存进 kfifo），剩下的只是"怎么让用户空间摸到这份数据"——
  用 misc device 把 `file_operations` 接出去，就是给用户空间开了一
  个标准的读取入口。

（一个时间线上的小细节：`control`/`fifo_level`/`data_val` 这几个
"问 MCU 当前状态"的 sysfs 接口，实际是第一版 debug 阶段就加上的，为
了验证 DATA_READY 接线是否正确（详见 case-03），不是第三版才加的；
但这个细节不影响"四个版本一步步搭建业务能力，最后一步只是开放给用户
空间"这个整体理解。）

## Q28：用户空间没写任何新代码，为什么就能调用到内核里的驱动函数？

`file_operations` 本身不是系统调用，它是内核里的一张函数指针表——
是**系统调用碰到某个设备节点时，内核用来查表分发的对象**，不是接口
本身。

真正的"接口"是 `open()`/`read()`/`poll()` 这几个标准系统调用——它
们是 POSIX/libc 层面早就定义好的通用接口，任何用户空间程序（`cat`、
`dd`、自己写的 C 程序）天生就会调用它们，不需要为某个具体设备重新
学一套新 API。我们做的事情，是在**内核这一侧**把 `/dev/acq0` 这个
VFS 节点跟一张写好的 `file_operations` 表关联起来：用户空间程序对
这个节点调用 `read()` 时，内核顺着 VFS 找到这个节点、查到这张表、
跳转执行我们写的 `custom_acq_read()`。所以是**用户空间复用了早就存
在的通用系统调用接口，去触达这个新节点背后、内核这一侧新写的函数**，
而不是用户空间自己也要写配套的新代码。

## Q29：`file_operations` 用"显式结构体填函数指针"、sysfs 用"命名约
定 + 宏自动生成"，这两种绑定方式该怎么选？

跟"哪种更优雅"无关，取决于**要绑定的这组函数数量是固定小集合，还是
会不断增长的一大批**：

- `file_operations` 的字段是 VFS 这一层一次性定死、几十年基本不变的
  一组操作（`open`/`read`/`write`/`poll`/`release`/`mmap`/`ioctl`
  ……），而且大多数驱动只实现其中几个，没实现的字段留空即表示"不支
  持"。这种"字段少、语义各不相同、大多可选"的场景，显式结构体字面
  量（`.read = custom_acq_read`）最清楚：一眼看出支持哪些操作，编译
  器还会检查函数签名对不对。
- sysfs 的场景相反——一个驱动可能暴露几十个属性（`device_id`、
  `control`、`fifo_level`……），每个属性的"形状"高度重复（都要包进
  一个 `struct device_attribute`，都是 `xxx_show(dev, attr, buf)`
  签名），唯一不同的只是函数名。这种"数量多、结构高度重复，只有一
  处变化"的场景，用宏（`DEVICE_ATTR_RO(x)`）把重复的结构体初始化自
  动生成出来，程序员只需要遵守"函数名叫 `x_show`"这个命名约定，能省
  掉大量重复劳动。

## Q30：V4 Phase 2 的 `MetricsReporter` 打印的那些数字是它自己统计
的吗？跟日志（logging）是什么关系？

不是它自己统计的，`MetricsReporter` 不维护任何独立的计数器。它做的
事情是**定时去读取别的模块早就在维护的状态**——`AcquisitionWorker`
的 `samples_read()`/`gap_count()`、`RingBuffer` 的 `size()`、
`Device` 读到的 `kfifo_overflow`（一次真实的 sysfs 读）——然后**调
用日志库（spdlog）把这些数字汇总打印成一行**。

所以关系是"`MetricsReporter` 是日志的调用方"，不是反过来"日志使用
`MetricsReporter`"。它存在的价值不在"计数"本身（这些数早就有别的模
块在维护了），而在"定时把已经存在、但分散在各处的状态，汇总成一行
人类能一眼看懂的运行状况"，避免重复发明第二套计数系统。

## Q31：`Watchdog` 发现长时间没收到新样本后，具体的处理顺序是什么？

分两步，顺序很关键：

1. **先做一次非侵入式的"探活"**——读一次 `device_id`（sysfs，本身就
   是一次真实的 SPI 往返），不是直接就去尝试重启采集。
2. **只有探活成功，才尝试软复位**（把 `control` 写 `0` 再写
   `1`）。如果探活这一步本身就失败（抛异常），说明 SPI 链路已经不
   通，软复位走的还是同一条 SPI 总线，大概率也发不出去——这种情况
   下直接放弃自动恢复，记一条 error 日志，指向 `tools/mcu-reset.sh`
   （走调试器 SWD、不经过 SPI 的真硬件复位）作为人工兜底手段，不会
   盲目重试。

这套"先确认链路通不通，再决定要不要采取行动"的顺序，是为了避免在链
路真的断了的情况下，还对着一条已经不通的总线反复发指令。

## Q32：systemd 集成具体指的是哪两件事？

**不是** `main.cpp` 里给各个功能模块（`Config`/`Metrics`/`Watchdog`
……）配参数、决定谁先启动谁后启动那部分代码——那部分是 `main.cpp`
一直在做的、模块接线的日常工作，从 Phase 1 起就有，Phase 2 每加一个
新模块只是多接一根线，跟 systemd 无关。

systemd 集成specifically 指的是这个程序和"操作系统的服务管理器
（systemd）"之间的对接，具体是两件独立的事：
1. **`.service` 配置文件**（`systemd/device-service.service`）——
   告诉 systemd"这个程序该怎么启动、崩了要不要自动重启、多久没心跳
   算卡死"。
2. **程序内部调用 `sd_notify()`**——反过来让程序主动向 systemd 汇
   报自己的状态（`"READY=1"` 表示"我启动完成了"，`"WATCHDOG=1"` 表
   示"我还活着，定期心跳"）。

这两者合起来，才是"systemd 集成"——是程序和外部服务管理机制之间的
协议对接，跟程序内部自己怎么组织模块是两个不同层面的事情。

（补充：这个沟通不是只在启动时发生一次——`"READY=1"` 是启动自检成
功后发一次，`"WATCHDOG=1"` 是运行期间跟着 `MetricsReporter` 的心跳
持续重复发送，贯穿整个运行过程。而且这整套协议是**可选、需要显式声
明**的——`.service` 文件里写了 `Type=notify` 才等于告诉 systemd"别
用你默认那套粗糙判断（进程一 fork 出来就算启动成功），我会自己主动
汇报状态"；不写这行，程序照样能被 systemd 启动和管理，只是 systemd
对它状态的判断会更粗糙。）

## Q33：systemd 到底是什么？

systemd 是 Linux 系统里负责"开机后第一个启动、然后管理所有其他程序"
的那个特殊程序——几乎所有现代 Linux 发行版（包括这台树莓派用的
Debian/Raspberry Pi OS）都用它。

电脑开机后，内核（kernel）启动完自己，会启动一个进程号（PID）永远是
`1` 的特殊进程，这个进程接下来负责启动这台机器上几乎所有其他长期在
后台跑的程序（统称 service，服务）：网络、SSH、我们自己写的这个采集
服务……在现在大多数 Linux 发行版上，PID 1 这个角色就是 systemd。

systemd 具体管理服务要做的事：按正确顺序启动它们、收集它们的日志
（`journalctl` 查的就是它收集的）、服务崩了按配置自动重启、提供统一
命令控制任何服务（`systemctl start/stop/restart/status`）、支持开机
自动启动（`systemctl enable`）。`device-service.service` 这个文件，
本质上就是"往 systemd 那里注册一个新服务"——写之前 systemd 根本不知
道这个服务存在，写完 `daemon-reload` 之后，它就被 systemd 当成跟
SSH、网络这些系统自带服务同等地位的东西来管理了。

**关键的一点：systemd 虽然角色是 PID 1、地位很核心，但它本身只是一
个普通的用户空间（userspace）程序，不是内核（kernel）的一部分。**
`fork()`/`exec()`（创建新进程用的通用系统调用）是内核提供的机制，但
"用这套机制去启动 SSH、启动我们的服务"这个决策和调度逻辑，是 systemd
自己（用户空间）在做的，不是内核自己决定要启动什么。

## Q34：`sd_notify` 和 signal 都是"系统暴露出来的接口"，它们的本质
区别是什么？

**两者确实都可以理解成"系统暴露出来给程序用的接口"，但区别在于这个
接口的机制本身是运作在内核态还是用户态——不能因为"都很基础/都很系统
级"就默认归为同一类。**

**signal 是内核级别的机制**：内核自己在维护"这个进程有没有信号在排
队""屏蔽了哪些信号"这些状态，`sigwait`/`pthread_sigmask` 背后调用的
是真正的系统调用（比如 `rt_sigprocmask`），信号的产生、投递、排队，
内核直接参与其中。

**`sd_notify` 完全不是这么回事**——它是我们的程序和 systemd（一个普
通的用户空间进程）之间，用 Unix domain socket（一种进程间通信方式）
自己约定好的一套通信协议。我们的程序往这个 socket 里发一条消息（内
容就是字符串 `"READY=1"`），这个 socket 在哪、该往哪发，是靠一个叫
`NOTIFY_SOCKET` 的环境变量告诉我们的（systemd 启动我们的进程时自己
设置进去的）。`socket()`/`sendto()` 这些收发消息用的调用确实是内核
提供的通用 IPC（进程间通信）机制没错，但"发的这条消息该长什么样、
`READY=1` 是什么意思"这套协议本身，完全是 systemd 自己发明的、纯用
户空间层面的约定，内核根本不知道、也不关心这条消息的内容。

一般化的判断标准：一个"系统暴露出来的接口"是不是内核态的，要看这个
机制实际运作在哪个空间——是内核自己参与维护状态、亲自处理（signal），
还是两个用户空间进程之间借助内核提供的通用工具（socket）自己达成的
约定（`sd_notify`）。不能只看"这个东西听起来是不是很核心/很系统级"
就默认它是内核机制。

## Q35：`SequenceTracker` 里，`gap_count_` 用了 `std::atomic`，但
`last_seq_` 没有用，为什么？

判断标准是"这个字段会不会被别的线程读/写"，不是看字段本身的数据类
型。`gap_count()` 这个读接口会被 `MetricsReporter` 在它自己的线程里
定时调用，跟 `AcquisitionWorker` 自己的线程（唯一会调用
`observe()`、修改这两个字段的地方）是两个不同的线程——两个线程碰同
一块内存，不加同步就是数据竞争，所以 `gap_count_` 需要
`std::atomic`。`last_seq_` 则完全相反：它只在 `observe()` 内部被读
写，从来不会被 `AcquisitionWorker` 之外的任何代码直接访问，从始至终
只有一个线程会碰它，不存在"两个线程同时读写"的场景，所以不需要
`atomic`。

## Q36：`AcquisitionWorker::last_sample_time()` 内部为什么存的是
`std::atomic<int64_t>`（毫秒数），而不是直接存一个
`std::atomic<std::chrono::steady_clock::time_point>`？

**订正过一次的版本**：最初的说法（"`time_point` 不保证能被
`atomic` 安全包装"）说重了。`time_point` 通常满足
`std::atomic<T>` 要求的"trivially copyable"这个条件，
`std::atomic<time_point>` 大概率能编译、也能正确工作——标准库真正不
保证的，是它是不是 **lock-free**（无锁，意味着底层直接用硬件的原子
指令操作，速度快）；不满足无锁条件时，`std::atomic` 会退化成内部悄
悄用一把锁去实现"看起来是原子操作"的效果——**没有变得不安全，只是
可能变慢**。转成 `int64_t`（毫秒数）更多是"图省心，确保拿到最简单、
肯定无锁的版本"，不是"不这样写就会出 bug"这么绝对。

这依然是同一类考虑——只要涉及"会被别的线程读"的字段，就要去确认选
用的类型在 `atomic` 包装下的实际表现（能不能编译、是不是无锁），不
能凭直觉想当然，但具体判断标准（trivially copyable、lock-free）是
`std::atomic` 这个标准库工具自带的规则，需要单独查文档确认，不是靠
推理能推出来的。

## Q37：`MetricsReporter` 的 `on_tick_`（`std::function<void()>` 回
调钩子）为什么不直接在内部调用 `sd_notify`，而要绕这一圈？

因为"定时汇报运行状态"（`MetricsReporter` 自己的职责）和"通知
systemd 我还活着"（`main.cpp` 为了 systemd 集成才需要的额外行为）是
两件不该绑死在一起的事——`MetricsReporter` 不应该知道、也不应该依
赖"systemd 存不存在"这个具体用途。用一个回调钩子，让真正需要
`sd_notify` 的那一方（`main.cpp`）自己决定要不要接上这个钩子，
`MetricsReporter` 本身完全不用碰 `<systemd/sd-daemon.h>`，也能被将
来任何不需要 systemd 的场景直接复用。这是一种解耦（decoupling）：一
个模块只做自己该做的事，把"这个心跳还能派上什么别的用场"这个决定权
交给使用它的一方。

## Q38：`AcquisitionWorker`/`Watchdog` 用"短超时 `poll`/`wait_for`
循环检查停止标志"，`MetricsReporter` 用
`cv_.wait_for(lock, interval_, [this]{ return stop_requested_; })`
这种带谓词的写法，两者最终效果一样吗？

效果一样，都是`docs/systems-programming-patterns.md`里"带超时的等
待"这一类——都能被 `stop()` 提前叫醒、也能到设定的时间自动醒过来重
新检查一次，只是实现工具不同：前者是"设一个较短的固定超时，醒来后
手动判断该不该继续"，后者是把"等多久"和"被提前用条件变量唤醒"这两
件事都交给 `std::condition_variable::wait_for` 一次性处理（第三个参
数是谓词，`wait_for` 内部会在超时或者被唤醒时都检查一次这个谓词，只
有谓词为真才真正返回）。两种写法都是同一个通用套路的具体实现方式，
不是能力上有差异。

## Q39：Yocto 造一个镜像，总共涉及哪几样东西？

四样东西 + 一个动作。东西：① BitBake——真正干活的引擎本身（Python
写的通用调度工具，自己不懂任何 Linux/嵌入式知识）；② 配方
（recipe）——"怎么编译安装某一个具体软件"的说明书；③ 层
（layer）——存放配方的文件夹，按"谁写的"分类（官方一层、社区一层、
板厂一层、自己一层）；④ 镜像配方（image recipe）——一种特殊的配方，
内容不是"怎么编译"，而是一张写满软件名字的"购物清单"。动作：先决定
这次要启用哪几层，BitBake 才知道去哪几个地方找配方。执行顺序是：先
扫一遍所有启用层里的全部配方（建立"名字 → 配方"的索引），再打开购
物清单挨个按名字去索引里查，查到就照着对应配方真正下载/编译/安装，
清单上所有东西都装完后打包成一个可烧录的镜像文件。

## Q40：`build/conf/bblayers.conf` 和 `<层>/conf/layer.conf` 是同一
个东西吗？

不是，是两种完全不同角色的文件，只是名字像。`bblayers.conf` 只有一
份，住在编译目录里，内容是"这次启用哪几层的路径"——一张花名册。
`layer.conf` 每一层各自有一份，住在每层自己的 `conf/` 下，内容是
"我（这一层）叫什么名字、优先级多少"——层自己的身份证，只描述自己，
不涉及别的层。

## Q41：购物清单（镜像配方）里会写"用哪个层的哪个配方"吗？

不会，购物清单上只写软件的名字，完全不提这个名字是哪个层提供的——
层与配方的对应关系，是 BitBake 在启动时扫描所有启用层后自动建立、
自动查询的，没有任何一个文件是手写去声明"这个名字对应哪个层"的。

## Q42：如果两个不同层里恰好有同名配方，听谁的？这个"优先级"信息写
在哪？

每一层在自己的 `conf/layer.conf` 里声明一个优先级数字（比如这个项
目里 `meta-device-platform` 是 6、`meta-raspberrypi` 是 9），数字大
的层说了算。这是**层级别**的单一数字（一层只有一个优先级，层内所有
配方共用，不是每个软件单独定优先级），不写在共享的 `bblayers.conf`
里。这套机制不只是"意外撞车时的仲裁"，更常见的实际用途是**主动覆
盖/定制别人已经写好的配方**——想微调一个官方层提供的软件，不用去改
官方层的文件，只需要在自己层里放一个同名（或用 `.bbappend`）的配
方，靠更高的优先级让自己这份生效。
